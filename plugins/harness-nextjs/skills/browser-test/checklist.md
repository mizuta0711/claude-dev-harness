# ブラウザテスト チェックリスト

browser-tester エージェントが使用する共通チェックリスト。
画面固有のテスト項目は、各機能設計書の**「動作確認計画」の章**に記載する
（章番号は変わりうるため、見出し名で探すこと）。
**章が無い設計書（M の最小形）では、「受け入れ基準チェックリスト」の各行の確認方法が画面固有のテスト項目になる。**

## 壊れていないか（共通チェック項目）

すべての画面で確認する項目:

### 表示・レンダリング
- [ ] ページが正常に表示される（白画面・エラー画面でない）
- [ ] コンソールにエラーが出ていない
- [ ] ローディング状態が適切に表示される（スケルトン/スピナー）

### レイアウト
- [ ] ヘッダー・ナビゲーションが表示され、機能する
- [ ] コンテンツが多い場合にスクロールが正しく機能する
- [ ] 要素のはみ出し・重なりがない

### レスポンシブ
- [ ] スマホ幅（375px）でレイアウトが崩れない
- [ ] PC幅（1280px）でレイアウトが崩れない
- [ ] ブレークポイント前後で切り替えが正しい

### インタラクション
- [ ] ボタン・リンクのクリックが正しく動作する
- [ ] フォーム入力・送信が正常に動作する（該当する場合）
- [ ] エラー時に適切なフィードバックが表示される（該当する場合）

## 画面の使い方

**「崩れていない」と「使いやすい」は別である。** スクロールできても、縦に長すぎて目的の項目を探せないなら、利用者は困る。
**原則は「利用者の不利益になるものを指摘する」。数値ごとの合否は付けず、点数にもしない**（致命的な 1 点が平均に隠れる）。

### 測る

対象画面ごとに、**PC（1280x800）とスマホ（375x812）**の両方で行う。前回と比べられるよう、表示領域の大きさは変えない。

1. `browser_resize` で表示領域を合わせ、読み込みが終わるのを待つ（ページの先頭で測る）
2. 測定スクリプト（`ux-metrics.js`）の本文を読み、`browser_evaluate` の `function` に次の形で渡す。
   主要な操作は、ボタンなどの文字なら `primaryText`、セレクタなら `primary` で指定する。無ければ `{}` にする。
   画面の下にある操作（保存など）が目的なら、上部のボタンではなくそれを指定する

   ```js
   () => (ここに本文)({ primaryText: "保存" })
   ```

3. `browser_take_screenshot` を `fullPage: true` で撮る。`filename` は作業ルートからのパスで、
   `tests/browser-evidence/{フォルダ}/screenshots/連番_ページ名_pc_full.png`（スマホは `_sp_full.png`）と指定する。
   `innerScroll` が `true` の画面は内側の領域が画像に写りきらないので、その領域をスクロールして続きも撮る
4. 同じ画面の前回の値を、`tests/browser-evidence/*/report.md` の新しいものから探して「前回との差」に書く（無ければ「前回なし」）

| 記録する数値 | スクリプトの値 |
|------------|--------------|
| 何画面分（ページまたは本文の領域の高さ ÷ 表示領域の高さ） | `pageScreens`（本文が内側の領域でスクロールするなら `innerScroll` が `true`） |
| 内容幅の比（文字・画像・操作部品が広がる幅 ÷ 表示領域の幅。縦の帯ごとに測り、広い方から 4 分の 1 の位置の値） | `contentWidthRatio` |
| 列数（横に並ぶ箇所の最大） | `columns` |
| 横スクロール | `horizontalOverflowPx` |
| 主要操作が最初の画面に入るか | `primaryInFirstScreen`（`null` は指定なし、`not-found` は見つからない） |
| 最小の文字・最小のボタン | `minFontPx` / `minButtonPx`（`smallestButton` が該当の部品） |

### 項目が最も多い状態で見る

機能追加のたびに項目が増える画面（設定項目・メニューなど）は、**項目が最も多い状態**で確認する。
テストデータは作らないので、その状態を用意できないときは「確認した場面」に**最大の状態は未確認**と書く。

### ひとこと触れる目安

**次に当たった数値には、困るか困らないかをひとこと書く。合否ではない。**
当たっていても問題なしでよく、当たっていなくても困るなら指摘する。

| 数値 | 目安（初期値） |
|------|-------------|
| 何画面分 | 3 を超える / 前回より 1 以上伸びた |
| 内容幅の比（PC） | 0.6 未満で、何画面分が 1.25 を超える |
| 横スクロール | 0 より大きい |
| 主要操作が最初の画面に入るか | `false` / `not-found` |
| 最小の文字 | 12px 未満 |
| 最小のボタン | 24px 未満 |

目安は 1 種類の画面群の実測から置いた仮の値である。プロジェクトの rules に別の目安があれば、そちらを使う。

### 判断する

- **指摘は「誰が・何をするときに・どう困るか」で書く。** 書けないものは指摘にしない
- **問題がなくても、確認した場面を書く**
- **目的は数値を変えることではない。** スクロールをなくす・余白を埋めること自体を求めない
- **余白が問題になるのは、表示する内容があるのに、並べ方のせいで使われていないときだけ。** 内容が少ない画面の余白は問題にしない
- 重要度の既定は**改善提案（低・中）**で、それだけでは判定を下げない。
  主要な操作ができない・たどり着けないほど困るなら、「発見した問題」に壊れている問題として書く

## 使い方

### スポットテスト時
1. 「壊れていないか」の共通チェック項目を対象画面に対して実施
2. 「画面の使い方」の測定と下書きを対象画面に対して実施
3. 機能設計書の「動作確認計画」に固有テスト項目があれば、それも実施
   （章が無い設計書では、受け入れ基準の各行の確認方法を実施）

### フルテスト時
1. 全画面に対して、共通チェック項目と「画面の使い方」の測定を実施
2. 作業中の機能設計書があれば、その評価計画も実施
