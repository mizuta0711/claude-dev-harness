# ブラウザテスト実施

`harness.config.json` の `verification.skill` が `browser-test` の環境で使う動作確認スキル。

## Step 1: テスト対象の特定

$ARGUMENTS が `full` の場合 → **フルテスト**として browser-tester を呼び出す。

$ARGUMENTS に画面URLが指定されている場合 → その画面を **スポットテスト**。

$ARGUMENTS が未指定の場合 → 直近の変更ファイルからUI変更を含む画面を特定:

```bash
git diff --name-only
```

変更がない場合は直近1コミット:

```bash
git diff --name-only HEAD~1
```

### 変更ファイル → 対象画面の対応（ヒューリスティック）

- `src/app/{path}/page.tsx` → 対応する URL パス
- `src/app/{path}/**/*.tsx` → そのルート配下の画面
- `src/features/{feature}/` → その feature が使われている画面
- `src/components/` → 影響範囲が広い可能性があるため、作業中の機能設計書を参照して対象画面を決定

### データを描画する画面をたどる

**画面のファイルを変えなくても、一覧・定義・設定の項目が変われば画面の見た目は変わる。**
上の対応で見つかった画面に、次で見つかった画面を足す。**見つからなかったときも、終了する前に必ず行う。**

1. 作業中の機能設計書（`docs/features/` 直下）に見出し「対象と操作フロー」があれば、そこに書かれた画面を対象に入れる
2. 画面以外の変更ファイルを、**一覧を出したときと同じ範囲の** `git diff` で読み、**表示される項目**（一覧・定義の要素、ラベル、API の応答の項目）が変わったものを選ぶ。
   内部処理・型・テストだけの変更は選ばない
3. 選んだファイルを import している箇所を Grep でたどり、`page.tsx` に着いたらその URL を対象に入れる（たどるのは 3 段まで）。
   `layout.tsx` / `template.tsx` に着いたら、その配下の代表的な画面を 1 つ入れる。
   API の応答が変わったときは、その API のパスを呼んでいる画面を探す

1〜3 でも画面が無ければ、「UI変更なし（表示される項目の変更も無し）。ブラウザテスト不要です。」と報告して終了。

## Step 2: 評価計画の確認

関連する機能設計書（`docs/features/` 直下の作業中の設計書）に
**「動作確認計画」の章**がある場合、その内容に基づいてテストを実施する。
**章が無い設計書（M の最小形。harness-core 0.42.0 以降）では、「受け入れ基準チェックリスト」の各行の末尾に書かれた確認方法を入力にする**
（確認方法が操作手順・「目視」の行を画面固有のテスト項目として扱う。確認スクリプト名の行は、そのスクリプトの結果を確かめる）。

> 章番号ではなく**見出し名で探すこと**。機能設計書テンプレートの章構成は変わりうるため、
> 「§4」「§5」のような番号での参照はしない。

設計書がない場合は `${CLAUDE_SKILL_DIR}/checklist.md` の共通チェック項目で実施する。

## Step 3: エビデンスフォルダの作成

browser-tester に委譲する**前に**、メインエージェント側でエビデンスフォルダを作成する:

```bash
# フォルダ名: YYYYMMDD_HHMMSS_テスト対象（例: 20260418_153000_example-page）
mkdir -p tests/browser-evidence/YYYYMMDD_HHMMSS_テスト対象/screenshots
```

## Step 4: browser-tester エージェントに委譲

エビデンスフォルダのパスと**チェックリストの絶対パス**を必ず含めて呼び出す
（サブエージェントは `${CLAUDE_SKILL_DIR}` を解決できないため、呼び出し側が解決して渡す）:

```
# スポットテスト
Agent(subagent_type: "browser-tester", prompt:
  "スポットテスト。対象: {対象画面URL}。
   変更内容: {変更ファイルの概要}。
   確認観点: {評価計画の内容 or チェックリストの該当項目}。
   主要な操作: {画面ごとの、利用者がその画面で最もしたい操作。画面の下にある操作が目的ならそれを選ぶ。無ければ「なし」}。
   チェックリスト: {${CLAUDE_SKILL_DIR}/checklist.md を解決した絶対パス}。
   測定スクリプト: {${CLAUDE_SKILL_DIR}/ux-metrics.js を解決した絶対パス}。
   エビデンス保存先: tests/browser-evidence/{作成したフォルダ名}/")

# フルテスト
Agent(subagent_type: "browser-tester", prompt:
  "フルテスト。主要画面を網羅的に確認する。主要な操作は画面ごとに判断し、report.md に「推定」と書く。
   チェックリスト: {${CLAUDE_SKILL_DIR}/checklist.md を解決した絶対パス}。
   測定スクリプト: {${CLAUDE_SKILL_DIR}/ux-metrics.js を解決した絶対パス}。
   エビデンス保存先: tests/browser-evidence/{作成したフォルダ名}/")
```

## Step 5: レポート保存（メインエージェントが責任を持つ）

**サブエージェントが report.md を保存していない場合、メインエージェントが必ず自分で保存する。**

browser-tester の返答を受け取ったら:

1. `tests/browser-evidence/{フォルダ名}/report.md` が存在するか確認する
2. **存在しない場合** → browser-tester の返答内容をもとに、以下のフォーマットで `report.md` を自分で作成する
3. **存在する場合** → 内容に不足がないか確認し、不足があれば追記する

```markdown
# ブラウザテスト結果

- **実施日時**: YYYY-MM-DD HH:MM
- **モード**: スポットテスト / フルテスト
- **テスト対象**: [ページURL・機能名]
- **変更内容**: [何を変更したか（スポットテストの場合）]

## 機能テスト結果

| # | テスト項目 | 操作内容 | 期待結果 | 実際の結果 | 判定 |
|---|-----------|---------|---------|-----------|------|
| 1 | | | | | ✅/❌ |

| 観点 | 結果 | 確認した内容・問題 |

## 総合判定

- **機能テスト**: ✅ 全項目合格 / ⚠️ 一部不合格 / ❌ 重大な問題あり
- **壊れていないか**: ✅ 問題なし / ❌ 問題あり（N 件）
- **画面の使い方**: 指摘なし / 指摘 N 件（中 x・低 y）
- **判定**: ✅ 合格 / ⚠️ 条件付き合格 / ❌ 不合格
```

### 「画面の使い方」はメインエージェントが確定する

browser-tester が担うのは**採取と下書き**で、**判断はこのセッションが行う**。
`report.md` の測定値と、PC 幅・スマホ幅のページ全体のスクリーンショットを自分で見て、「画面の使い方」の節を直す
（フルテストで画面が多いときは、目安に当たった画面と前回から数値が変わった画面を見る）。

- **基準は `${CLAUDE_SKILL_DIR}/checklist.md` の「画面の使い方」に従う。** 数値では合否を付けない
- 「誰が・何をするときに・どう困るか」を書けないものは指摘にしない
- 目安に当たった数値には、困るか困らないかを必ずひとこと書く（黙って通さない）
- 指摘を増減したら、「総合判定」の件数も合わせる

## Step 6: 結果報告

ユーザーに以下を報告する:
- 総合判定（✅ 合格 / ⚠️ 条件付き合格 / ❌ 不合格）
- テスト対象の画面一覧
- 発見した問題の件数と重要度
- 「画面の使い方」の指摘の件数と、目安に当たった数値
- エビデンスの保存先: `tests/browser-evidence/{フォルダ名}/report.md`
