# 利用実績の監査

**「この仕組みは今も必要か」を、記憶ではなく実測で答える。**

`update-docs` / `sync-check` が「設計書と実装のずれ」を見るのに対し、
このスキルは **「配ったものと、実際に動いたもののずれ」** を見る。

> **実測（2026-08-17）**: この監査を初めて回したとき、**4ヶ月間ゼロ起動のエージェントと、
> 「自動実行される」と書いてあるのに実装が無いスキル**が見つかった。
> どちらも**動かなくても何も起きない**ので、実測するまで誰も気づいていなかった。

---

## ⚠️ このスキルが守ること（過去に2回間違えた）

| # | 守ること | 破ったときに起きたこと |
|---|---------|---------------------|
| **1** | **`~/.claude` を全部探す。1個だと決めつけない** | Windows 側だけを見て「ゼロ起動」と判定したエージェントが、**WSL 側では3回起動していた**。危うく消すところだった |
| **2** | **ゼロ起動は必ず原因まで出す**（未配線 / 呼ばれていない）。**回数だけ出さない** | 原因を確かめずに「捨てる候補」と報告した。実際は**呼び出し側が存在しないだけ**で、機能は要るものだった |
| **3** | **期間・件数・データ量を必ず併記する** | 保持期間は短く、しかも**連続していない**（間の月が消えていることがある） |
| **4** | **要否を判断しない。材料を出すだけ** | 「0回だから要らない」は導けない。**間に「呼ぶ側が居るか」「呼ぶ理由が書かれているか」の2問が挟まる** |

## Step 1: `~/.claude` を全部見つける

**ここを飛ばすと、この監査の結果はその分だけ嘘になる。**

```bash
ls -d ~/.claude/projects 2>/dev/null            # いま動いている環境
```

**さらに、次を必ず確認する**（あれば `projects` ディレクトリのパスを控える）:

| 環境 | 探し方 |
|------|--------|
| **WSL**（Windows から） | `wsl -l -q` で distro を列挙 → `wsl -e bash -lc 'ls -d ~/.claude/projects'` |
| **devcontainer / リモート** | プロジェクトが `.devcontainer/` を持つなら、**コンテナ内に別の `~/.claude` がある**。マウント設定を見る |
| 別ユーザー・別マシン | チームで使っているなら、その人の実測は**ここには出ない**。報告に明記する |

> **判断材料**: プロジェクトが devcontainer を持つかは `ls -d .devcontainer` で分かる。
> **「見つからなかった」と「無い」は違う。** 見つけられなかったものは報告に書く。

引数で追加のディレクトリが渡された場合は、それも対象に加える。

## Step 2: 配布物の一覧を作る

`--known` に渡すと、**transcript に混ざった引用テキストを隔離**できる
（実測: 会話の中で説明のために書いた名前が「2回起動」として数えられた）。

```bash
ls -d "${CLAUDE_PLUGIN_ROOT}"/../*/skills/*/ 2>/dev/null | sed 's|.*/skills/||;s|/$||' | sort -u | paste -sd,
```

導入済みプラグインが分からない場合は `.claude/settings.json` の `enabledPlugins` を見る。

## Step 3: 集計する

```bash
node "${CLAUDE_PLUGIN_ROOT}/skills/usage-audit/scripts/usage-audit.mjs" \
  <projects-dir> [<projects-dir> ...] --known=<スキル名をカンマ区切り>
```

`--json` を付けると機械可読な出力になる。

**このスクリプトは判断をしない。** 数えるだけである。

## Step 4: ゼロ起動の原因を特定する（最重要）

**回数だけ報告してはいけない。** 配布物と突き合わせ、**動いていないものそれぞれについて原因を出す。**

| 原因 | 見分け方 | 対応の方向 |
|------|---------|-----------|
| **未配線** | **呼び出し側が存在しない**、または**コメントブロックの中にしかない** | **捨てるのではなく配線する** |
| **宣言と実装のずれ** | 「自動実行される」と書いてあるのに、呼び出しが無い | **嘘を先に消す。** そのうえで実行点を決める |
| **明示呼び出し設計** | ユーザーが呼ぶ前提で、そもそも自動起動を想定していない | **0回は欠陥とは限らない。** 使う機会があったかで判断する |
| **本当に不要** | 呼び出しもあり、呼ぶ理由も書かれていて、それでも使われない | ここで初めて要否の検討に入る |

呼び出し側は次で探す。**コメントブロック（`<!-- ... -->`）の中は呼び出しと認めない。**

```bash
grep -rn "<名前>" "${CLAUDE_PLUGIN_ROOT}/.." --include="*.md" | grep -v "/<名前>/"
```

> **なぜコメントを除くのか**: 実測で、あるエージェントの唯一の呼び出しが
> **「作成後、このセクションは削除してよい」と書かれたコメントの中**にあった。
> 設計書を作った時点で消えるので、**実際には一度も呼ばれない。**

## Step 5: 規律の遵守を読む

スクリプトが出す3項目は**目安**である。数字だけで断じない。

| 項目 | 読み方 |
|------|--------|
| 範囲まるごとの git 操作 | **いつのものか**を見る。ガード導入前の期間なら、それは過去の記録であって現状ではない |
| `model` 未指定のサブエージェント起動 | **その場限りの依頼**でも指定する規律になっている（`constitution.md`）。継承すると委譲の目的の1つ（コスト）が消える |
| `pre-push-check` の無い push | **同一 transcript 内の出現順で見た目安**。別セッションで実行した場合は拾えない |

## Step 6: 報告と記録

`docs/reviews/YYYYMMDD_利用実績監査.md` に残す。**チャットに流して終わりにしない。**

記録に必ず含めるもの:

- **見たディレクトリの一覧**（と、見つけられなかったもの）
- 期間・transcript 件数・データ量
- スキル・エージェントの起動回数
- **ゼロ起動それぞれの原因**（Step 4）
- 規律の実測と、その期間の解釈

最後に、次回の判定に使うマーカーを更新する:

```bash
node -e "require('fs').writeFileSync('.claude/.harness-audit.json', JSON.stringify({lastRunAt:new Date().toISOString().slice(0,10)},null,2)+'\n')"
```

> このファイルは `.gitignore` 済み（ハーネスの作業ファイル）。
> SessionStart フックがこれを読み、**前回から日数が空いたら知らせる**。

## Step 7: 判断は返す

**要否の判断はユーザーが行う。** このスキルは材料を出すところまで。

削除を伴う場合は、**別コンテキストの査読を通してから確定する**（`constitution.md`）。
査読者には次の2点を必ず見てもらう:

1. **探した場所が足りているか**（`~/.claude` は複数ある）
2. **ゼロ起動の原因は「不要」か「未配線」か**
