# 設計レビュー

機能設計書の Stage 1 / Stage 2 に対応するレビューを実施する。

## モード

| モード | 対象 | 使用エージェント |
|-------|------|-----------------|
| `feature` | 「3. 機能・画面設計（Stage 1）」 | code-reviewer + 体験系アドバイザー（あれば並列実行） |
| `tech` | 「4. 技術設計（Stage 2）」 | code-reviewer |
| (省略) | 設計書全体 | code-reviewer |

## Step 1: 対象設計書の特定

$ARGUMENTS が `feature` / `tech` のいずれかならそのモード、それ以外・未指定なら全体モード。

対象の機能設計書（`docs/features/yyyymmdd_*.md`）は以下の順で特定する:

1. 未コミット変更の中の `docs/features/` 配下（`git diff --name-only`）
2. 直近コミットの中の `docs/features/` 配下（`git diff --name-only HEAD~1 HEAD`）
3. それでも見つからなければユーザーに確認

## Step 2: 設計書の部分読み（トークン効率化）

**全文読みはしない**。必要なセクションのみ読む。

セクションの開始行は**見出し名で検索する**（番号は変わりうるため番号で検索しない）:

```
grep -n "^## .*機能・画面設計" {設計書パス}
grep -n "^## .*技術設計" {設計書パス}
grep -n "^## .*動作確認計画" {設計書パス}
```

| モード | 読む範囲 |
|-------|---------|
| `feature` | メタ情報 + Stage 1 + 関連する `designDocs.docs` の該当文書 |
| `tech` | メタ情報 + Stage 2 + 関連する `designDocs.docs` の該当文書 |
| (省略) | 設計書全体 + 関連する設計書 |

`designDocs` は `.claude/harness.config.json` の `designDocs.docs`（`file` / `tracks` / `sources`）を見て決める。
config が無い場合は `docs/設計書/` 配下から関連しそうな文書を推定する。

## Step 3: トレーサビリティ検査（全モード共通・軽量）

エージェント起動の前に、設計書内で完結する整合チェックを行う:

| # | 検査 | 不整合の例 |
|---|------|-----------|
| 1 | **未解決事項がゼロか**（Stage 1 の `[NEEDS CLARIFICATION]`） | ❓未解決が残ったまま承認しようとしている |
| 2 | **受け入れ基準 → 技術設計**（feature/全体では対象外、tech で実施） | Stage 1 の受け入れ基準に対応する設計が Stage 2 に無い |
| 3 | **技術設計 → タスク一覧** | Stage 2 で決めた変更ファイルがタスク一覧に現れない |
| 4 | **受け入れ基準 → 動作確認計画** | 受け入れ基準に対応する確認項目が無い |
| 5 | **タスクの依存・並列マーカー**（L 規模のみ） | 依存関係が矛盾している / 競合するタスクに `[P]` が付いている |

検査 2〜4 は「対応表」として結果に載せる（どの基準がどこに落ちたか）。**漏れは指摘として扱う。**

## Step 4: エージェント起動

### feature モード

code-reviewer を起動する。加えて、**有効なプラグインに体験系アドバイザー
（`product-advisor` / `game-designer` 等、企画・UX 体験を担当する agent）があれば並列で起動する**。
無ければ code-reviewer のみで実施し、その旨を結果に明記する。

```
Agent(subagent_type: "code-reviewer", model: "sonnet", prompt:
  "Stage 1 設計レビュー。対象: {設計書パス} の「機能・画面設計」セクション。
   観点:
   【設計書整合性】他の設計書との矛盾 / 受け入れ基準がテスト可能な形か / 動作確認計画の記入状況
   【UI・体験の設計観点】既存パターンとの一貫性、情報階層、アクセシビリティ、
     想定表示サイズでの成立性、再利用可能な既存資産の有無
   ※ 環境固有の観点（デザインシステム、プラットフォーム規約）は
     プロジェクトの rules / 環境プラグインが提供するものを参照すること。
   結果は『要修正』テーブル形式で返して。")

Agent(subagent_type: "{体験系アドバイザーの agent 名}", model: "sonnet", prompt:
  "Stage 1 設計レビュー。対象: {設計書パス} の「機能・画面設計」セクション。
   観点: 課題-解決策フィット / ユーザーフローの自然さ・摩擦 / 代替案 / 優先度 / 既存機能との整合。
   結果は『課題・懸念』テーブル形式（優先度: 高/中/低）で返して。")
```

**矛盾・タイムアウト時**:
- 片方が失敗した場合、成功した側の結果でレポートを作り、失敗側は再実行を促す
- 両者の指摘が真逆のケース（技術制約 vs 体験要求）は自動解決せず「要判断」として明示する

### tech モード

```
Agent(subagent_type: "code-reviewer", model: "sonnet", prompt:
  "Stage 2 設計レビュー。対象: {設計書パス} の「技術設計」セクション。
   観点:
   - インターフェース仕様の入出力例が全て記載されているか
   - データ構造・永続化の変更とインターフェースの整合
   - 内部設計（サービス・ViewModel・フック等）の戻り値とインターフェースの整合
   - 命名規則・型安全性（プロジェクトの rules に従う）
   - Stage 1 の受け入れ基準が全て設計に反映されているか（対応表で示す）
   結果は『要修正』テーブル形式で返して。")
```

### 全体モード

Stage 分離されていない設計書向け。tech の観点 + 動作確認計画のチェックを包括的に実施する。
動作確認計画が未記入の場合、「1. 概要」と設計内容から草案を生成して設計書に追記する。

## Step 5: 結果統合 + ファイル保存

`docs/reviews/YYYYMMDD_HHMMSS_design-review-{mode}.md` に保存:

```markdown
# Stage {1|2} 設計レビュー結果

- 実施日時: YYYY-MM-DD HH:MM
- 対象: {設計書パス}
- モード: {feature|tech|全体}

## 総合判定: ✅ 承認 / ⚠️ 条件付き承認 / ❌ 差し戻し

## トレーサビリティ検査

| # | 検査 | 結果 | 詳細 |
|---|------|------|------|

## code-reviewer

| # | 重要度 | 内容 | 対象 | 対応状況 |
|---|--------|------|------|---------|

## 体験系アドバイザー（起動した場合）

| # | 優先度 | 観点 | 指摘内容 | 対応状況 |
|---|--------|------|---------|---------|

## 指摘が競合する場合（要判断）

| # | 競合内容 | 技術側の主張 | 体験側の主張 | ユーザー判断 |
|---|---------|-------------|-------------|-------------|
```

## Step 6: 機能設計書への記録

レビュー結果ファイルを保存した後、機能設計書の「Stage 1 レビュー記録」/「Stage 2 レビュー記録」表に
日付 / レビューファイルパス / 判定 / 対応状況 を追記する。

## Step 7: ユーザーへの報告

- 総合判定
- トレーサビリティ検査の結果（漏れ件数）
- 要修正の件数、競合（要判断）の件数
- レビューファイルのパス
- 次のアクション（feature: ユーザー承認後 Stage 2 へ / tech: 承認後 実装へ）
