# 設計レビュー

機能設計書の Stage 1 / Stage 2 に対応するレビューを実施する。

## モード

| モード | 対象 | 使用エージェント |
|-------|------|-----------------|
| `feature` | 「3. 機能・画面設計と受け入れ基準（Stage 1）」。**L**。画面に触る M でユーザーが頼んだときも（規模は M のまま。結果は 4-5 に「対象: Stage 1」で記録） | code-reviewer + 体験系アドバイザー（あれば並列実行） |
| `tech` | 「4. 技術設計（Stage 2）」の**全体**。**L と試作**（M は既定で回さない。頼まれれば回す） | code-reviewer |
| **`tech Phase{n}`** | **Stage 2 のうち「共通」の小見出し ＋ そのフェーズの小見出しだけ** | code-reviewer |
| (省略) | 設計書全体 | code-reviewer |

### `tech Phase{n}`（フェーズ指定）はいつ使うか

Stage 2 を**フェーズごとに書く**とき（`new-feature/開発フローと規模判定.md` §2-3）、
**そのフェーズの実装に入る直前**に回す。設計書は Stage 2 の中に
**`#### Phase {n}: 〇〇`** の小見出しと、フェーズ名の付かない **`#### 共通`** を持つ。

**節の番号では探さない。** 範囲は**小見出しの文字列**で決める:

```
grep -n "^#### *Phase *{n}" {設計書パス}     # そのフェーズ
grep -n "^#### *共通" {設計書パス}               # 全フェーズに効くもの
```

**引数のフェーズ名は正規化して照合する**（表記ゆれで空振りさせない）:

| 渡された形 | 扱い |
|---|---|
| `Phase2` / `Phase 2` / `phase2` | すべて `Phase\s*2` として照合する |
| `2`（数字だけ） | 同じく `Phase\s*2` として扱う |
| 日本語などのフェーズ名（例 `基盤整備`） | **小見出しの `Phase {n}: ` の後ろの名前**とも照合する |

**該当する小見出しが1つも無ければ、そこで止めてユーザーへ報告する。**
Stage 2 がフェーズ別に分かれていない設計書に対してフェーズを指定しても絞れないため、
**`tech`（全体）で回すよう案内する**。番号が近い別の節を読みにいかない。

## Step 1: 対象設計書の特定

`$ARGUMENTS` の先頭が `feature` / `tech` のいずれかならそのモード、それ以外・未指定なら全体モード。
**`tech` に続けて `Phase{n}`（例: `tech Phase2`）が渡されたらフェーズ指定**として扱う。

対象の機能設計書（`docs/features/yyyymmdd_*.md`）は以下の順で特定する:

1. 未コミット変更の中の `docs/features/` 配下（`git diff --name-only`）
2. 直近コミットの中の `docs/features/` 配下（`git diff --name-only HEAD~1 HEAD`）

**`docs/features/prototype/` は候補に含める。** あちらは**試作・作業中**の置き場で、
**試作でも Stage 1 の査読は残す**と決めている（`/harness-core:new-prototype`）。
除外しているのは `planned/` だけなので**既定で含まれる**が、
**`planned/` と同じだと読まれやすい**ので明記する。

**`docs/features/planned/` は候補から外す。** あちらは**着手前**の置き場で、
**着手するときに直下へ `git mv` してからレビューする**（`sync-check` と同じ扱い）。
マイルストーンに分けたとき「残りの Stage 1 も先に書いてよい」ので、
除外しないと**未着手の設計書が必ず候補に並ぶ**。
3. それでも見つからなければユーザーに確認

## Step 2: 設計書の部分読み（トークン効率化）

**全文読みはしない**。必要なセクションのみ読む。

セクションの開始行は**見出し名で検索する**（番号は変わりうるため番号で検索しない）:

```
grep -n "^## .*機能・画面設計" {設計書パス}
grep -n "^## .*技術設計" {設計書パス}
grep -n "^## .*動作確認計画" {設計書パス}
```

| モード | 読む範囲 |
|-------|---------|
| `feature` | メタ情報 + Stage 1 + 関連する `designDocs.docs` の該当文書 + `projectDocs.requirements` の見出し |
| `tech` | メタ情報 + Stage 2 + **受け入れ基準の節**（検査2・4 の起点。**規模によらず読む**）+ **UI・挙動に触るなら「対象と操作フロー」の節** + 関連する `designDocs.docs` の該当文書 + `projectDocs.policy` の該当文書 |
| **`tech Phase{n}`** | メタ情報 + **「設計方針への書き戻し」** + Stage 2 の **`#### 共通`** と **そのフェーズの `#### Phase {n}`** だけ + 受け入れ基準の**そのフェーズ分** + 上と同じ外部文書 |
| (省略) | 設計書全体 + 関連する設計書 |

**フェーズ指定では、他のフェーズの小見出しを読まない。** これが効き目そのものである
（Stage 2 は設計書の大半を占めるので、全体を読むと部分読みが無意味になる）。
探し方は上の「`tech Phase{n}` はいつ使うか」の grep に従う。

`designDocs` は `.claude/harness.config.json` の `designDocs.docs`（`file` / `tracks` / `sources`）を見て決める。
config が無い場合は `docs/設計書/` 配下から関連しそうな文書を推定する。

**2種類の文書を混同しないこと**（どちらも config が正典。登録が無ければ素通りする）:

| キー | 中身 | 検査の向き |
|------|------|-----------|
| `designDocs` | **実装の現況**（API一覧・ER図等） | 設計書の内容が実態と食い違っていないか |
| `projectDocs.policy` | **プロジェクトの設計方針**（層構成・エラー処理方式等） | **Stage 2 が既存の方針に反していないか**。反するなら「方針を変えるのか、設計を直すのか」を明示させる |
| `projectDocs.requirements` | **要件・ドメイン知識** | Stage 1 がドメイン制約・ビジネスルールに反していないか |

## Step 3: トレーサビリティ検査（全モード共通・軽量）

エージェント起動の前に、設計書内で完結する整合チェックを行う:

| # | 検査 | 不整合の例 |
|---|------|-----------|
| 1 | **未解決事項がゼロか**（Stage 1 の `[NEEDS CLARIFICATION]`） | ❓未解決が残ったまま承認しようとしている |
| 2 | **受け入れ基準 → 技術設計**（feature/全体では対象外、tech で実施）。**M 規模でも実施する** | 受け入れ基準に対応する設計が Stage 2 に無い |
| 2b | **フェーズ指定時は、そのフェーズの受け入れ基準だけを検査2 の対象にする** | 未着手フェーズの基準まで「設計に落ちていない」として挙がる（**誤検出**） |
| 3 | **（設計時は実施しない）** 技術設計 → タスク一覧 | 0.42.0 で外した。「作成・変更ファイル」は**実装後に書く節**なので設計時には無い。差分との一致は `/harness-core:code-review` が見る |
| 4 | **受け入れ基準の各行に確認方法が書かれているか**（「動作確認計画」の章があれば、そちらとの対応も見る）。**M 規模でも実施する** | 確認スクリプト名・操作手順・「目視」などが無い行がある |
| 5 | **タスクの依存・並列マーカー**（L 規模のみ） | 依存関係が矛盾している / 競合するタスクに `[P]` が付いている |
| 6 | **技術設計にプログラム言語のコードブロックが無いか**（tech / 全体で実施。0.43.0。**M は既定で tech を回さないので、`code-review` 層1 が同じ基準で見る**） | 「技術設計」の章の中の ```` ``` ```` の言語名が**許す言語名**（下）**以外**（`ts` `tsx` `js` `cs` `kt` `py` など）。**「実装の写し」として重要度 中で指摘する**（差し戻しにはしない）。signature・interface・処理手順は設計書ではなくコードが持つ |

**許す言語名**（info string の**先頭の語**で判定。大文字小文字は区別しない。**この列挙が正**で、`TEMPLATE.md` 4 章のコメントは写し）:
`json` `jsonc` `json5` / `sql` `prisma` `graphql` `gql` `proto` / `yaml` `yml` `toml` `ini` `properties` `env` `dotenv` `xml` /
`http` / `sh` `bash` `console`（CLI の呼び出し例）/ `mermaid` `mmd` / `text` `txt` `plaintext` `csv` `diff` / 指定なし。

検査2・4 は「対応表」として結果に載せる（どの基準がどこに落ち、どう確認するか）。**漏れは指摘として扱う。**

**検査6 の探し方**: 章の範囲は見出し名で切る（`grep -n "^## .*技術設計"` から次の `^## ` まで）。
その範囲で `grep -n '^```'` を取り、開始行の言語名を見る。**許す言語名は上の列挙が正**で、
プロジェクトの `CLAUDE.md` に見出し「**設計書に置いてよいコードブロック**」があればその箇条書きを足す。
指摘の文は「4-4 の `ts` ブロック（N 行）は関数の signature で、実装の写し。決めたこと（代案と理由）だけ残して削る」の形。
**「作成・変更ファイル」が空であることは指摘しない**（実装後に書く節である）。

> **検査4 は二重にならない。** M は「動作確認計画」の章を持たないので、確認方法は受け入れ基準の行にしか無い。
> L で章があるときは、**各行の確認方法を正として、章の確認項目がそれと食い違わないか**だけを見る
> （同じ確認を2箇所で別々に数えない）。

**受け入れ基準の節が空のときは、検査2・4 を走らせず「受け入れ基準が未記入」を指摘として返す。**
**規模を理由に黙って飛ばさないこと。** 受け入れ基準は **M / L ともに必須**であり
（`TEMPLATE.md` 3-2・`constitution.md` §3）、空なら設計書側の欠落である。

> **0.41.0 まではここが無言で空振りしていた。** 受け入れ基準は Stage 1 の節の中にあり、
> M は Stage 1 を `⚪ 不要` にしていたため、**M で tech を回すたびに検査2・4 が起点を失い、
> しかもエージェントには無条件で「受け入れ基準が全て設計に反映されているか」を渡していた**
> （存在しないものの反映を求める形になっていた）。

**`tech Phase{n}` では検査の範囲を絞る**:

| 検査 | フェーズ指定時の扱い |
|---|---|
| 1 未解決事項 | **そのまま実施**（Stage 1 全体が対象。未解決が残っていれば Stage 2 に入れない） |
| 2 受け入れ基準 → 技術設計 | **そのフェーズの受け入れ基準だけ**を対象にする（上の 2b） |
| 3 技術設計 → タスク一覧 | **実施しない**（全体のときと同じ。「作成・変更ファイル」は実装後に書く） |
| 4 受け入れ基準の確認方法 | **そのフェーズの受け入れ基準の分だけ**。他フェーズ分が未記入でも指摘しない |
| 5 タスクの依存・並列 | **そのまま実施**（タスク一覧は全体で1つなので、フェーズをまたぐ依存の矛盾はここで出る） |

**受け入れ基準がフェーズ別に分かれていない設計書では、検査2・4 を絞れない。**
判定は `grep -n "^#### *Phase" {設計書パス}` が受け入れ基準の節の中で1件も当たらないこと。
そのときは**フェーズ指定を断り**、「受け入れ基準を `#### Phase {n}: 〇〇` の小見出しに分けるか、
`tech`（全体）で回すか」をユーザーに返す。**絞れないまま走らせて誤検出を出さない。**

## Step 4: エージェント起動

### feature モード

code-reviewer を起動する。加えて、**有効なプラグインに体験系アドバイザー
（`product-advisor` / `game-designer` 等、企画・UX 体験を担当する agent）があれば並列で起動する**。
無ければ code-reviewer のみで実施し、その旨を結果に明記する。

**M（メタ情報の変更規模が M）で feature を足したときは code-reviewer だけ。** 体験系アドバイザーは
ユーザーが明示したときだけ起動する（M の feature は置き場・文言を見るためのもので、企画の段ではない）。
**M では「動作確認計画」の章が無い**ので、プロンプトの「動作確認計画の記入状況」は
「受け入れ基準の各行の確認方法」に読み替えて渡す（章が無いことを欠落と判定させない）。

```
Agent(subagent_type: "code-reviewer", prompt:
  "Stage 1 設計レビュー。対象: {設計書パス} の「機能・画面設計」セクション。
   ※ M の最小形では「動作確認計画」の章が無い。受け入れ基準の各行の確認方法で代えているので、章の不在は指摘しないで。
   観点:
   【設計書整合性】他の設計書との矛盾 / 受け入れ基準がテスト可能な形か / 動作確認計画の記入状況（L）
   【UI・体験の設計観点】既存パターンとの一貫性、情報階層、アクセシビリティ、
     想定表示サイズでの成立性、再利用可能な既存資産の有無
   ※ 環境固有の観点（デザインシステム、プラットフォーム規約）は
     プロジェクトの rules / 環境プラグインが提供するものを参照すること。
   結果は『要修正』テーブル形式で返して。")

Agent(subagent_type: "{体験系アドバイザーの agent 名}", prompt:
  "Stage 1 設計レビュー。対象: {設計書パス} の「機能・画面設計」セクション。
   観点: 課題-解決策フィット / ユーザーフローの自然さ・摩擦 / 代替案 / 優先度 / 既存機能との整合。
   結果は『課題・懸念』テーブル形式（優先度: 高/中/低）で返して。")
```

**矛盾・タイムアウト時**:
- 片方が失敗した場合、成功した側の結果でレポートを作り、失敗側は再実行を促す
- 両者の指摘が真逆のケース（技術制約 vs 体験要求）は自動解決せず「要判断」として明示する

### tech モード

**フェーズ指定のときは、対象をその節に限ったうえで「他フェーズは対象外」と明示して渡す**
（書かれていない節を欠落と判定されないようにする）。

```
Agent(subagent_type: "code-reviewer", prompt:
  "Stage 2 設計レビュー。対象: {設計書パス} の「技術設計」セクション。
   ※「作成・変更ファイル」は実装後に書く節。空でも指摘しないで。
   ※フェーズ指定時: 対象は「設計方針への書き戻し」と、
     Stage 2 の「#### 共通」および「#### Phase {n}: 〇〇」の小見出しだけ。
     他フェーズの小見出しは未記入でよく、対象外として扱って。
     受け入れ基準も Phase {n} の分だけを突き合わせて。
   観点:
   - 外部境界（利用者・他プロセス・他システムが呼ぶもの）の入出力例が記載されているか
   - データ構造・永続化の変更と外部境界の整合
   - 内部設計が「決めたこと（代案と理由）」と「実装前に確かめること」になっているか。
     関数の signature・ファイルごとの変更点・処理手順の逐語があれば、削る側の指摘にする
     （実装の写しは実装でずれる。設計書が先に書いた列挙の漏れをレビューで拾うのは無駄）
   - 決めたことが projectDocs.policy の方針に反していないか
   - 受け入れ基準が全て設計に反映されているか（対応表で示す）
   結果は『要修正』テーブル形式で返して。")
```

**渡さない観点**（0.43.0 で外した）: 「内部設計の戻り値・型とインターフェースの整合」「命名規則・型安全性」。
どちらも **signature を設計書に書かせる方向に働く**観点で、実物の照合は実装後の `code-review` と型検査が担う。

**UI・挙動に触る設計では、UI・体験の設計観点も渡す。** 判定は
**「対象と操作フロー」の節に記入があるか**（`design-review` が自分で見る）。
記入があれば、上のプロンプトの観点に次を足す:

```
   - UI・体験の設計観点: 既存画面・既存操作とのパターン一貫性 /
     情報階層・視覚優先度 / アクセシビリティ（キーボード操作・コントラスト・代替テキスト） /
     想定される表示サイズで成立するか
     （対象は「対象と操作フロー」の節に書かれた画面・コンポーネント）
```

**なぜ tech にも渡すか。** L でも Stage 2 で画面の作りが決まるものがあり（部品の分け方・状態の持ち方）、
3-1 があるなら tech でも見る。
**M の UI・体験の観点は、ここではなく 2 つの経路で見る**（0.43.0 で M は tech を既定で回さなくなった）:
① `/harness-core:code-review` が **3-1 に記入があれば実装後に UI・体験の観点を見る**（画面が実物で見られる）
② 置き場や文言を実装前に見てほしいときは、ユーザーの指示で **`design-review feature` を1回足す**（規模は M のまま）。
**体験系アドバイザー（企画・ビジネス観点）は `feature` のままで、頼まれない限り M では起動しない** ——
**承認ゲートは増やさない**（規模ゲート原則）。

### 全体モード

Stage 分離されていない設計書向け。tech の観点 + 確認方法のチェック（検査4）を包括的に実施する。
**「動作確認計画」の章がある設計書（L）で章が未記入なら**、「1. 概要」と設計内容から草案を生成して設計書に追記する。
**章が無い設計書（M の最小形）には章を足さない**（受け入れ基準の各行の確認方法で代えている）。

## Step 6: 機能設計書への記録

レビュー結果ファイルを保存した後、機能設計書の「Stage 1 レビュー記録」/「Stage 2 レビュー記録」表に
日付 / レビューファイルパス / 判定 / 対応状況 を追記する。

**Stage 2 レビュー記録は行を足す**（上書きしない）。表に「対象」列があれば
**全体なら `全体`、フェーズ指定なら `Phase {n}`** を書く。列が無い古い TEMPLATE の設計書では、
**「対応」列の先頭にフェーズ名を書く**（列を勝手に増やさない）。
**M の最小形で `feature` を回したとき**は「Stage 1 レビュー記録」の節が無いので、
**「Stage 2 レビュー記録」の表に「対象」を `Stage 1` として書く**（節を新設しない）。
`—（M・レビューなし）` の行があれば、それを置き換える。
**承認されたら、メタ情報の「Stage 1」を `⚪ 不要` から `✅ 確定（M・feature を足した）` に変える**
（`⚪ 不要` のままだと、回したレビューが記録からしか分からない）。

**フェーズ指定で承認したら、メタ情報の「Stage 2」を `🔵 Phase {n} まで確定` に更新する**
（この値は TEMPLATE.md の凡例にある）。
**`✅ 確定` にしてよいのは、全フェーズの小見出しが記入・レビュー済みになったときだけ。**
**⏸️保留 / ❌却下 のフェーズは「対象外」として済み扱いに数えてよい**
（小見出しの本文に `⏸️ 対象外（理由）` と書かれていることを確かめる）。

## Step 7: ユーザーへの報告

- 総合判定
- トレーサビリティ検査の結果（漏れ件数）
- 要修正の件数、競合（要判断）の件数
- レビューファイルのパス
- 次のアクション
  - `feature`: ユーザー承認後 Stage 2（技術設計）へ
  - **`tech`: 承認後、実装フェーズへ。実装は `coding-specialist` サブエージェントへ委譲してよい**（下記）
  - **`tech Phase{n}`: 承認後、そのフェーズだけを実装する。** 次のフェーズに入るときは
    **「共通」の小見出しを見直してから**次のフェーズを書く
    （前のフェーズの実装で前提が変わっていることがある）。
    **残りのフェーズ名と、未記入のものを報告に並べる。**
    あわせて**メタ情報の「Stage 2」を更新したことを報告する** — セッションをまたぐと
    この報告は残らず、**設計書のメタ情報だけが引き継がれる**ため

### 「推奨で進める」が指示されているとき（`feature` / `tech` / `tech Phase{n}`）

**既定は上のとおりユーザーの承認を待つ。** ユーザーがこの設計書について「推奨で進める」を明示していれば
（`/harness-core:new-feature` の「推奨で進める」）、返事を待たずに承認欄を記して次へ進む:

| モード | 記す欄 |
|---|---|
| `feature` | メタ情報の「Stage 1」を `✅ 確定（AI 推奨で確定・ユーザー指示 yyyy-mm-dd「…」）` |
| `tech` | メタ情報の「Stage 2」を同じ形で |
| `tech Phase{n}` | 「Stage 2」を `🔵 Phase {n} まで確定`（全フェーズ済みで上の形）。4-5 の「対応」列に「AI 推奨で承認」と書く |

- **レビューは省かない**（このスキルを回したうえでの承認の代行である）。**ただし足さない** —— M では既定どおりこのスキルを呼ばない（`new-feature` の「推奨で進める」c）
- **❌ 差し戻しは推奨で承認しない**（直して回し直す）
- **要判断の競合と、`new-feature` の既定リスト（止めて聞く判断）に当たる指摘は、止めてユーザーに聞く**

### `tech` で承認したときに案内すること

Stage 2 が確定したら、**実装をフェーズ単位で `coding-specialist` へ委譲できる**旨を案内する。

**なぜ委譲するか**:

| 理由 | 内容 |
|------|------|
| **コンテキスト衛生** | 実装は**そのフェーズでしか読まない文書**（設計方針・ライブラリ規約）を大量に読む。メインの文脈に持ち込むと、以降の判断に無関係な内容が居座る |
| **思い込みの排除** | 設計をレビューした文脈のまま実装すると、**設計書ではなく自分の理解に合わせて**書いてしまう |
| **コスト** | 設計が確定した後の実装は、上位モデルを要さない部分が多い |

**委譲するときに必ず渡すもの**: 機能設計書のパスと対象フェーズ、
`projectDocs.policy` に登録された設計方針のパス、`harness.config.json` の `commands`。

> **モデルはエージェント定義が持つ**（`coding-specialist` は `model: sonnet`）。
> 起動側で上書きしないこと。**「コストが低い」という委譲の理由は、この指定で担保されている。**

**委譲した場合も、結果は必ずメインで差分確認してからコミットする**（`constitution.md`）。
副作用のあるコードは呼び出し先まで追跡して検証する。
