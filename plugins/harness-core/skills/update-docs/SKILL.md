# 設計書反映チェック＋更新（config 駆動）

直近の実装変更を分析し、設計書を更新する。
照合対象は `.claude/harness.config.json` の `designDocs` が決める。

## Step 0: 設定の読み込み

`.claude/harness.config.json` を読み、以下を把握する:

- `designDocs.dir` — 設計書のディレクトリ
- `designDocs.docs[]` — `file`（設計書名）/ `tracks`（何を追跡するか）/ `sources`（対応するソースの glob）
- `designDocs.ledger` — 同期記録の台帳パス

config が読めない場合は、`docs/設計書/` 配下を対象に推定で進め、その旨を報告に明記する。

## Step 1: 変更されたファイルの特定

```
git diff --name-only HEAD~1 HEAD    # 直近1コミット
git diff --name-only                # 未コミットの変更
```

`$depth` に 2 以上の数値が指定されている場合は `git diff --name-only HEAD~$depth HEAD` で対象を広げる。

> 引数はスキルの `arguments: [depth]` により `$depth` として渡される。
> シェルの位置パラメータ（`${1:-1}` 等）は置換されないため使わないこと。

## Step 2: 照合対象の決定

変更ファイルを `designDocs.docs[].sources` と突き合わせ、**該当する設計書だけ**を更新対象にする。

| 判定 | 動作 |
|------|------|
| `sources` の glob に一致する変更がある | その `file` を更新対象にする |
| どの `sources` にも一致しない | 設計書の更新は不要（Step 4 で「更新不要（理由）」として記録） |
| `docs/features/yyyymmdd_*.md` に基づく実装 | 該当する機能設計書のタスクステータスを更新（Step 3.5） |

## Step 2.5: 更新の実行者（委譲）

Step 3 の設計書更新は、**`documentation-manager` サブエージェントへ委譲してよい**。
対象が2文書以上、または1文書でも大きい（数百行規模）場合は**委譲を推奨する**。

**なぜ委譲するか**（3つとも実利があるので、面倒でも守る価値がある）:

| 理由 | 内容 |
|------|------|
| **コンテキスト衛生** | 設計書の更新は**大量の設計書を読む**。それをメインの文脈に持ち込むと、**その後の作業に無関係な内容が居座り続ける**。設計書はここでしか読まない |
| **思い込みの排除** | 実装したメイン自身が設計書を書くと、**実装の意図で書いてしまう**。読み手が読む「実装の現況」にならない |
| **コスト** | 突き合わせと転記は上位モデルを要さない作業が多い |

**委譲するときに必ず渡すもの**（渡さないと委譲した意味が消える）:

- 対象の設計書パス（`designDocs.docs[].file`）と、その `tracks`（何を追跡する文書か）
- 変更されたソースのパス一覧（Step 1 の結果）
- 改訂履歴の記入ルール（下記 Step 3 の「改訂履歴の記入ルール」）

> **モデルはエージェント定義が持つ**（`documentation-manager` は `model: sonnet`）。
> 起動側で上書きしないこと。**「コストが低い」という委譲の理由は、この指定で担保されている。**

**委譲した場合も、結果は必ずメインで差分確認してからコミットする**（`constitution.md`）。

## Step 3: 設計書の更新

対象の設計書を読み、変更内容を反映する。`tracks` の記述が「その文書が何を追跡するか」を示すので、
それに沿った粒度で更新する（実装の全詳細を書き写さない）。

**改訂履歴の記入ルール:**
- フォーマット: `| 版数 | 日付 | コミット | 内容 | 担当 |`
- コミット列は**トリガーとなった実装コミット**の短縮ハッシュ（7文字）
- **このスキルはコミット前に走るため、通常はハッシュが確定していない。その場合は `—` を書く**
  - `(未確定)` と書かない。**埋め戻す機会が来ないため永久に残る**（実測: 1プロジェクトで12ファイル34行）
  - **ハッシュは `git log -- <file>` で常に引ける。** 引ける情報を転記して腐らせない
  - 既にコミット済みの実装に**後から**追従する場合（`$depth` 指定など）は、そのハッシュを書く

**自動生成される設計書がある場合**（`tracks` に「自動生成」と書かれているもの）:
生成コマンドがプロジェクトの `tools/` 等にあればそれを実行し、差分を確認して取り込む。手書きで直さない。

## Step 3.5: 機能設計書のタスクステータス更新＋完了判定

変更が `docs/features/yyyymmdd_*.md` に基づく実装である場合:

1. **タスクステータス更新**: 実装済みタスクを ✅完了 に更新
2. **受け入れ基準の確認**: Stage 1「受け入れ基準チェックリスト」のうち、実装で満たされた項目にチェックを入れる
3. **全タスク完了判定**: 🔵未実施 / 🟡実装中 が残っていないか確認
   （⏸️保留 / ❌却下 は「未完了」とみなさない）
4. **全タスク完了時**: 変更範囲の設計書が Step 2〜3 で更新済みであることを確認する。
   **ここで全量照合はしない**（実装と設計書の全量照合は `/harness-core:pre-push-check` の職掌）
5. **移動判定**: 完了処理は `/harness-core:complete-feature` に委ねる（このスキルでは移動しない）

## Step 3.6: 未記載の作業をタスク一覧へ追記（converge）

照合の過程で「**実装されているが機能設計書のタスク一覧に無い作業**」を見つけた場合、
勝手に無視せず、タスク一覧に追記する:

| 発見 | 追記の仕方 |
|------|-----------|
| 実装済みだがタスクに無い | ✅完了 として追記し、備考に「実装から逆追記」と記す |
| 未実装だが設計上必要と判明 | 🔵未実施 として追記し、ユーザーに残作業として報告する |

**追記した内容は必ずユーザーに報告する**（黙って設計書を膨らませない）。

## Step 4: 同期トラッキングファイルに記録

`designDocs.ledger`（既定: `docs/設計書/.doc-sync.md`）の同期記録テーブルに追記:

```markdown
| {コミットハッシュ} | {日付} | {同期先の設計書と版数、または「更新不要（理由）」} | ✅ |
```

設計書の更新が不要だったコミットも `更新不要（理由）` として必ず記録する。

**例外**: 台帳自体の更新のみのコミットは記録不要（鶏と卵問題の回避）。

## Step 5: 結果報告

更新した設計書名と件数、converge で追記したタスクがあればその件数を簡潔に報告する。
更新不要の場合は「更新不要」と1行で報告する。
