# 機能設計書の完了処理

M/L フローの最後に実行する。設計書の全タスクが完了した後、
設計書と実装の整合性を確認してから `completed/` に移動する。

> **`disable-model-invocation` は付けない**（0.19.0 で外した）。一度「フロー末尾のゲートで
> 不可逆な移動を伴うから」という理由で `harness-update` と区別して残していたが、
> **破壊的な部分（`completed/` への移動）は Step 2 のゲート3種で既にスキル内から
> ゲートされている**——ユーザーが「この機能を完了処理して」と自然文で頼めば、
> それはスラッシュコマンドの直接入力と同じ「人の明示的な指示」である。
> `harness-update`（0.16.0）で外したときと同じ理由で、こちらも取り違えを解消した。

## Step 1: 対象の設計書を特定

引数でファイル名が指定されている場合はそれを使う。
未指定の場合は `docs/features/` 直下の設計書一覧（`TEMPLATE.md` を除く）を提示し、ユーザーに選択を求める。
**`planned/` は出さない**（着手前の置き場。完了処理の対象になりえない）。

## Step 2: 完了ゲート（3種類）

以下を**すべて**満たさない限り完了処理を進めない。

> **節は「見出し名」で探す。番号を当てにしない。**
> プロジェクトが独自の `docs/features/TEMPLATE.md` を持つ場合、番号が同梱版とずれていることがある
> （実測: あるプロジェクトでは `3-3` が「Stage 1 レビュー記録」だった）。
> **見出し名で見つからない節は「存在しない」と扱い、番号が近い別の節で代用しない。**
> ゲートが空振りしていることに気づけなくなる。

### ゲート1: タスク一覧

- 🔵未実施 / 🟡実装中 が残っていたら**中断**し、残タスクを一覧で報告する
- ✅完了 / ⏸️保留 / ❌却下 のみなら通過（⏸️・❌ は備考に理由が書かれているかも確認する）

### ゲート2: 受け入れ基準チェックリスト（Stage 1 の該当節）

- **未チェック項目が残っていたら中断**し、未チェックの項目を列挙する
- 各項目について、次のいずれかが必要:
  - 動作確認で満たしたことを確認してチェックを入れる
  - 満たさないと決めた場合は、理由を書いて「対象外」に変更する（黙って消さない）
- Stage 1 が `⚪ 不要`（M 規模）の場合はこのゲートをスキップする

### ゲート3: 設計方針への書き戻し（Stage 2 の該当節）

設計書の**見出し「設計方針への書き戻し」**の表に **⚪ 未反映** が残っていたら**中断**する。

- 未反映の項目を、`.claude/harness.config.json` の `projectDocs.policy` 配下の
  指定ファイルへ反映してから ✅ に変える（該当ファイルが無ければ新規作成し、改訂履歴を付ける）
- 反映しないと決めた場合は、理由を書いて行を「対象外」に変更する（黙って消さない）
- 表が「なし」または存在しない場合、および `projectDocs.policy` が未登録の場合はスキップする

> **なぜゲートにするか**: 「今後も従う設計判断」が機能設計書の中だけに残ると、
> 次の機能を作るときに誰も見つけられない。完了時に設計方針へ移すことで初めて効く。

## Step 3: 整合性チェック

`/harness-core:sync-check` を、**この設計書の変更範囲に関係する対象だけに絞って**実行する。

対象の決め方: 設計書の**見出し「作成・変更ファイル」**の一覧を、
`.claude/harness.config.json` の `designDocs.docs[].sources` と突き合わせ、
一致した設計書のみを照合対象にする（全量照合はしない）。

- 乖離あり → 一覧で報告。自動修正可能なものは修正し、改訂履歴を更新する。複雑な場合はユーザーに確認
- 乖離なし → 「✅ 設計書と実装は同期済み」と報告

## Step 4: 完了処理

1. メタ情報のステータスを更新:
   - ✅ と ❌ のみ → `🟢 完了`
   - ⏸️保留 が1つ以上 → `⏸️ 一部保留`
   - **「Stage 2」が `🔵 Phase {n} まで確定` のままなら、ここで確定させる**
     （Stage 2 をフェーズごとに書いた設計書。→ 下の注記）
2. 移動:
   - `🟢 完了` → `docs/features/completed/` へ移動
   - `⏸️ 一部保留` → `docs/features/pending/` へ移動（`pending/` が無ければ作成する）
> **Stage 2 をフェーズごとに書いた設計書にも、ゲートを足していない。**
> 未記入のフェーズが残っていれば**そのフェーズのタスクが 🔵 のままなのでゲート1 が止める**。
> 書き戻しの表（ゲート3）も作成・変更ファイルの一覧も**フェーズで分けず1つ**なので、そのまま効く。
>
> **「Stage 2」の値だけは機械が直せない。** ⏸️保留 / ❌却下 のフェーズがあると
> 「全フェーズが記入・レビュー済み」には永久にならないため、**ここで次のように書き換える**:
>
> - 保留・却下したフェーズが無い → `✅ 確定`
> - ある → `✅ 確定（Phase {n} は対象外）`。**そのフェーズの小見出しの本文に
>   `⏸️ 対象外（理由）` が書かれていることを確かめる**（空のまま残っていたら書かせる）

3. **台帳（`docs/backlog.md`）の行を消す**（**見出し「計画」**（既存プロジェクトでは「マイルストーン」）の表に、この設計書を指す行があれば）:
   - **照合はファイル名（`yyyymmdd_名前.md`）で行う。** 台帳の欄は `planned/` のパスのままかもしれず、
     この時点で現物は `completed/` へ移っているので、**パスの一致では必ず空振りする**
   - **行ごと消す。** 「✅完了」に書き換えない（**進捗を積み上げると必ず腐る**。履歴は git が持つ）
   - **`⏸️ 一部保留` のときは、後続のマイルストーンがその分を前提にしているかで分ける**:
     - **前提にしている → 行を消さない。** 設計書の欄を `pending/` のパスへ書き換えて**順序に残す**
       （消すと、後続が前提にしていた分が起動時の視界から消える。「残作業」の表はフックが読まない）
     - 前提にしていない → **行を消し、台帳の「残作業」の表へ1行書く**（消したまま忘れるのを防ぐ）
   - 台帳が無い・その見出しが無い・指す行が無ければ**何もしない**（fail-open）

   > **なぜ完了処理で消すのか。** 台帳の行を人が消す運用だと消し忘れが残る。
   > **行の寿命を設計書の寿命に重ねる**ことで、乖離が起きない。

4. 結果報告:

```
## 完了処理結果

### 設計書: {ファイル名}
### 受け入れ基準: ✅ 全項目クリア / ⚠️ 対象外 N件（理由つき）
### 整合性チェック: ✅ 同期済み / ⚠️ N件修正
### ステータス: 🟢 完了 → completed/ へ移動 / ⏸️ 一部保留 → pending/ へ移動
### 台帳: 行を削除（マイルストーン #N） / 該当なし
```

5. **利用者が読む日本語を書いた機能なら、校正を案内する**:

> 💡 `/harness-core:proofread-ja` で日本語を校正できます（対象: この機能で書いた文書・UI 文言）

**自動で走らせない。** 機能の完了は**利用者向けの文言が確定する時点**であり、
ここを逃すと校正されないまま出る。ただし判断はユーザーに返す。

**当てはまらないなら添えない**（内部リファクタリングなど）。
