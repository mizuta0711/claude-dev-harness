# 作業完了報告

作業が完了したときに呼び出すスキル。決められたフォーマットで報告を出力する。

## 手順

1. 直近の作業内容を把握する（タスク一覧、直近のコミット、変更ファイル）。
   **設計書があれば、メタ情報と未解決事項の表から `AI 推奨` の付いた判断を拾う**
   （メタ情報の「変更規模」「Stage 1」「Stage 2」の `AI 推奨で確定`・未解決事項の「回答」列の先頭の `AI 推奨:`）。「推奨で決めた判断」行に使う。
   **対象の設計書は、直近のコミットが触った `docs/features/**` の設計書**（`completed/`・`pending/` へ移ったものを含む。
   `complete-feature` の後に呼ばれると、設計書はもう直下に無い）
2. `.claude/harness.config.json` の `verification` を読み、「動作確認」行の書き方を決める:

| config | 「動作確認」行の書き方 |
|--------|---------------------|
| `skill` 非 null / `manualGate: false` | `✅ /{skill} を実施（エビデンス: パス）` |
| `skill` 非 null / `manualGate: true` | **両方必要**。スキルを実施したうえで、人手確認が済むまで `⚠️ 要手動確認（/{skill} は実施済み）` のままにする。両方揃って初めて ✅ |
| `skill` が null / `manualGate: true` | 未実施なら `⚠️ 要手動確認` として明示する（勝手に ✅ にしない） |
| 両方が無効（skill が null かつ manualGate が false） | `⬜ 不要（この環境に自動確認手段なし）` |
| config 不在 | `⬜ 不明（harness.config.json 未配置）` |

3. 以下のフォーマットで報告を出力する

## 報告フォーマット（必須）

```
### {作業名} 完了報告

| ステップ | 状況 |
|---------|------|
| 設計 | ✅ 具体的な内容 / ⬜ 不要（理由） |
| 設計レビュー | ✅ 具体的な内容 / ⬜ 不要（理由） |
| 推奨で決めた判断 | ✅ n 件（要点を列挙） / ⬜ なし（すべてユーザー承認） |
| 実装 | ✅ 変更したファイル・内容の要約 |
| コードレビュー | ✅ 具体的な内容 / ⬜ 不要（理由） |
| 動作確認 | ✅ 手段とエビデンス / ⚠️ 要手動確認 / ⬜ 不要（理由） |
| 設計書更新 | ✅ 具体的な内容 / ⬜ 不要（理由） |
| ビルド確認 | ✅ 実行したチェックと結果 / ⬜ 不要（理由） |
| コミット | ✅ ハッシュとコミット概要 |
| プッシュ | ✅ / ⬜ ユーザー指示待ち |
```

## ルール

- 各ステップの「具体的な内容」は省略せず、何をしたか・どのファイルを変更したかがわかるように書く
- バグ修正など軽微な作業でも同じフォーマットで報告する
- 「⬜ 不要」の場合は理由を必ず記載する（例: S規模、設計書のみ、等）
- **「推奨で決めた判断」は件数だけで済ませず、要点（何をどちらに決めたか）を並べる。**
  ユーザーが「推奨で進めて」と委ねた判断を、**最後にまとめて見て覆せる**ようにするための行である。
  委ねていない作業（既定どおり止めて聞いた）・設計書を作らない S は `⬜ なし（すべてユーザー承認）`
- コミットハッシュは短縮形（7文字）で記載
- **`manualGate` が true の環境で、人手の確認をしていないのに動作確認を ✅ にしない**
- プッシュはプロジェクトのルールに従い、フェーズ完了時またはユーザー指示時のみ実施する。勝手にプッシュしない
