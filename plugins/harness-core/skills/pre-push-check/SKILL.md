# プッシュ前 設計書同期チェック（config 駆動）

> **このスキルは `context: fork` ＋ `model: haiku` で動く**（サブエージェントとして走る）。理由は、
> **メインが上位モデルでも、この検査をその単価で回さないため**。スキルの `model:` 単独は
> **スラッシュで直接呼んだときしか効かず、Skill ツール経由（モデルが呼ぶ通常の経路）では切り替わらない**
> （2026-10-18・`claude -p` のトランスクリプトで実測。`fork` を併用すると両経路で切り替わる）。
> fork では **会話の文脈が無く、ユーザーに質問もできない**。**最後のメッセージだけが呼び出し元へ返る**ので、
> 報告フォーマットは省略せずにそのまま出すこと。
> **Step 3.5 の `sync-check` は、この中からさらに fork される**（`model: sonnet`。入れ子でも指定どおりのモデルになることを実測済み）。

git push の前に必ず実行する。`.claude/harness.config.json` の `designDocs.ledger`
（既定: `docs/設計書/.doc-sync.md`）に全コミットハッシュが記録されているかを確認する。

## Step 0: 設定の読み込み

| 使う設定 | 用途 |
|---------|------|
| `designDocs.ledger` | 台帳のパス |
| `paths.source` | 「ソース変更あり」の判定に使う glob 群 |
| `designDocs.docs[]` | Step 3.5 の全量照合の対象一覧 |

> **このスキルは2つの別々の検査を行う。混同しないこと。**
>
> | Step | 見るもの | 見ないもの |
> |------|---------|-----------|
> | Step 1〜3（**台帳**） | 未プッシュの全コミットが台帳に**記録されているか** | 設計書の**中身** |
> | **Step 3.5（全量照合）** | 設計書の記述が**実装と合っているか** | — |
>
> **台帳が合っていても中身は腐る。** 台帳に「更新不要（理由）」と書いた後にコードだけが動いた場合や、
> `docTriggers` のパターンから外れた層を変更した場合、**台帳検査は素通りする**。
> それを拾うのが Step 3.5 である。

> ⚠️ **ここで言う「台帳」は設計書同期台帳（`docs/設計書/.doc-sync.md`）である。**
> **残作業台帳（`docs/backlog.md`）は見ていない。** あちらは別の仕組みが見る —
> push の直前に `pre-push-backlog-check` フックが整合を確かめ、
> 食い違っていれば **deny して `/harness-core:backlog-sync` を案内する**（H63）。
> **このスキルを通したからといって、残作業台帳が合っている保証は無い。**

config が読めない場合: 台帳が `docs/設計書/.doc-sync.md` にあれば推定で続行し、
その旨を報告に明記する。台帳も無ければ「チェック不能」として報告し、push の可否はユーザーに委ねる。

## Step 1: 未プッシュコミットの列挙

引数: `$ARGUMENTS`（空なら下の `@{upstream}..HEAD`。コミットの範囲が渡されたら、それを使う）

```
git log --format=%h @{upstream}..HEAD
```

出力が空なら「未プッシュのコミットはありません」と報告して終了する。
（upstream が未設定の場合は範囲を決められない。**fork では質問できないので、その旨を報告して終了する**。
呼び出し元が範囲（`git log --format=%h -20` 等）を決めて、引数で渡して再実行する）

## Step 2: コミットごとの判定

各コミットについて:

1. 変更ファイルを取得: `git diff-tree --no-commit-id --name-only -r {hash}`
2. **SKIP 判定**: 変更ファイルが `paths.source` のどの glob にも一致しない場合は
   「ソースコード変更なし」として SKIP（設計書・ドキュメントのみのコミット等）
3. 一致するものがある場合、台帳にそのハッシュが記録されているか検索する
   - 記録あり → OK
   - 記録なし → **MISSING**

> パスの比較はリポジトリルートからの相対パス・フォワードスラッシュで行う（Windows でも `/` に揃える）。

## Step 2.5: 試作中かを見る（harness-core 0.39.0 以降）

**`docs/features/prototype/` に設計書が1本以上あれば「試作中」である。**

試作中は、**Step 3 の MISSING と Step 3.5 の乖離を `deny` ではなく「警告」として扱う**
——「**止めないが、黙らない**」。報告には**警告に落としたことを必ず書く**。

| | 通常 | 試作中 |
|---|---|---|
| Step 3 の MISSING | **全件記録されるまで push しない** | **警告。push してよい** |
| Step 3.5 の乖離 | **直してから push** | **警告。push してよい** |

**なぜ止めないのか。** 試作のフロー（`/harness-core:new-prototype`）は
**`update-docs` を最後に1回だけ回し、フェーズごとにコミットしてよい**ことにしている。
**台帳（`designDocs.ledger`）は1回の `update-docs` で1コミットぶんしか記録しない**ので、
**中間コミットが必ず MISSING になる** —— 止めると試作が push できない。

**なぜ飛ばさずに警告は出すのか。** **本実装と試作は並行する。**
検査ごと止めてしまうと、**同じ push に乗っている本実装側の乖離も見えなくなる**。
だから**判定は行い、結果の重さだけを下げる**。

> **台帳の穴は昇格のときに埋める。** 試作を本実装へ上げる手順に
> 「**台帳の穴を埋める**」が入っている（`new-prototype` の出口）。
> **試作のまま終える・破棄する場合は埋めない**（照合対象ではないので埋める意味が無い）。

## Step 3: 判定と対応

**試作中は Step 2.5 のとおり警告に落とす**（以下は通常時）。

- **MISSING なし** → Step 3.5 へ進む
- **MISSING あり** → 該当コミットの内容を `git show --stat {hash}` で確認し、
  **ハッシュと変更の要約を報告に並べて ❌ 未同期あり で終える。ここでは直さない**
  （fork では質問できず、`update-docs` を呼ぶと設計書の更新がこのスキルのモデルの仕事になる）。
  **直すのは呼び出し元**: `/harness-core:update-docs` で設計書と台帳を更新し、このスキルを**もう一度**走らせて全て記録済みになったことを確認する

**全コミットが記録されるまでプッシュしないこと**（**試作中を除く**。Step 2.5）。

## Step 3.5: 全量照合（ソース変更があるときだけ）

**実行条件**: Step 2 で **SKIP 以外のコミットが1件以上あった場合のみ**。
**試作中でも実行する**（結果の扱いだけが変わる。Step 2.5）。
全コミットが SKIP（ソース変更なし）なら**この Step は飛ばす**。

`/harness-core:sync-check` を**対象を絞らずに**実行する。

> ⚠️ **ここで範囲を絞ってはいけない。** 変更範囲に絞った照合は `update-docs` が
> 実装変更のたびに行っており、**このスキルの役目はそこで拾えない乖離を見つけること**である。
> 絞った時点で二重になり、しかも**どちらも本来の仕事をしない**。
>
> **実測（2026-08-16・WPF の実プロジェクト）**: 設計書が **2ヶ月前に削除されたクラスを「✅ 実装済」と
> 記載し続けていた**。`docTriggers` は該当層をパターンに含んでおらず変更駆動では拾えず、
> 台帳（Step 1〜3）はハッシュしか見ないので素通りした。**全量照合だけが拾える乖離だった。**

- 乖離が見つかったら、**内訳を報告に並べて ❌ 乖離あり で終える。ここでは直さない**（Step 3 と同じ理由）。
  呼び出し元が `/harness-core:update-docs` で直してから、このスキルをもう一度走らせて push する
- **照合対象は `designDocs.docs[]` に登録された文書だけ**。登録されていない文書は照合されない
  （登録漏れ自体が乖離の原因になるので、報告に含める）

### 重くなりすぎたときは

このスキルは **push のたびに走る**。重すぎると外される。

- push は「フェーズ完了時・指示時にまとめる」運用が前提（`constitution.md` §4）
- それでも重い場合は、**照合対象を減らすのではなく `designDocs.docs[]` の粒度を見直す**
  （1文書が大きすぎる＝実態の一覧を1本に詰め込みすぎている可能性）

## Step 3.7: 全体査読の目安（催促だけ・止めない）

`node "${CLAUDE_PLUGIN_ROOT}/hooks/scripts/whole-review-nudge.js"` を実行し、出力があれば報告に載せる
（`.claude/harness.config.json` の `wholeReview.nudge` の閾値に達したときだけ出る。無ければ何も出ない）。
**push は止めない。** 回すかはユーザーが決める（`/harness-core:whole-review`。見送るなら `--snooze`）。
push 前はどのみち立ち止まる場所なので、ここで知らせる。

## Step 4: 結果報告

```
## プッシュ前チェック結果

### 試作中か（Step 2.5）
試作中: いいえ / **はい（docs/features/prototype/ に N本）→ 以下は警告扱い**

### 台帳チェック
チェック対象: N件のコミット（SKIP: M件 = ソース変更なし）
未同期: 0件（または K件 → ハッシュと要約を並べる。呼び出し元が直す / **試作中のため警告**）

### 全量照合（Step 3.5）
実行: ✅ 実施 / ⏭️ スキップ（全コミットがソース変更なし）
対象: designDocs.docs[] の L件
乖離: 0件（または J件 → 内訳を並べる。呼び出し元が直す / **試作中のため警告**）

### 全体査読の目安（Step 3.7）
⬜ 未到達（または閾値の設定なし） / スクリプトの出力の `[全体査読]` 以降をそのまま（push は止めない）

### 判定: ✅ プッシュ可能 / ⚠️ プッシュ可能（試作中のため警告）/ ❌ 未同期あり / ❌ 乖離あり
```

**試作中に警告へ落としたときは、「⚠️ プッシュ可能（試作中のため警告）」を使い、
警告の中身を必ず並べる。** 黙って通すとこの検査が無いのと同じになる。
**本実装側の乖離も同じ報告に出る**ので、**試作のものか本実装のものかを書き分ける。**
