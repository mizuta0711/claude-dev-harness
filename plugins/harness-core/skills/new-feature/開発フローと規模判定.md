# 開発フローと規模判定（harness-core 共通仕様）

変更規模判定（S/M/L）と S/M/L 開発フローの詳細仕様。**環境非依存**。
`/harness-core:new-feature` スキルから参照される。

環境ごとに変わるもの（実行コマンド・動作確認の手段・設計書の軸）は
`.claude/harness.config.json` が持つ。この文書はコマンド名を直接書かない。

## 0. 軸は2つある（規模と、本実装 / 試作）

**この文書が決めるのは規模の軸だけである。**

| 軸 | 決めるもの | どこが持つか |
|---|---|---|
| **規模 S / M / L** | **設計書の厚み** | この文書 |
| **本実装 / 試作** | **フロー**（どのレビューを何回通すか） | `/harness-core:new-prototype` |

**2つを混ぜないこと。** 「試作だから設計書を省く」ではない ——
**試作でも設計書は L 相当に書き、減らすのはレビューの回数だけ**である。

**試作かどうかは利用者が決める。** 規模判定でこちらから振り分けてはいけない
（理由は `new-prototype` の冒頭にある）。**明示が無ければ本実装として進める。**

## 1. 規模判定の詳細

### 1-1. 基準表（5軸）

| 観点 | S | M | L |
|------|---|---|---|
| 変更ファイル数 | 1〜2 | 3〜10 | 10超 または広範囲 |
| 新規インターフェース（API・公開メソッド・コマンド） | なし | 既存パターンに沿った 1〜2 | **新パターン、または 3 本以上** |
| データ構造・永続化の変更 | なし | 後方互換のある追加のみ | **破壊的変更、または新しい永続化先・新しいテーブル／エンティティ** |
| **UX変更（画面・操作フローの変更）** | **なし** —— 挙動と操作フローが変わらない（文言・色・余白・整列） | **既存の単一画面（コンポーネント）内の改修** —— その画面の中で挙動が変わる | **複数の画面（コンポーネント）に影響する** —— 画面遷移・動線が変わる、新しい画面を足す |
| 設計書更新 | 不要 | 必要 | 必要（複数種類） |

#### 判定ルール

1. **最も該当する項目が多い規模を採用**
2. **1つでも L 相当の項目があれば L に引き上げる。** **この規則が UX 軸の判定より優先する** ——
   単一画面内の改修でも、**データ構造・永続化が L 相当なら L になる**
3. **UX 軸は影響範囲で判定する**（上の表の3行目）。
   - **S / M の境界は「挙動が変わるか」。** 文言・色・余白・整列のように
     **挙動と操作フローが変わらないものは S に留まる**
   - **M / L の境界は「影響が1つの画面（コンポーネント）に収まるか」**
   - ⚠️ **「UX 変更を含めば自動的に L」ではない**（0.41.0 で変えた）。
     旧規則は表の M 列を到達不能にしており、**「UI 微調整」が S とも L とも読めた**
   - ⚠️ **判定に迷ったら、影響範囲の広い側（L）で提示する**（§1-3）
4. **壊れたときの影響が大きい変更は、ファイル数が S でも引き上げる。**
   認証・認可、課金、削除、マイグレーション、依存ライブラリの追加に触るなら、
   **1ファイルでも S に置かない**（S は `/code-review` を省くので、
   **セキュリティ観点を通す経路が1つも無くなる**）。
   **データ構造・永続化を壊す変更は上の表の3行目どおり L** であり、ここで M に留めない
5. **L の上に天井がある。** 上の表は L の上限を書いていないので、**10ファイルでも100ファイルでも L になる。**
   **受け入れ基準が独立に「動くもの」として確認できる塊に2つ以上に分かれるなら、1本の設計書に収めない**
   → `/harness-core:plan-milestones`（§1-6）

### 1-2. 判定プロセス

**AI が推測 → ユーザーが承認** の2ステップ。

```
1. ユーザーが作業を依頼
2. メイン Claude が指示内容と影響範囲から S/M/L を推測して提示（根拠つき）
3. ユーザーが承認 or 修正
4. 承認された規模でフローに入る
```

### 1-3. AI バイアス補正ルール

AI が「楽な方（S 寄り）」に判定する傾向を抑制するため、以下を徹底する:

- **判定に迷ったら L 寄りで提示する**
- ファイル数やデータ構造変更の有無が不明確なら **M 以上で提示する**
- **過小見積もりより過大見積もりの方が安全**（ユーザーが S に下げるのは容易、L を後から発覚するのは辛い）
- **「分ける／分けない」の判定（§1-6）でも、同じバイアスが1本に全部入れる方向へ働く。**
  §1-6 の**一次ゲートの判定で迷ったときだけ、分ける方向で提示する**
  （分けすぎは台帳の行を畳めば戻せるが、1枚が膨らんでから分けるのは後始末になる）
- ⚠️ **ただしこのバイアスを規模そのものに重ねない。** 上の3つと合わせると
  **重くする側へ2段倒れる**。**分けた結果の1本が M に届かないなら分けない**
  （下限は `/harness-core:plan-milestones` が持つ。§1-6 には書いていない）

### 1-4. スコープ拡大時の再判定ルール

| 気づくタイミング | 対応 |
|----------------|------|
| 着手前 | 即停止して再判定 |
| **Stage 2 を書いていて「1本に収まらない」と気づいた** | **現在のマイルストーンは書き切り、残りを `plan-milestones` で分ける。** 書いた Stage 2 は捨てない |
| フェーズ実行中 | **現フェーズを完了**させ、フェーズ完了時の報告で再判定を提案 |
| 破壊的変更・データ構造変更が必要と判明 | **即停止**（戻しが困難なため） |

**原則**:
- 作業途中で止めると中途半端な状態になるため、切りの良いところまで進める
- AI 単独でフロー切り替えをしない（必ずユーザーに報告）
- 引き上げ判断後は、必要な設計書追記・レビュー等を**遡って実施**する

### 1-5. 補助軸（変更の性質）

| 区分 | 意識すべき点 |
|------|-------------|
| 新規追加 | 既存パターンを先に確認してから設計する。再利用可能な既存資産を特定 |
| 改修 | 「何を変えるか・何を変えないか」の境界を明示する。既存挙動を壊さない保証をレビュー観点に含める |
| バグ修正 | 根本原因を確定してから修正する（§3 参照）。症状に飛びつかない |

性質は規模と独立した概念。「M 規模の改修」「L 規模のバグ修正」等は自然な組み合わせ。

### 1-6. L を超えるとき — マイルストーンに分ける

**要件と機能設計書の間に「どこまでを最初に作るか」を決める層が無いと、要件がそのまま1枚の設計書になる。**

> **実測**（ある新規プロジェクト・2026-10-07〜08）: 機能設計書1本が **2,226行／157,345文字**、
> タスク39本・フェーズ7区分・変更ファイル75件・受け入れ基準46項目。**上流の要件文書は188行**で、その約12倍。

**判定（一次ゲート・質的）**: **受け入れ基準が、独立に「動くもの」として確認できる塊に2つ以上に分かれるか。**
行数やファイル数は書き終わるまで分からないが、**これは依頼の時点で判定できる**。

**適用条件**: **L 規模かつ一次ゲートを満たすときだけ。M 以下では分けない**（§2-5 の規模ゲート原則）。

| | 置き場 |
|---|---|
| **順序と「どの設計書か」** | **台帳**（`docs/backlog.md` の「計画」の表。**単発の設計書も同じ表に載る**）。**分けたものは全順序（1本道）にする** |
| 各マイルストーンの設計 | **1本ずつの機能設計書**（着手前は `docs/features/planned/`） |
| 今後も従う設計判断 | **設計方針層へ昇格**（`projectDocs.policy`）。**既存のゲート3（設計方針への書き戻し）がその導線** |

**手順は `/harness-core:plan-milestones`。**

#### 「設計書を分ける」と「Stage 2 をフェーズごとに書く」の選び分け

**この2つは別の機構で、どちらも同じ実測1件から出ている**（§2-3 がもう一方）。**ほぼ常に両方成立するので、基準を決めておく。**

| | 選ぶ条件 |
|---|---|
| **設計書を分ける**（この節） | **それぞれが独立に「動くもの」として出せる** — 1本目を実装した時点で、利用者に見せられるものが成立する |
| **1本のままフェーズに分ける**（§2-3） | **動くものは最後に1つしか出来上がらない** — 途中のフェーズは部品で、単体では見せられない |

**迷ったら §2-3（1本のまま）を選ぶ。** 設計書は1本のままで、**台帳も `planned/` も承認も増えない。**
1本のままでも、**Stage 2 をフェーズごとに書くかは別の判断**である（§2-3 の条件。既定はまとめて書く）。

**「索引（親設計書）」という文書種は作らない。** 設計書を分けるなら**各設計書を自己完結させ**、
**受け入れ基準は子（各設計書）が正**にする（索引側に写しを置かない）。

**「Stage 1 を先に全部書く」のは見通しを立てるためで、確定させるためではない。**
**後続のマイルストーンの Stage 1 は、先行の実装を進める中で変わる。**
だから**未着手のものは `✅ 確定` にせず**（`🔵 記入中` のまま）、
**`design-review feature` も着手するときに1本ずつ回す**（横断のレビューは置かない）。

## 2. S/M/L フローの詳細

以下の `/xxx` は harness-core のスキル（実際の呼び出しは `/harness-core:xxx`）。
「動作確認」は `harness.config.json` の `verification` が定める手段で行う:

- `verification.skill` が非 null → そのスキルを実行（例: browser-test / unity-verify / capture-screenshots）
- `verification.manualGate` が true → 人間による体感確認を必須ステップとして残す
- 両方が無効 → 動作確認ステップは「⬜ 不要」として報告する

### 2-1. S 規模（軽微な変更）

対象: **挙動と操作フローが変わらない**見た目の調整（文言・色・余白・整列）、
1ファイル程度の修正、軽微なバグ修正

**S に置かないもの**（判定ルール4）: 認証・認可・課金・削除・マイグレーション・
依存ライブラリの追加に触る変更。**ファイル数が1でも M 以上**にする。
**データ構造・永続化を壊すものは L。**

```
実装 → /build-check → コミット → /done
```

省略する工程: 設計書作成、設計レビュー、コードレビュー、`/update-docs`

**S だけは「完成の定義」を持たない**（設計書を作らないので受け入れ基準が無い）。
**挙動が変わるなら S ではない** —— 判定の時点でここを見分けること。

### 2-2. M 規模（機能追加・インターフェース変更・複数ファイル変更）

**前提**: UX の影響が**既存の単一画面（コンポーネント）内に収まる**こと。
**複数画面に影響するなら L に引き上げる**（§1-1 の3行目）。

```
設計（受け入れ基準 ＋ Stage 2）→ ユーザー承認（Stage 2 を読む）
  → 実装 → /code-review → 動作確認 → /build-check
  → /update-docs → コミット → /complete-feature → /done → プッシュ
```

- **M は設計レビューを既定で回さない**（0.43.0）。承認ゲートは Stage 2 の1つで変わらない。
  **3-2 の各行に確認方法があるか**は `/code-review` が見る（`complete-feature` の完了ゲートを空振りさせないため）。
  頼まれれば `/design-review tech` は回る（既定で回さないだけ）
  - **なぜ外したか**: 実プロジェクトの M 3件で tech レビューが出した指摘（高3・中14）は、
    fixture の前提・例外が 500 になる経路・開閉の初期値・`export` の置き場で、
    **どれも実装時の型検査・確認スクリプト・`code-review` で拾える種類**だった。
    設計の段で人の目が要る種類（置き場・文言・脅威モデル）は、下の feature を足す経路で残す
- **画面に触る M は、ユーザーの指示で `/design-review feature` を1回足せる**（規模は M のまま。tech は足さない）。
  置き場や文言を実装前に見てほしいときに使う。**既定では足さない**。
  結果は 4-5 に「対象: Stage 1」で記録する（3-4 は M の最小形に無い）
- 機能設計書は **1段階設計**（Stage 1 の 3-1 と Stage 1 レビューは `⚪ 不要`）
- **M の設計書は最小形**: メタ情報 / 1 概要 / 3-2 受け入れ基準（**各行に確認方法**）/ 3-3 未解決事項 / 4-0 / 4-1（空。実装後に記入）/ 4-2〜4-4（**判断があるものだけ**）/ 4-5 / 改訂履歴。
  **タスク一覧・Stage 1 レビュー記録・動作確認計画・関連ドキュメント・注意事項の節は作らない**（TEMPLATE.md の `規模: L のみ` の印）
- **受け入れ基準チェックリスト（3-2）は M でも必須である。**
  省くと `complete-feature` の完了ゲートと `code-review` の確認方法の検査（L は `design-review` の検査2・4）が
  **どちらも空振りし、M に「できたと言える条件」が無くなる**
  （`constitution.md` §3 は規模を限定していない）
- **UI・挙動に触る M では、3-1（対象と操作フロー）も書く。**
  S / M の境界が「挙動が変わるか」なので、**挙動の記述はここに要る**
- **外部境界**（利用者・他プロセス・他システムが呼ぶもの）の入出力例は必須。内部の関数・型は書かない（§4-2）
- **レビュー前にコミットしない**（この規律は `.claude/harness/core.md` の運用ルールにもある。
  **あの文書は規模判定のときにしか読まれないので、コミットの直前に読まれる側にも置いてある**）
  - **外れるのは試作のときだけ**（`/harness-core:new-prototype`）。**規模では外れない**

### 2-3. L 規模（新機能・大規模変更・複数画面に影響する UX 変更・データ構造変更）

```
設計 Stage 1（機能・画面設計 + 受け入れ基準チェックリスト + 未解決事項の解消）
  → /design-review feature（code-reviewer + 体験系アドバイザー）
  → ユーザー承認
設計 Stage 2（技術設計）
  → /design-review tech（code-reviewer）→ 承認
  → 実装 → /code-review → 動作確認 → /build-check
  → /update-docs → コミット → /complete-feature → /done → プッシュ
```

L 規模ではタスク一覧に依存関係と並列可否マーカー `[P]` を付け、
タスク分解自体を第一級の成果物として扱う（TEMPLATE.md「2. タスク一覧」参照）。

- **レビュー前にコミットしない**（M と同じ。フェーズごとに実装する場合も、
  各フェーズの `/code-review` を通してからコミットする）
  - **試作では外れる** —— `new-prototype` は `code-review` を**最後に1回**にするので、
    **フェーズごとにコミットしてよい**。**L 規模だから外れるのではない**（軸が違う）

#### Stage 2 はフェーズごとに書いてよい（依存があるときだけ）

上のフローは **Stage 2 を全フェーズ分まとめて書き、`/design-review tech` を1回で通す形**で、**これが既定**である。
**フェーズは「実装 → `/code-review` → コミット」の単位として使う。** Stage 2 を分ける理由にはしない。

**後のフェーズの設計が前のフェーズの実装結果に依存するときだけ、着手するフェーズの分だけ書いて進めてよい。**
**コストは `/design-review tech` がフェーズ数ぶん増えること**（3フェーズなら tech が3回）。
依存が無いのに分けると、**同じ設計を見るレビューの回数だけが増える**。

```
設計 Stage 1（全体。受け入れ基準も #### の小見出しでフェーズ別に分ける）
  → /design-review feature → ユーザー承認
  ↓
  ┌─ Phase 1 の分を書く → /design-review tech Phase1 → 承認 → Phase 1 を実装 → /code-review → コミット
  ├─ Phase 2 の分を書く → /design-review tech Phase2 → 承認 → Phase 2 を実装 → /code-review → コミット
  └─ …（着手するフェーズの分だけ書く）
  ↓
動作確認 → /build-check → /update-docs → /done → プッシュ
```

**節の構成は変えない。** `4-2` 〜 `4-4` の中を **`#### Phase {n}: 〇〇`** の小見出しで分けるだけで、
全フェーズに効くものは **`#### 共通`**（フェーズ名を付けない）に置く。
**「第2の形」を作るのではなく、同じ節の中の粒度の話である。**

**なぜ分けられるようにするか。** Stage 2 は**フェーズ数に比例して線形に膨らむ**
（インターフェース仕様は入出力例が必須なので、API の本数ぶん積まれる）。
全フェーズ分を先に書くと、**Phase 1 の実装で分かったことを Phase 2 以降の設計へ戻す経路が、
巨大な1ファイルの改訂しかなくなる**。

> **実測**: ある新規プロジェクトの L 規模1本で、**設計書 2,226行のうち Stage 2 が 1,698行（76%）**だった
> （Stage 1 は 174行）。フェーズは7区分・タスク39本・変更ファイル75件。実装は1行も始まっていない時点で改訂14版。

**実装はすでにフェーズ単位を前提にしている。** TEMPLATE.md の Stage 2 の末尾は
「実装は `coding-specialist` サブエージェントへ委譲できる（**フェーズ単位**）」と書いており、
これは**設計の記入とレビューだけが一括だった非対称を揃えるもの**である。

| | まとめて書く（既定） | フェーズごとに書く |
|---|---|---|
| 採る条件 | いつでも | **L 規模で、後のフェーズの設計が前のフェーズの実装結果に依存するとき** |
| コスト | tech 1回 | **tech がフェーズ数ぶん** |
| 節 | `4-2` 〜 `4-4`（小見出しは任意） | **同じ。中を `#### Phase {n}: ` で分ける** |
| 作成・変更ファイル | `4-1` に1つ（**実装後に記入**） | **同じ。実装後に記入するとき「フェーズ」列を付ける** |
| 受け入れ基準 | フラットでよい | **`#### Phase {n}: ` の小見出しで分ける**（`design-review tech Phase{n}` が範囲を絞れなくなるため） |
| レビュー | `/design-review tech` を1回 | `/design-review tech Phase{n}` をフェーズごと |
| Stage 2 ステータス | `✅ 確定` | `🔵 Phase {n} まで確定`（全フェーズ済みで `✅ 確定`） |

**承認ゲートは増やさない。** フェーズごとの `design-review tech` は
**そのフェーズの実装に入る直前の1回**で、**まとめて書く場合の Stage 2 承認がフェーズに分散しただけ**である
（§2-5 の規模ゲート原則を崩さない）。

**途中で切り替えてよい。** 小見出しを足す／外すだけなので、**節の意味は変わらない**。
残りをまとめて書くなら、以降のフェーズを1つの小見出しにまとめる。
**受け入れ基準の小見出しを後から足す場合も、Stage 1 の中身は変わらないので再レビューは要らない**
（`design-review feature` を回し直さない。改訂履歴に「受け入れ基準をフェーズ別に分けた」と書けば足りる）。

### 2-4. プッシュ前の共通フロー

```
/pre-push-check → プッシュ
```

- **`/sync-check`（全量照合）は `/pre-push-check` が実行する。** 未プッシュコミットに
  ソース変更が含まれる場合だけ走る（含まなければスキップ）
- `/complete-feature` も機能単位で実行する（対象はその設計書の変更範囲に絞る）
- **`/update-docs` は全量照合をしない。** あちらは変更駆動で、
  **変更駆動では拾えない乖離を見つけるのが `/sync-check` の役目**

### 2-5. 規模ゲート原則（重要）

要求 → 設計 → タスク → 実装 → 実態設計書 のフル形パイプラインは **L 規模のみ**に適用する。
S/M は上記の軽量フローを維持する。「全変更に重いセレモニーを課す」ことは、
このハーネスが避けたい失敗そのものであるため、規模ゲートを崩さない。

ただし以下の**軽量なトレーサビリティ検証は全規模に適用してよい**:

- 受け入れ基準の各行に確認方法があるかの検査（**L は `/design-review` が設計時に、M は `/code-review` が実装後に**）。
  「受け入れ基準が Stage 2 に落ちているか」の対応表は L だけ（M は設計が薄く、対応表を作る値が無い。
  基準に対応する設計判断の欠落は `/complete-feature` のゲート2 が最後に止める）
- 実装状態と設計書の突合と、残作業のタスク一覧への追記（`/sync-check` / `/update-docs`）

**`constitution.md` §1 の「設計レビューは L 規模にのみ課す」と衝突しない。**
あちらが言う「フル形のパイプライン」は **2段階設計・設計レビュー・網羅同期チェックの組み合わせ**で、
**L だけが2段階設計と `design-review feature`（＋ 体験系アドバイザー）と `design-review tech` を持つ。**
**M は設計レビューを既定で持たない**（0.43.0。画面に触る M でユーザーが頼めば feature を1回足せる）。
**承認ゲートは M・L ともに Stage 2 の1つ**である（L はこれに Stage 1 の承認が加わって2つ）。

## 3. バグ修正の詳細

### 3-1. フロー順序（原因特定 → 規模判定 → 設計書）

バグ修正も S/M/L 判定の対象だが、**症状だけで規模を決めない**。原因特定後に判定する。

```
1. バグ発見（症状の報告）
   ↓
2. 原因特定フェーズ（対話的、設計書なし）
   - エラーメッセージ全文確認
   - ログ追加 or 最小再現手順で原因を確定
   - 「何が原因だと考えたか」を短く示す（仮説の先行共有）
   ↓
3. 規模判定フェーズ（AI 推測 → ユーザー承認）
   ↓
4. フロー選択
   ├─ S: 直接修正 → /build-check → コミット → /done
   ├─ M: 設計書作成（**M の最小形で、§3-3 の読み替え表の節だけ**。これが「軽量」の実体）
   │      → ユーザー承認 → /code-review → /build-check → /update-docs → コミット → /done
   │      （設計レビューは既定で回さない。§2-2）
   └─ L: 通常の設計書作成（2段階設計）→ 以降 L フローと同じ
```

### 3-2. 緊急バグ対応の2段構え

1. **暫定修正（S 規模）**: 原因不明のまま応急処置。影響を最小化
2. **恒久対応（後日 M/L）**: 落ち着いた後、根本原因を調査して恒久修正

**暫定修正時の注意**:
- 「根本原因不明で暫定対応」とコミットメッセージに明記
- 後日の恒久対応のために issue / TODO を必ず残す
- 暫定対応のまま放置しない

### 3-3. M/L 規模バグの設計書の書き方

専用テンプレートは用意せず、機能設計書テンプレートをそのまま使う。セクションを読み替える:

| 機能設計書のセクション | バグ修正時の内容 |
|---------------------|-----------------|
| 1. 概要 > 背景 | 問題の発見経緯・症状 |
| 1. 概要 > 方針 | 根本原因の分析・修正アプローチ |
| 3-2. 受け入れ基準チェックリスト | 「この操作で再発しないこと」を検証可能な形で。**各行の末尾に再発確認の方法**（確認スクリプト名・操作手順） |
| 4. 技術設計 | 修正内容・影響範囲・再発防止策（4-1 は実装後に記入） |
| （M は 3-2 の各行の確認方法。L は 5. 動作確認計画） | 修正箇所と再発確認の手順 |

**専用ディレクトリは作らない**。運用上の不便が出てから検討する（YAGNI）。

## 4. 2段階設計の詳細（L 規模）

### 4-1. Stage 1: 機能・画面設計

**目的**: 「何を作るか」「なぜ作るか」を確定する（実装の「HOW」は扱わない）

**記入内容**:
- 対象画面・機能の一覧（識別子、新規/変更の区別）
- 操作フロー（ユーザーの動き）
- **受け入れ基準チェックリスト**（テスト可能な形式。完了処理のゲートになる）
- **未解決事項** `[NEEDS CLARIFICATION]`（承認前に 0 件にする）
- 確認の重点観点

**節ごとに適用規模が違う。** この節全体が L だけのものではない:

| 節 | L | M |
|---|---|---|
| 3-1 対象と操作フロー | 必須 | **UI・挙動に触るときだけ** |
| 3-2 受け入れ基準 | 必須 | **必須**（省かない） |
| 3-3 未解決事項 | 必須 | 仕様が曖昧なら |
| 3-4 Stage 1 レビュー記録 | 必須 | 不要（`design-review feature` を回さない） |

**レビュー**: `/design-review feature`
- **code-reviewer**: 設計書間の整合性 + UI/UX 設計観点
- **体験系アドバイザー**（環境プラグインが提供する場合のみ）: 企画・UX 体験観点

**承認ゲート**: ユーザー承認で Stage 2 に進む

### 4-2. Stage 2: 技術設計

**目的**: 「どう作るか」を確定する

**記入内容**（**決めたこと・実装前に確かめること・外部境界・スキーマ**だけ。M・L・試作とも）:
- インターフェース仕様 —— **外部境界だけ**（利用者・他プロセス・他システムが呼ぶもの。外部 API の入出力例は必須）。
  **内部モジュール間の関数・型・interface は書かない**（型検査が守る）
- データ構造・永続化の変更（スキーマ・移行はコードブロックでよい）
- 内部設計 —— **決めたこと（代案と理由）の表**と**実装前に確かめること**（`【実装時に実測】`）。データの流れは文か図で。
  **ファイルごとの変更点・関数の signature・型定義・処理手順のコードブロックは置かない**
- 作成・変更ファイル一覧（**実装後に記入**。設計時は空で置く。`/code-review` が差分と突き合わせる）

**なぜ絞るか**（0.43.0）: 実プロジェクトの L 3本で 4 章が 165〜500 行、うち **3分の1 がコードブロック**
（signature・interface・ファイルごとの変更点）だった。tech レビューの指摘 31 件のうち 12 件は
**節どうしの食い違い・列挙の漏れ・タスクの順序**で、**設計書が先に実装を書いたから生まれた誤り**。
決めたことだけなら、その誤りは存在しない。**行数の目安は置かない** —— 守られないので、
**コードブロックの有無**を `/design-review` の検査6 が機械で見る。

**レビュー**: `/design-review tech`（**L と試作**。M は既定で回さない）
- **code-reviewer**: 技術的な矛盾・設計書整合性 + Stage 1 の受け入れ基準が全て設計に落ちているか
  + **内部設計が実装の写しになっていないか**（signature・ファイルごとの変更点があれば削る側の指摘）

**承認後**: 実装フェーズへ

#### まとめて書くか、フェーズごとに書くか

**既定はまとめて書く**（Stage 2 を全フェーズ分書き、`/design-review tech` を1回通してから実装に入る）。
**後のフェーズの設計が前のフェーズの実装結果に依存するときだけ、フェーズごとに書いてよい**
（§2-3「Stage 2 はフェーズごとに書いてよい」。**tech レビューがフェーズ数ぶん増える**）。

フェーズごとに書くとき:

1. **共通のものを先に書く** — `4-0`（設計方針への書き戻し）・
   `4-2` 〜 `4-4` の **`#### 共通`** の小見出し（複数フェーズに効く取り決め）。
   `4-1`（作成・変更ファイル）は**実装後に記入するとき「フェーズ」列を付ける**
2. **着手するフェーズの小見出しだけを書く** — `4-2` 〜 `4-4` の `#### Phase {n}: 〇〇`
3. `/design-review tech Phase{n}` を回す
4. 承認されたらそのフェーズを実装する
5. **次のフェーズに着手するとき、1 の共通部分を見直してから次の小見出しを書く**
   （前のフェーズの実装で前提が変わっていることがある。**ここが分けて書く利点**）

**書いていないフェーズの小見出しを省略しない。** `#### Phase 3: 〇〇` の見出しは立てて、
本文に `🔵 未記入（Phase 3 に着手するときに書く）` と書く。
**見出しが無いと、設計漏れと未記入の区別がつかない。**

**保留・却下したフェーズは「対象外」と書く。** タスク一覧で ⏸️保留 / ❌却下 にしたフェーズは、
小見出しの本文に `⏸️ 対象外（理由）` と書く。**空のまま残すと、全フェーズ完了の判定ができない。**

### 4-3. Stage 2 → Stage 1 戻り手順

Stage 2 記入中に技術制約で実現不可と判明した場合:

1. Stage 2 の記入を中断
2. メタ情報の「Stage 1 ステータス」を `🟡 レビュー中` に戻す
3. 該当する Stage 1 セクション（受け入れ基準・操作フロー等）を修正
4. `/design-review feature` を再実行
5. ユーザー再承認
6. Stage 2 を再開

改訂履歴には「Stage 1 を再修正した版」として明記する。
