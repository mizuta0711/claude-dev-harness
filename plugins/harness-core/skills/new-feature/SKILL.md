# 新規設計書の作成

機能開発・改修・バグ修正のいずれかに対応する設計書を作成する。

判定基準・フローの詳細は同梱の [開発フローと規模判定.md](開発フローと規模判定.md) を参照（必要になった時点で読む）。

> **利用者が「試作」「MVP」「プロトタイプ」だと明示しているなら、
> `/harness-core:new-prototype` を案内する**（設計書の厚みは同じで、レビューの回数が減る）。
> **こちらから自動で渡さない。** 規模判定で試作かどうかを決めてはいけない ——
> **試作かどうかは利用者が決める**（あのスキルの冒頭に理由がある）。
> **明示が無ければ本実装として進める。**

## 推奨で進める（ユーザーが選んだときだけ）

**既定は止めてユーザーに聞く。** 規模判定（Step 1）・未解決事項の確定（Step 2）・Stage 1 の承認・Stage 2 の承認は、
既定ではユーザーの返事を待つ。**この既定を AI の側から緩めない**（「推奨で進めましょうか」と持ちかけない）。

**「推奨で進めて」「判断は任せて完了まで止めないで」のように、止めない意思が明示されたときだけ、その設計書の範囲で切り替わる。**
**「進めて」「任せる」だけでは切り替えない**（作業を進める指示であって、承認を委ねる指示とは限らない）。
切り替わるのは**指示を受けた設計書1本だけ**で、次に `new-feature` で作る設計書には引き継がない。
この切り替えは `constitution.md` §1・§2 の例外（指示をもってユーザー承認とみなす）に当たる。

切り替え中にすること:

| | すること |
|---|---|
| **a. 推奨で確定する** | 規模判定・未解決事項・Stage 1 の承認・Stage 2 の承認を **AI の推奨で確定**し、記録を残す。メタ情報の該当欄（「変更規模」の値の末尾・「Stage 1」・「Stage 2」）に `✅ 確定（AI 推奨で確定・ユーザー指示 yyyy-mm-dd「…」）`（「…」は指示の文言）。未解決事項の表は「回答」列の先頭に `AI 推奨:` を付け、状態は ✅ 解決にする |
| **b. それでも止めて聞く** | 下の既定リストに当たる判断は、**切り替え中でも止めてユーザーに聞く** |
| **c. レビューは省かない** | `design-review` はいつもどおり回す（L の feature / tech。M は既定で回さないので、ここでも増えない）。省けるのは**ユーザーの返事を待つこと**だけ |

**それでも止めて聞く判断（既定リスト）**（**このリストの正はここだけ**。他のスキル・文書は「`new-feature` の既定リスト」として参照する）:

- 認証・認可・課金
- **削除**（データ・機能・画面を消す判断）
- マイグレーション
- **外へ出す機能**（push・公開・送信）
- **新しい画面やタブを足すか／どの画面に置くか**

**プロジェクトごとの足し引き**: プロジェクトの `CLAUDE.md` に見出し「**推奨で進めるときも止めて聞く判断**」があれば、
その箇条書きを既定リストに**足す**。既定から**引く**ときは、同じ見出しの下に「〜は止めない」と書く。
**判断に迷ったら止めて聞く側に倒す。**

> **なぜ記録を設計書に残すか。** ユーザーは「推奨で進めて」と言った時点では個々の判断を見ていない。
> 何を AI が決めたかが設計書に残っていれば、`/harness-core:done` と `/harness-core:complete-feature` が
> **「推奨で決めた判断」として最後に一覧で出せる**（ユーザーはそこで見て、覆すものだけ指示すればよい）。

## Step 0: プロジェクトが初期化済みかを確認

**空のリポジトリ・未初期化のリポジトリで呼ばれることは珍しくない**（初回の機能開発＝土台構築）。
規模判定の前にここを確認する。判定を誤ると「機能追加のつもりが実は環境構築込み」になる。

`.claude/harness.config.json` の `paths.source` のグロブに**実ファイルが1つも無ければ未初期化**とみなす
（環境ごとの判定条件をハードコードせず、設定契約から導く）。

未初期化だった場合の**既定の対応**:

1. ユーザーに「プロジェクトが未初期化であること」を伝える
2. **初期化を `Phase 0` として同じ設計書に含める案を提示する**（既定）。
   別作業に切り出すと、設計書の受け入れ基準が「動くもの」にならず、
   タスク一覧と実装の対応が崩れるため
3. 初期化を含めると**ほぼ必ず L 規模になる**（新パターン・データ構造・10ファイル超）。
   Step 1 の規模提示にその理由を明記する

```
このリポジトリはまだ初期化されていません（src/ にファイルがありません）。
初期化を Phase 0 として設計書に含める前提で進めます。
そのため規模は L と判断します（環境構築 + 新規データ構造 + 新規画面）。
```

初期化の具体的な手順は**環境側の責務**である。`.claude/harness/environment.md`（`CLAUDE.md` から展開される）と
`.claude/rules/` に注意点が書かれていれば必ず読むこと（既存ファイルを壊す足場ツールがある）。

> ユーザーが「初期化は別でやる」と明示した場合のみ、初期化を含めずに進める。

## Step 1: 変更の性質と規模をユーザーに確認

テンプレートを読み込む前に、以下を確認する:

1. **変更の性質**（AI が推測して提示、ユーザー承認）: 新規追加 / 改修 / バグ修正
2. **変更規模**（AI が推測して提示、ユーザー承認）:
   - S: 1〜2ファイル、データ構造変更なし、**挙動と操作フローが変わらない**（文言・色・余白・整列）
   - M: 3〜10ファイル、既存パターンに沿った変更、**UX の影響が既存の単一画面（コンポーネント）内に収まる**
   - L: 10ファイル超、新パターン、データ構造の破壊的変更、または **複数の画面（コンポーネント）に影響する**

判定ルール:
- 判定に迷ったら **L 寄りで提示する**
- **UX は影響範囲で判定する。** 挙動が変わらない＝S / 単一画面内で挙動が変わる＝M /
  複数画面に影響する・画面を足す＝L（**「UX 変更を含めば自動的に L」ではない**）
- **1つでも L 相当の軸があれば L。** この規則が UX 軸より優先する ——
  単一画面内の改修でも**データ構造・永続化が L 相当なら L**
- **認証・認可・課金・削除・マイグレーション・依存ライブラリの追加に触るなら、
  1ファイルでも S に置かない**（S は `/code-review` を省くため）

**提示例**:
```
指示内容から以下と判断します:
- 変更の性質: 新規追加
- 変更規模: M 規模（既存パターンに沿った項目追加、関連ファイル5つ程度、
  UX の影響は設定画面1つの中に収まる）

この判定で進めてよいですか？
```

**「推奨で進める」に切り替わっているときは、聞かずに推奨の規模で確定し、メタ情報に記録する**
（→ 上の「推奨で進める」。規模の提示そのものは報告に残す）。

### L 規模で、1本に収まらないなら先に分ける

**L の上に天井がある。** 規模判定の表は L の上限を書いていないので、
**10ファイルでも100ファイルでも L** になる。**プロジェクト開始時はとくに危ない** —
依頼が「作りたいものの全体」なので、**要件がそのまま1枚の設計書になる**。

**判定（一次ゲート）**: **受け入れ基準が、独立に「動くもの」として確認できる塊に2つ以上に分かれるか。**
行数やファイル数は書き終わるまで分からないが、**これは今この時点で判定できる。**

> **実測**（ある新規プロジェクト）: 機能設計書1本が **2,226行／157,345文字**・タスク39本・
> 受け入れ基準46項目。**上流の要件文書は188行**で、その約12倍だった。

**分かれるなら、設計書を書き始める前に `/harness-core:plan-milestones` へ渡す。**
あちらが台帳（`docs/backlog.md`）に順序を置き、**1本目の設計書作成のためにここへ戻す。**

**迷ったら分ける方向で提示する。** §1-3 のバイアス補正は規模を**上げる**方向にしか働かないので、
**1本に全部入れる方向へ倒れる**（→ [開発フローと規模判定.md](開発フローと規模判定.md) §1-3・§1-6）。

**M 以下では分けない**（軽い変更に重い手続きを課さない。同 §2-5）。

### S 規模と確定した場合はここで終了する

**S 規模では設計書を作成しない**（開発フローと規模判定.md §2-1 の軽量フロー）。
以下を案内してスキルを終了する:

```
S 規模のため設計書は不要です。
実装 → /harness-core:build-check → コミット → /harness-core:done の軽量フローで進めます。
```

⚠️ **S は「完成の定義」を持たない**（設計書が無いので受け入れ基準が無い）。
**挙動が変わるなら S ではない。** 判定を S にする前にここを見分けること。

S は設計書を作らない。**設計書を残したいなら M として扱う**（M の最小形で作る）。

## Step 2: 曖昧さの解消（`[NEEDS CLARIFICATION]`）

**L 規模では必須。M 規模でも仕様が曖昧な場合は実施する。**

**M 規模でも「未解決事項」の節は使う。** Stage 1 で `⚪ 不要` にするのは
**3-1（対象と操作フロー）と Stage 1 レビュー**だけで、
**3-2（受け入れ基準）と 3-3（未解決事項）は M でも書く**（0.41.0 で変えた）。

設計書に推測を書き込む前に、確定していない事項を洗い出してユーザーに質問する。

### やること

0. **プロジェクトの要件・ドメイン文書を先に見る**（`.claude/harness.config.json` の
   `projectDocs.requirements`）。登録があれば配下の見出しを拾い、**依頼内容と矛盾する
   ドメイン制約・ビジネスルールが無いか**を確認する。矛盾があればそれを質問に含める。
   **登録が無ければ素通りしてよい**（fail-open）
1. 依頼内容から未確定事項を列挙する。下の**定番の観点**を一度に通しで見ること
2. 各項目を **選択肢つきの質問**にしてユーザーに提示する（自由記述だけの質問にしない）
3. 回答を設計書の**見出し「未解決事項」**の節の表に記録する（→ 下記「節の探し方」）
4. その場で決められない項目は `❓ 未解決` のまま残し、本文の該当箇所に
   `[NEEDS CLARIFICATION: 何が不明か]` を書く

### 定番の観点チェックリスト

**質問は一度にまとめる。** 聞き漏らして往復が増えるのが最大の摩擦になる
（`AskUserQuestion` は1回4問までなので、**この表で先に洗い出してから**質問をまとめる）。
該当しない観点は飛ばしてよいが、**飛ばす判断を一度は通すこと**。

| 観点 | 具体的に聞くこと |
|------|----------------|
| 対象範囲 | どこまでを含むか / 含まないか |
| **永続化先** | どこに保存するか。**それが今この開発機で動くか**（DB サーバー・外部サービスの要否） |
| **データ構造** | 正規化するか非正規化か。多対多は中間テーブルを作るか |
| 入力の許容範囲 | 必須項目・形式の制約・上限・未入力や異常値の扱い |
| **一意制約と重複** | 重複を許すか。禁止するなら**重複時に入力を保持するか捨てるか** |
| **破壊的操作の UX** | 削除・上書きに確認を挟むか。取り消せるか |
| **従属データの掃除** | 親を消したとき、参照が切れた子をどうするか |
| **一覧の並び順とページング** | 既定の並び順は何か。件数が増えたときどうするか |
| **画面配置** | 同一画面に同居させるか、モーダルか、別ページか |
| 失敗時の挙動 | エラー表示・リトライ・ロールバック |
| 既存機能との関係 | 置き換えるのか、併存するのか |
| 完了条件 | どうなったら「できた」と言えるか |

> **太字の観点は、実運用で実際に漏れて往復を生んだもの**（C1 1周目の実測）。
> とくに「永続化先が今この開発機で動くか」は、確認を怠ると設計確定後に
> **設計書の改訂が必要になる**（PostgreSQL 前提で設計 → 開発機に無く SQLite へ変更、が実際に起きた）。

### 禁止事項

- **未確定事項を推測で埋めて設計書を書き進めない**
- 「後で決める」で放置しない（未解決として明示的に残す）
- **質問を小出しにして往復を増やさない**（上の表で先に洗い出す）

**Stage 1 のレビュー・承認前に、未解決事項は 0 件にすること。**

**「推奨で進める」に切り替わっているときは、質問を出さずに推奨の選択肢で確定する**
（回答列の先頭に `AI 推奨:`）。**上の「推奨で進める」の既定リストに当たる項目だけは質問する。**

## Step 3: テンプレートをコピーして設計書を作成

1. テンプレートを読み込む:
   - プロジェクトに `docs/features/TEMPLATE.md` があればそれを使う（プロジェクト固有の調整が入っている可能性があるため優先）
   - 無ければ本スキル同梱の [TEMPLATE.md](TEMPLATE.md) を使う
   - **M では `規模: L のみ` の印が付いた節を生成しない**（印のある見出しから、**次の同レベル以上の見出し**の手前まで。`### 3-4` なら次の `## 4.` で止まる）。
     同梱版では「タスク一覧」「Stage 1 レビュー記録」「動作確認計画」「関連ドキュメント」「注意事項」の5つ。
     **印はコピー後に全部消す**（L では節を残して印だけ消す）。
     印の無い古いプロジェクト版 TEMPLATE では、節を落とさずに従来どおりコピーする（見出し名で推測して消さない）
2. 以下の命名規則でファイルを作成:
   - パス: `docs/features/yyyymmdd_$ARGUMENTS.md`
   - **マイルストーンに分けた中の「まだ着手しない」分は `docs/features/planned/yyyymmdd_$ARGUMENTS.md`**
     （無ければ作る）。**着手するときに直下へ `git mv` し、台帳（`docs/backlog.md`）の「設計書」の欄も直下のパスへ直す** —
     直下に未着手を並べると、フックが毎セッション列挙し `sync-check` が毎回照合する
   - 日付は本日の日付（yyyymmdd 形式）
3. メタ情報を埋める:
   - 全体ステータス: `🔵 設計中`
   - 変更の性質 / 変更規模: Step 1 で確定した値
   - **Stage 1 ステータス**: L 規模 = `🔵 記入中` / M 規模 = `⚪ 不要`
     （**`⚪ 不要` は「3-1 と Stage 1 レビューが不要」という意味で、
     受け入れ基準 3-2 は M でも書く**。TEMPLATE.md の凡例を参照）
   - **Stage 2 ステータス**: M/L 規模 = `⚪ 未着手`
   - 未解決事項: Step 2 で残った件数
   - 作成日・最終更新: 本日の日付
4. **L 規模ではタスク一覧を記入し、依存関係と並列可否 `[P]` を必ず埋める。**
   M はタスク一覧の節を作らない（完了の判定は受け入れ基準のチェックで行う）
5. **「作成・変更ファイル」の節は空のまま置く**（M・L とも）。実装後に `/harness-core:code-review` が差分から記入する
   （型検査と確認スクリプトが実装中の網羅を担うので、設計時に列挙しない）
6. **Step 2 の回答で Stage 1 が埋まるなら、そのまま Stage 1 の各節まで記入してよい。**
   一度スキルを終えてから「では記入します」と戻るのは無駄な2手になる。
   Step 2 で曖昧さを潰した直後は、機能・画面設計と受け入れ基準を書ける状態になっていることが多い

   - **「未解決事項」**の節には **Step 2 の質問の選択肢と回答をそのまま転記する**。
     「なぜその設計にしたか」が設計書に残り、後から読む人が判断を追える
   - 埋まらない項目が残る場合は無理に書かず `[NEEDS CLARIFICATION]` を残す

### 台帳（`docs/backlog.md`）に1行足す

**作った設計書は、必ず台帳の「計画」の表に載せる。** 人が**プロジェクト全体の作業と
その優先順位を1枚で見渡せる**ようにするため（これが台帳の役目）。

| 場面 | すること |
|---|---|
| **単発で設計書を作った**（このスキルだけで完結） | **表の末尾に1行足す** |
| `plan-milestones` から来た | **何もしない**（あちらが既に行を置いている） |
| `planned/` の設計書に着手して直下へ移した | 行はある。**「設計書」の欄を直下のパスへ直す** |

- **列はこう埋める**:

  | 列 | 書くもの |
  |---|---|
  | `#` | **空欄にする。** 番号は `plan-milestones` が1つの依頼を分けたときだけ `1..n` で振る |
  | やること | 設計書の題名（`$ARGUMENTS`） |
  | 狙い | **これができたら終わり**、と言える一文 |
  | 設計書 | `` `docs/features/yyyymmdd_<名前>.md` `` （コードスパン。着手前なら `planned/` を含めたパス） |

- **骨格の空のプレースホルダ行（`| | | | |`）が残っていれば、それを置き換える**（空行を残さない）
- **進捗は書かない**（置き場とメタ情報が正。「✅完了」も書かない）
- **末尾に足したうえで、「順序＝優先順位なので、違うなら動かしてください」と報告に添える。**
  位置を毎回聞くと往復が増える
- **見出しは「計画」。** 既存プロジェクトでは「マイルストーン」のことがあるので、**どちらでも拾う**
- **台帳が無い・その見出しが無ければ、そこに書かずユーザーへ報告する**（fail-open）
- **S 規模は設計書を作らないので、ここも行わない**

### 節の探し方（重要）

**設計書の節は「見出し名」で探す。番号を当てにしない。**

プロジェクトが独自の `docs/features/TEMPLATE.md` を持つ場合、`new-feature` は**そちらを優先する**。
その TEMPLATE が同梱版より古いと、**同じ番号が別の節に使われている**ことがある
（実測: あるプロジェクトでは `3-3` が「Stage 1 レビュー記録」で、
このスキルが書き込むはずの「未解決事項」は存在しなかった）。

- 見出し名で探し、**番号は無視する**（`### 3-3. 未解決事項` でも `### 3-2. 未解決事項` でも同じ節）
- **見つからなければ、そこに書かずユーザーへ報告する。**
  「TEMPLATE.md に『未解決事項』の節が無い。同梱版と節構成がずれている可能性がある」と伝え、
  **番号が近い別の節に書き込まない**

## Step 4: ユーザーへの報告

- 作成したファイルパス
- 変更の性質と規模（確定値）
- 未解決事項の件数（残っている場合は内容も）
- **次のアクション**:
  - **L 規模**: Stage 1（機能・画面設計＋受け入れ基準チェックリスト）を記入 → `/harness-core:design-review feature`
    - **Stage 2 は既定どおりまとめて書き、`design-review tech` を1回で通す。** フェーズは
      「実装 → `code-review` → コミット」の単位として使う
    - **Stage 2 に書くのは「決めたこと（代案と理由）・実装前に確かめること・外部境界・スキーマ」だけ**（M・L とも）。
      関数の signature・interface・ファイルごとの変更点・処理手順のコードブロックは置かない
      （コードと型検査が持つ。`design-review` の検査6 が「実装の写し」として指摘する）
    - **後のフェーズの設計が前のフェーズの実装結果に依存するときだけ、Stage 2 をフェーズごとに書いて進められる**旨を添える。
      **コストは `design-review tech` がフェーズ数ぶん増えること**。依存が無いなら分けない。
      **節の構成は変えず、`4-2` 〜 `4-4` の中を `#### Phase {n}: 〇〇` の小見出しで分けるだけ。**
      そうするなら**受け入れ基準（3-2）も同じ形の小見出しで分けておく**こと
      （→ [開発フローと規模判定.md](開発フローと規模判定.md) §2-3）
  - **M 規模**: **受け入れ基準（3-2）** と Stage 2（技術設計）を記入
    → **ユーザーが Stage 2 を読んで承認** → 実装
    - **M は設計レビューを既定で回さない**（0.43.0）。承認ゲートは Stage 2 の1つで変わらない。
      3-2 の各行の確認方法は `/harness-core:code-review` が見る。頼まれれば `design-review tech` は回る
    - **画面に触る M で、置き場や文言を実装前に見てほしいとき**は、ユーザーの指示で
      `/harness-core:design-review feature` を**1回足せる**（規模は M のまま。tech は足さない。
      結果は 4-5 に「対象: Stage 1」で記録する）。**既定では足さない**
    - **M の設計書は最小形**（タスク一覧・Stage 1 レビュー記録・動作確認計画・関連ドキュメント・注意事項の節が無い）。
      Stage 2 の `4-2` 〜 `4-4` は**判断があるものだけ**書き、無いものは「なし」とする
    - **受け入れ基準を省かない。各行の末尾に確認方法を併記する**（確認スクリプト名・操作手順・「目視」など）。
      **M ではこれが動作確認計画の代わりになる。** 省くと `complete-feature` の完了ゲートと
      `design-review` の検査2・4 が空振りし、**M に「できたと言える条件」が無くなる**
    - **UI・挙動に触る M では 3-1（対象と操作フロー）も書く**
      （`design-review tech` が UI・体験の観点を見る手がかりになる）
  - **バグ修正（M/L）**: 「1. 概要 > 背景」に症状、「1. 概要 > 方針」に根本原因を記入
  - **S 規模**: 設計は不要。そのまま実装 → `/harness-core:build-check` → コミット → `/harness-core:done`
- **実装フェーズに入ったら `coding-specialist` サブエージェントへ委譲できる**旨を添える
  （委譲する理由と渡すものは `/harness-core:design-review` の Step 7 にある）
- 💡 L 規模で UI・挙動の変更を含む場合は「5. 動作確認計画」も記入する旨を案内する
  （確認手段は `.claude/harness.config.json` の `verification` を参照）。
  **M は動作確認計画の節を作らず、受け入れ基準の各行の確認方法で代える**
