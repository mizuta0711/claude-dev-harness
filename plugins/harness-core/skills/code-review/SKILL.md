# コードレビュー＋指摘対応

## Step 1: レビュー対象の特定

$ARGUMENTS が指定されている場合はそのファイル/ディレクトリを対象とする。未指定の場合:

1. 未コミットの変更: `git diff --name-only`
2. 1 が空なら直近コミット: `git diff --name-only HEAD~1 HEAD`

**対象の機能設計書も特定する**（層1 の「設計書との一致」「作成・変更ファイル」で使う）:
`docs/features/` 直下の設計書のうち、**全体ステータスが `🟡 実装中` のもの**。
**複数あればどれかをユーザーに聞く。無ければ「作成・変更ファイル」の記入はしない**（設計書との突き合わせも省き、その旨を結果に書く）。

## Step 2: レビュー観点の決定

観点は3層で構成する。**すべてを毎回チェックせず、変更内容に該当するものだけを見る。**

### 層1: 環境非依存の共通観点（常にチェック）

- **設計書との一致**: 実装が機能設計書「4. 技術設計」の**外部境界（4-2）・スキーマ（4-3）・決めたこと（4-4 の表）に反していないか**。
  **signature の一致は見ない**（0.43.0 から設計書は内部の関数・型を持たない。`4-4` の決めたことに反していれば
  「設計書を直すか実装を直すか」をユーザーに返す）
- **受け入れ基準の各行に確認方法があるか**（M では `design-review` を既定で回さないので、ここが唯一の検査になる。
  無い行があれば記入を求める。`/harness-core:complete-feature` の完了ゲートがこの行で判定する）
- **UI・体験の観点**（「対象と操作フロー」の節に記入がある変更だけ。M は設計レビューを回さないので、
  実装後の画面で見る）: 既存画面・既存操作とのパターン一貫性 / 情報階層 /
  アクセシビリティ（キーボード操作・コントラスト・代替テキスト）/ 想定する表示サイズで成立するか
- **「作成・変更ファイル」と差分の一致**: 設計書の見出し「作成・変更ファイル」の表が、
  レビュー対象の差分（`git diff --stat` 等）と一致するか。**空なら差分から記入する**
  （**空 = ファイル名の入った行が1行も無い**。枠の行 `| | 新規/変更 | |` だけなら空）
  （**実装後に書く節**である。設計時は空で置き、ここで埋める。`/harness-core:complete-feature` の整合性チェックがこの表を使う）。
  フェーズごとに実装しているなら「フェーズ」列を付けて、今回のフェーズの行を足す
- **エラーハンドリング**: 失敗パスの扱い（握り潰していないか、利用者に伝わるか）
- **境界値・異常系**: 未入力・上限・null/空コレクションの扱い
- **セキュリティ**: 認証・認可の抜け、機密情報のログ出力、外部入力の検証
- **パフォーマンス**: ループ内の重い処理、N+1 的な繰り返し取得、不要な再計算
- **可読性・保守性**: 命名、重複（DRY）、過剰な一般化（YAGNI）

### 層2: プロジェクトの rules（自動ロード）

`.claude/rules/` の paths ルールは、該当パスのファイルを読んだ時点で自動ロードされる。
**手動で読みに行かない**。ロードされたルールに違反していないかを見る。

### 層3: 環境プラグインが提供する観点

有効な環境プラグイン（`harness-nextjs` / `harness-unity` / `harness-wpf` 等）の
agent・skill が固有の観点（フレームワーク規約、UI 規約、プラットフォーム制約）を提供する場合はそれに従う。
無い場合は層1・層2 のみで実施し、その旨を結果に明記する。

## Step 3: 動作確認のリマインド

UI・挙動の変更を含む場合、レビュー結果の末尾に次を付記する:

- `.claude/harness.config.json` の `verification.skill` が非 null →
  「指摘の修正後に `/{verification.skill}` を実施してください」
- `verification.manualGate` が true → 「人手による動作確認が必須です」

## Step 4: 結果をファイルに保存 + 報告

`docs/reviews/YYYYMMDD_HHMMSS_code-review.md` に保存:

```markdown
# コードレビュー結果

- 実施日時: YYYY-MM-DD HH:MM
- 対象: （レビュー対象ファイル一覧）
- 適用した観点: 共通 / rules（ロード済みのもの）/ 環境プラグイン（名称）

## 指摘事項
| # | 重要度 | 場所 | 内容 | 対応状況 |
|---|--------|------|------|---------|
| 1 | 重要/中/低 | ファイル:行 | （指摘内容） | 修正済み/未対応 |

## 判定: ✅ 承認 / ⚠️ 条件付き承認 / ❌ 差し戻し
```

ユーザーには**判定・指摘件数・重要な指摘の概要**のみ報告する。「良かった点」の列挙は不要。

## Step 5: 指摘対応（自動修正）

重要度「重要」の指摘で明確な修正方法がある場合は自動的に修正し、
レビュー結果ファイルの対応状況を「修正済み」に更新する。

修正が複雑・判断が必要な場合は、修正案を提示してユーザーに確認を求める。
