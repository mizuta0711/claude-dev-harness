# 試作・MVP のフロー

**この文書はスキルの手順書で、主語は実行する側（AI）である。**
**ユーザーが決める箇所は5つだけ**で、それ以外はこちらで進める。

| ユーザーが決めること | どこで |
|---|---|
| 試作でよいか（捨てる前提か・何を確かめたいか・やめる条件） | Step 0 |
| Stage 1 の承認 | Step 2 |
| Stage 2 の承認 | Step 3 |
| 確かめられたかの判定 | Step 6 |
| どの出口にするか | Step 7 |

---

**本実装と試作は、規模（S / M / L）とは別の軸である。**

| 軸 | 決めるもの |
|---|---|
| **規模 S / M / L** | **設計書の厚み** |
| **本実装 / 試作** | **フロー** —— どのレビューを何回通すか |

**だから「試作だから設計書を省く」ではない。設計書は本実装と同じに書く。**
**減らすのはレビューの回数だけである。**

## ⚠️ ここに来るのは、ユーザーが明示したときだけ

**`/harness-core:new-feature` の規模判定から自動で渡されることはない。**
利用者が「試作を作りたい」「MVP で試したい」と**明示したときだけ**この入口を使う。

**理由は、これが規律を緩める方向の分岐だからである。**
「規律が重いのか、運用が下手だったのか」の切り分けは**まだ付いていない**
（出所は1プロジェクトの実測1件）。**AI の判定で軽い側へ落ちる経路を作らない。**

**迷ったら `new-feature`（本実装）を使う。** 試作かどうかは利用者が決める。

## 2つの「台帳」を混ぜないこと

この手順には**別々の台帳が2つ**出てくる。**必ずどちらかを明示して呼ぶ。**

| 呼び名 | ファイル | 何を持つか |
|--------|---------|-----------|
| **残作業台帳** | `docs/backlog.md` | **どの作業が残っているか**（「計画」の表に1行） |
| **設計書同期台帳** | `docs/設計書/.doc-sync.md`（`harness.config.json` の `designDocs.ledger` が指す） | **どのコミットを設計書へ反映したか**（コミットハッシュの一覧） |

## Step 0: 試作でよいかを確認する（ユーザーに聞く）

**次を満たさないなら `new-feature` へ戻す。**

| 確認 | なぜ |
|------|------|
| **捨てる前提か**（うまくいかなければ消す／作り直す） | **残す前提なら本実装である** |
| **何を確かめたいかが言えるか** | 言えないなら試作ではなく「とりあえず作る」になる |

> **「捨てる前提」は「必ず捨てる」ではない。** **始める時点で残す約束をしない**という意味である。
> うまくいけば**昇格**（本実装にする）も**完了**（試作のまま終える）も選べる（Step 7）。
> **残すことが最初から決まっているなら、試作ではなく本実装**である。

### やめる条件を言葉にしてもらう

**試作は終わりを決めないと終わらない。** **判定できる形**で書いてもらう。

| 成立する例 | なぜ成立するか |
|---|---|
| 「3日触って動く形にならなければやめる」 | **時間で切れる** |
| 「実機で 1 秒以内に描画できなければやめる」 | **数値で測れる** |
| 「外部 API が必要な項目を返さないと分かったらやめる」 | **事実の有無で決まる** |

| 成立しない例 | なぜ駄目か |
|---|---|
| 「うまくいかなければやめる」 | **誰も判定できない**（Step 4 と Step 6 が機能しなくなる） |

**受け入れ基準（Stage 1）に、やめる条件も1項目として書く。**

## Step 1: Stage 1 を書く

`/harness-core:new-feature` の **Step 0（初期化済みかの確認）・Step 2（曖昧さの解消）・Step 3**と
**同じ手順**で作る。違いは**置き場だけ**。

- **Step 0（初期化）は飛ばさない。** 足場が無ければ試作も始まらない
- **Step 2（曖昧さの解消）も飛ばさない。** 設計書を L 相当に書くなら `[NEEDS CLARIFICATION]` の
  解消も L 相当である。**ここを飛ばすと「何を確かめたいか」が曖昧なまま作り始める** ——
  試作で一番避けたい形である
- テンプレートは `docs/features/TEMPLATE.md` があればそれ、無ければ
  `new-feature` 同梱の [TEMPLATE.md](../new-feature/TEMPLATE.md) を使う（**専用のものは作らない**）
- パスは **`docs/features/prototype/yyyymmdd_<短い名前>.md`**（無ければ置き場を作る）。
  **ファイル名は短い名前にする** —— 「確かめたいこと」は Step 0 で聞いて**設計書の中に書く**
- **ここで書くのは Stage 1 だけ**（機能・画面設計＋受け入れ基準）。**Stage 2 は Step 3 で書く**
- **残作業台帳（`docs/backlog.md`）の「計画」に1行足す**。`new-feature` と同じ書き方で、
  **「設計書」の欄は `prototype/` を含めたパス**にする

> **残作業台帳に載せる。** 試作中は**残っている作業**である。載せないと忘れるうえ、
> **`pre-push-backlog-check` が push を止める**（`prototype/` も検査対象である）。

## Step 2: Stage 1 の査読（本実装と同じ・残す）

```
/harness-core:design-review feature
```

**ここは減らさない。** 試作でも**文脈の外から見る目が1つ**は要る。
**受け入れ基準に「やめる条件」が入っているか**も、ここで見てもらう。

→ **ユーザー承認**を取る。**承認されてから Step 3 へ進む**
（Stage 1 が変われば Stage 2 の前提も変わるので、**先に書かない**）。

## Step 3: Stage 2 を書いて、1回で査読する

**全フェーズ分をまとめて書く。**

**TEMPLATE は「フェーズが3つ以上なら着手するフェーズの分だけ書く」と案内しているが、
試作では従わない。** 査読を1回にまとめるためである。

- **Stage 2 ステータスは `✅ 確定`**（`🔵 Phase {n} まで確定` は使わない）
- 節の構成は変えない。`#### Phase {n}: 〇〇` の小見出しで分けるのは本実装と同じ

```
/harness-core:design-review tech
```

**フェーズを指定しない**（`tech Phase1` のように絞らない）。全フェーズ分を**1回**で見る。

→ **ユーザー承認**を取ってから実装へ進む。

## Step 4: 実装（フェーズごとにコミットしてよい）

**試作では「レビュー前にコミットしない」を外す。**
フェーズごとに実装してコミットしてよい（本実装では各フェーズで `code-review` を通す）。

> **本実装の規律は `.claude/harness/core.md` と
> [開発フローと規模判定.md](../new-feature/開発フローと規模判定.md) にある。
> 外れるのは試作のときだけである。**

**実装の途中で Step 0 の「やめる条件」に当たったら、そこで止めて Step 6 へ行く。**
試作の価値は**早く分かること**であって、作り切ることではない。

## Step 5: レビューと確認（最後に1回）

```
/harness-core:code-review     ← 試作全体で1回
動作確認（harness.config.json の verification）
/harness-core:build-check
/harness-core:update-docs
コミット
```

**`code-review` は試作の最後に1回**だけ。**動作確認と `build-check` は減らさない**
——**動かないものからは何も分からない**ので、試作ではここが本体である。

**`/harness-core:done` はまだ呼ばない。** 試作は Step 6 の答え合わせと Step 7 の出口まで行って終わる。

## Step 6: 確かめたいことの答え合わせ（ユーザーに聞く）

**ここが試作の山場である。** Step 0 で決めたものを**並べて提示し、ユーザーに判定させる**。

```
試作の答え合わせ

- 確かめたかったこと: <Step 0 のもの>
  → 結果: <実際にどうだったか。動作確認で見たこと>
- やめる条件: <Step 0 のもの>
  → 当たったか: はい / いいえ

判定をお願いします: 確かめられた / 駄目だと分かった / まだ分からない
```

| 判定 | 行き先（Step 7） |
|------|----------------|
| **確かめられた。この先も育てる** | **昇格** |
| **確かめられた。動いたところで用済み** | **完了** |
| **まだ分からない（時間切れ・別の前提待ち）** | **中断** |
| **駄目だと分かった** | **破棄** |

**「まだ分からない」を昇格にしない。** 判定できていないものを本実装へ上げると、
**捨てる前提だったものが黙って本番になる** —— 試作で一番避けたい失敗である。

## Step 7: 出口（4つ。ここまでこのスキルが扱う）

**`/harness-core:new-feature` へ渡さない。** あちらは**常にテンプレートから新規作成する**ので、
渡すと**設計書と残作業台帳の行が二重になる**。

**出口の処理が終わったら `/harness-core:done` で報告する。**

### 昇格 ——「確かめられた。この先も育てる」

1. `git mv docs/features/prototype/<doc> docs/features/`
2. **残作業台帳（`docs/backlog.md`）**の「設計書」の欄を**直下のパスへ直す**
3. **設計書同期台帳（`docs/設計書/.doc-sync.md`）の穴を埋める** ——
   `git log` で未記録のコミットを拾い、`/harness-core:update-docs` の書式で追記する
   （**ここを飛ばすと次の push で未同期が出る**）
4. **ここから先、本実装の規律に戻る** —— **すでに実装した分は Step 5 の `code-review` 1回で
   済んだものとして扱い、遡らない。昇格後に足す分から**、`design-review tech` をフェーズごとに、
   `code-review` を各フェーズで通す

### 完了 ——「確かめられた。動いたところで用済み」

1. `git mv docs/features/prototype/<doc> docs/features/`（**`completed/` への出口は直下からしか無い**）
2. `/harness-core:complete-feature`
3. **受け入れ基準の「やめる条件」の項目は、満たさなかったまま閉じてよい** ——
   あれは**やめるかどうかの判定条件**であって、達成すべき基準ではない。
   **完了ゲートでは「当たらなかった（＝続けてよかった）」と書いて通す。
   項目を消して通さない**（騙した記録が残らなくなる）

### 中断 ——「まだ分からない」

`docs/features/pending/` へ移す。**残作業台帳の行は残す**
（「やると決めたが着手しない」の意味に合う）。**何を待っているかを設計書に1行書く。**

### 破棄 ——「駄目だと分かった」

1. **先に、試作で分かったことを引き写す。** 残す先は、今後も従う判断なら
   **設計方針層**（`projectDocs.policy`）、そうでなければ**作業記録**。
   **「これは駄目だった」が残らないと同じ試作を繰り返す**
2. 設計書を消し、**残作業台帳の行も消す**
3. **コミット済み・push 済みの実装をどうするかは、ユーザーに確認する。**
   Step 4 でフェーズごとにコミットしてよいことにしてあるので、**試作のコードは履歴に入っている**
   （push していればリモートにもある）。**こちらで決めない** ——
   残す（後で使う可能性がある）・revert する・ブランチごと捨てる、のどれかをユーザーが選ぶ。
   **残すなら「試作の残骸である」と分かるようにする**（そうしないと
   `code-review` や `sync-check` が、誰も使っていないコードを毎回指摘する）

## 報告（Step 1 の直後に1回出す）

```
試作フローで進めます。

- 置き場: docs/features/prototype/yyyymmdd_<名前>.md
- 確かめたいこと: <Step 0 のもの>
- やめる条件: <Step 0 のもの>
- 本実装との違い: design-review tech は1回・code-review は最後に1回・
  レビュー前のコミット禁止は外す・機能設計書のステータス照合は対象外・
  push 前の検査（設計書同期台帳と全量照合）は警告になる
- 変えないもの: 設計書の厚み（L 相当）・design-review feature・動作確認・build-check・
  残作業台帳への1行（載せないと push が止まる）

次: Stage 1 を記入 → /harness-core:design-review feature → 承認
```
