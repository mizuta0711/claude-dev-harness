# 設計書 ↔ 実装 網羅的同期チェック（config 駆動）

`/harness-core:update-docs` が「変更駆動」で差分を反映するのに対し、
このスキルは「全量照合」で設計書と実装の乖離を検出する。

**実行タイミング**: **`/harness-core:pre-push-check` が push 前に自動で呼ぶ**（Step 3.5。
未プッシュコミットにソース変更が含まれる場合のみ）。ほかに手動で、フェーズ完了時・大規模リファクタリング後。

> ⚠️ **呼び出し側が範囲を絞ってはいけない。** 変更範囲に絞った照合は `/harness-core:update-docs` が
> 実装変更のたびに行っている。**絞った時点でこのスキルの存在理由（変更駆動では拾えない乖離の発見）が
> 消える。** 例外は `/harness-core:complete-feature` で、あれは機能単位の完了ゲートなので絞ってよい。

## Step 0: 設定の読み込み

`.claude/harness.config.json` の `designDocs.docs[]` が照合の対象一覧そのものになる。

| フィールド | 使い方 |
|-----------|--------|
| `file` | 照合する設計書 |
| `tracks` | 「何を追跡している文書か」＝照合の粒度を決める |
| `sources` | 実装側の探索範囲（glob） |

config が読めない場合は「設定不在のため網羅照合はできない」と報告し、
`docs/設計書/` 配下から推定した範囲だけを照合して、推定であることを明記する。

## Step 1: 各設計書の照合（docs[] を順に処理）

設計書ごとに以下を実施する:

1. `sources` の glob で実装側の実体を列挙する（ファイル一覧、公開シンボル一覧）
2. 設計書を読み、記載されている実体一覧を抽出する
3. 差分を3種類に分類する:
   - **実装にあるが設計書に無い** → 追加漏れ
   - **設計書にあるが実装に無い**（削除済み表記を除く） → 削除漏れ
   - **両方にあるが内容が食い違う**（シグネチャ・型・パス等） → 更新漏れ

### 効率化のルール（守ること）

- **全ファイルを読まない**。まず一覧同士を突き合わせ、**差分が出た対象だけ**中身を読む
- 公開シンボルの抽出は grep で一括取得する（言語ごとの `export` / `public` 等のパターン）
- 内部実装（非公開シンボル）は照合対象外。設計書に書くべきは公開境界のみ
- 自動生成される設計書は、生成コマンドを実行して差分を見る（手で比較しない）

## Step 2: 機能設計書のステータス照合

1. `docs/features/` 直下（`completed/` と `pending/` を除く）の設計書を対象にする
2. 🔵未実施 / 🟡実装中 のタスクが**実際には実装済みでないか**を確認する
   （タスクに書かれたファイル・シンボルが既に存在するか）
3. 全タスクが最終状態（✅/⏸️/❌）なのに `completed/` / `pending/` に移動されていないものを検出する
4. `completed/` 内に 🔵/🟡 が残っていないか（誤移動チェック）
5. Stage 1 の受け入れ基準チェックリストに、未チェックのまま完了扱いになっている項目が無いか

## Step 3: 残作業のタスク一覧への追記（converge）

照合で見つかった乖離のうち、「**設計書にもタスクにも無いが、実装として必要**」なものは
発見して終わりにせず、**機能設計書のタスク一覧に追記する提案**を行う:

| 発見の種類 | 提案する追記 |
|-----------|-------------|
| 実装済み・設計書未記載 | 設計書へ反映（✅完了 として逆追記） |
| 設計書あり・実装なし | 🔵未実施 のタスクとして追記（またはタスクの再オープン） |
| 設計と実装が食い違う | どちらが正かをユーザーに確認する「要判断」項目として提示 |

**追記は必ずユーザーに提示してから行う**（このスキルは黙って設計書を書き換えない）。

## Step 4: 結果報告

```
## 同期チェック結果

| # | 設計書 | 判定 | 乖離 |
|---|--------|------|------|
| 1 | {designDocs.docs[].file} | ✅ 同期済み / ⚠️ N件 | （追加漏れ/削除漏れ/更新漏れの内訳） |

### 機能設計書: ✅ 同期済み / ⚠️ N件の乖離
| ファイル | 問題 | 詳細 |
|---------|------|------|

### converge 提案: N件
| # | 種別 | 内容 | 反映先 |
|---|------|------|--------|

### 総合判定: ✅ 全て同期済み / ⚠️ 要修正 N件
```

## Step 5: 乖離の修正

1. 各設計書を修正する（改訂履歴も更新。**コミット列は `—`**。`(未確定)` と書かない
   — 埋め戻す機会が来ず永久に残る。ハッシュは `git log -- <file>` で常に引ける）
2. 修正内容をユーザーに報告し、確認を求める
3. 確認後コミット → `designDocs.ledger` に記録
