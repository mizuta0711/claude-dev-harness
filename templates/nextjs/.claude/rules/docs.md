# 設計ドキュメントの運用ルール

## 前提知識が無くても読めるように書く

**ドキュメントは、それ単体で理解できることが基本である**（前提を要求する文書は、冒頭でそう宣言する）。

**初出の語には、一般的な語義を当てて意味が通るかを確かめる。** 通らないなら、
その場で定義するか、一般的な語へ言い換える。

| やってはいけないこと | なぜ |
|---|---|
| 文脈から推測できるから、と未定義のまま使う | **推測は読み手の仕事ではない** |
| 何度も使ったから定着した用語だ、と扱う | **繰り返しは定義の代わりにならない** |
| 英語の技術語をそのまま訳して使う | 一般語義と食い違うと、読み手は毎回つまずく |

> **実測（2026-08-17）**: ある文書が `measurement window` を「**窓**」と14箇所で使っていた。
> 読み手の最初の反応は「**窓ってなに？**」。
> **`/harness-core:proofread-ja` を3モデルで走らせても1件も検出できなかった**
> （文脈から推測できてしまい、「統制された用語」と判断された）。
> **書く側で止めるしかない種類の不備。**

### 固有語を使うなら、用語集に載せる

プロジェクト固有の語（製品名・役割名・独自の概念）を使うなら、
**`.claude/rules/` の用語集に載せる**。載っていない語は、読み手からは一般語に見える。

- 用語集があるなら、**そこに無い語は一般語として通じるかを確かめる**
- 用語集が無いプロジェクトでは、**固有語を使わない**（使うなら用語集を作る）

**用語集を増やすときは `glossary-keeper` エージェントへ申請する。** 自分で追記しない。

| 申請に要るもの | なぜ |
|---|---|
| 語 / 説明（1〜2文） | 定義できない語は載せても伝わらない |
| 使用箇所 | **1箇所しか無いなら、その場で言い換えれば済む** |
| **一般語で言い換えるとどうなるか** | **書けるなら、多くはそちらで足りる** |

**却下されたら、その語は使わない。** `glossary-keeper` が代替の一般語を示す。

## 改訂履歴ルール

`docs/設計書/` および `docs/features/` 配下の設計ドキュメントには末尾に改訂履歴テーブルを設け、改訂時は必ず更新すること。

**改訂履歴のフォーマット:**
```
| 版数 | 日付 | コミット | 内容 | 担当 |
```
- コミット列には**トリガーとなった実装コミット**の短縮ハッシュ（7文字）を記入
- **書けないときは `—`。`(未確定)` と書かない**
  - 設計書は実装と**同じコミットに入る**ことが多く、**自分自身のハッシュは原理的に書けない**
  - `(未確定)` は「後で埋める」ように見えるが、埋め戻す機会が来ないため**永久に残る**
    （実測: 1プロジェクトで12ファイル34行）
  - **正確なハッシュは `git log -- <file>` で常に引ける。** 転記して腐らせない
- `/harness-core:update-docs` 実行時は `docs/設計書/.doc-sync.md`（台帳）にも同期記録を追記すること

## 機能設計書の運用ルール

- 新規機能開発時は `/harness-core:new-feature` で作成する（スキル同梱のテンプレートが使われる）
- 命名: `docs/features/yyyymmdd_機能名.md`（**作業中は `docs/features/` 直下**。`pending/` は一部保留の置き場）
- タスクステータス: 🔵未実施 / 🟡実装中 / ✅完了 / ⏸️保留（理由必須） / ❌却下（理由必須）
- 全タスク完了時はメタ情報のステータスを 🟢完了 に更新し、
  `/harness-core:complete-feature` で `docs/features/completed/` へ移動する
