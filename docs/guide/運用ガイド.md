# 運用ガイド — 使い分けと運用のコツ

| 項目 | 内容 |
|------|------|
| 対応ハーネス版 | harness-core 0.6.2 / harness-nextjs 0.3.1 / harness-unity 0.2.1 / harness-wpf 0.2.0 |
| 最終更新 | 2026-08-16 |
| 対象 | 一度フローを通した人。**日々の判断の基準**を置く |
| 前に読む | [入門ガイド](入門ガイド.md)（期待値調整とつまずきポイント） |

**構造の説明は図に委譲する。** このガイドは「どう判断するか」だけを扱う。

## 1. 全体構成（最小限）

ハーネスは**2層**でできている。

| 層 | 中身 | 更新のしかた |
|----|------|------------|
| **プラグイン層** | skills / agents / hooks | `/harness-core:plugin-update` → 再起動 |
| **テンプレート層** | `CLAUDE.md` / `constitution.md` / `.claude/rules/` / `harness.config.json` / 設計方針層の骨格 / `docs/` 骨格 | `/harness-core:harness-update` |

両者を結ぶのが **`.claude/harness.config.json`**。
core のスキルとフックは**環境を決め打たず、このファイルを読んで振る舞いを決める**。

→ 配置の全体像は [全体アーキテクチャ図](../diagrams/01_全体アーキテクチャ図.md)、
更新手順は [セットアップガイド §6](セットアップガイド.md)。

### 1-2. いつ追従するか（版の方針）

**層で分ける。** 追従のコストが層によって桁違いに違うためである。

| 層 | 方針 | 理由 |
|----|------|------|
| **プラグイン層** | **常に最新へ追従する** | `/harness-core:plugin-update` と再起動で済み、**判断が要らない**。バグ修正が即届く |
| **テンプレート層** | **区切りで追従する**（機能が一周した / フェーズ完了時） | 競合の統合に**人の判断が要る**。作業の途中に挟むと本業が止まる |

**実測（0.2.3 → 0.5.0 の追従）**: プラグイン層は判断ゼロ。
テンプレート層は適用2 / 保持1 / **競合4** で、競合はすべて統合で解決できたが**中身を読む判断が4回**要った。

**実測（0.5.0 → 0.6.0 の追従・設計方針層の導入を含む）**:

| プロジェクト | 分類 | 競合の中身 |
|---|---|---|
| 新規適用済みのもの | 適用4 / 見送り4 / 保持3 / **競合2** | `CLAUDE.md` と `constitution.md` のみ |
| 旧テンプレから移行済みのもの（設計方針層 4,558行） | 適用6 / 保持8 / **競合3** | 同上 + `harness.config.json` |

**設計方針層（`.claude/01_development_docs/` 等）の中身は追従対象外**なので、
何千行あっても競合には出てこない（`README.md` だけがテンプレ所有として追従する）。

> **見送った差分は再提案されない**（baseline が進むため「意図的に外した」とみなされる）。
> 実態と食い違うテンプレート（使っていないライブラリの規約など）は**見送ってよい**。
> **テンプレートは既定であって強制ではない。**

> **「面倒だから追従しない」を選ぶと、直したはずの欠陥がそのプロジェクトにだけ残る。**
> 上の追従では `tools/export-to-sql.ts` にバックアップの世代上限が入っており、
> 取り込まなければ `.bak` が無制限に溜まり続けていた。
> **テンプレート層の競合は「面倒」であって「危険」ではない**（無断で上書きされることはない）。

#### `autoUpdate` は使わない

**自分のタイミングで `/harness-core:plugin-update` を実行する。** プラグインは**セッション起動時に読み込まれる**ため、
自動で版が変わると「今このセッションが何を読んでいるか」が曖昧になる。
更新のタイミングを自分で握っていれば、**いつ何が変わったかを追える**。

#### 版を固定したい場合

安定運用を優先して版を止めることはできる（更新コマンドを打たなければよい）。ただし:

- **止めていることを文書に残す**（`CLAUDE.md` 等）。でないと「なぜ古いのか」が分からなくなる
- **セキュリティや fail-open に関わる修正は例外**として取り込む。CHANGELOG で判断する

## 2. スキルの使い分け

### 2-1. いつ呼ぶか

| スキル | 呼ぶ場面 | 呼ばなくてよい場面 |
|--------|---------|------------------|
| `new-feature` | **すべての作業の入口**（新規・改修・バグ修正） | 進行中の作業の続き |
| `design-review feature` | Stage 1 を書き終えたとき（L のみ） | M / S |
| `design-review tech` | Stage 2 を書き終えたとき（L のみ） | M は任意 |
| `code-review` | 実装が一区切りしたとき（M / L） | S |
| `build-check` | **区切りごと**。フックを当てにせず自分から回す | — |
| `update-docs` | コミット前（M / L） | S |
| `sync-check` | フェーズ完了時・push 前。**全量照合** | 毎回 |
| `complete-feature` | 機能が完了したとき（**受け入れ基準**と**設計方針への書き戻し**のゲート） | 途中 |
| `pre-push-check` | **push の直前** | リモートが無いプロジェクト |
| `done` | 作業の締め | — |
| `harness-update` | ハーネスのテンプレート層が新しくなったとき | プラグイン更新だけのとき |
| `proofread-ja` | 文書を書き終えた区切り・外部に出す文書を作ったとき | **毎回のコミット**（差分レビューの負担に見合わない） |

環境固有のスキル（`browser-test` / `unity-verify` / `capture-screenshots`）は §7 を参照。

### 2-2. 迷いやすい組み合わせ

| 迷い | 判断 |
|------|------|
| `update-docs` と `sync-check` の違い | **変更駆動** vs **全量照合**。日常は `update-docs`、区切りで `sync-check` |
| `code-review` と `design-review` | **実装を見る** vs **設計書を見る**。設計が固まる前にコードを見ても意味がない |
| `build-check` と コミット前フック | **同じチェックを別のタイミングで**回す。フックは最後の砦であって、日常の確認手段ではない |
| `complete-feature` と `done` | **機能の完了処理**（設計書を `completed/` へ）vs **作業の完了報告**（毎回） |

> **`new-feature` は「新規機能」専用ではない。** 改修もバグ修正もここから入る。
> 規模判定を通すのが目的なので、入口を1つに保つ。

## 3. 規模判定 S/M/L の選び方

### 3-1. 判定の軸

| 観点 | S | M | L |
|------|---|---|---|
| 変更ファイル数 | 1〜2 | 3〜10 | 10超 または広範囲 |
| 新規インターフェース | なし | 既存パターンに沿った1〜2 | 新パターン or 複数 |
| データ構造・永続化 | 変更なし | 後方互換のある追加のみ | 新規・破壊的変更 |
| UX 変更 | なし | 限定的（1画面内） | 複数画面・フロー全体 |
| 設計書更新 | 不要 | 必要 | 必要（複数種類） |

**判定ルールは3つだけ:**

1. 該当が多い規模を採る
2. **1つでも L 相当があれば L に引き上げる**
3. **UX 変更を含めば自動的に L**

### 3-2. 運用上の注意

| 注意 | 理由 |
|------|------|
| **迷ったら L 寄りで出す** | AI は楽な方（S 寄り）に倒れやすい。過小見積もりの方が痛い |
| **規模を偽って測らない** | 「軽いフローを試したいから M にする」は自己汚染。実態で判定する |
| **途中で膨らんだら再判定** | フェーズ実行中なら**現フェーズを完了させてから**提案する。破壊的変更と分かったら**即停止** |

→ 承認ゲートと戻り経路は [開発フロー図](../diagrams/02_開発フロー図.md)。

### 3-3. 保留したスコープを次の周回で再開するとき

段階リリースでは「1周目 / 2周目」に分けることがある。**再開専用のスキルは無い**ので、
`new-feature` の規模判定から入り、**既存設計書の続き**として扱う。

**Stage 1 が承認済みなら再利用してよい**（`design-review feature` を丸ごと省ける）。
そのためには**1周目の時点で受け皿を書いておく**のが要点:

- 「2周目（保留）」節
- 2周目分の受け入れ基準
- 「2周目の確認項目はここへ追加する」の但し書き

これが無いと、再開のたびに設計をやり直すことになる。

## 4. サブエージェントの扱い

**文脈が分かれるのはサブエージェントだけ**（スキルはメインの文脈で動く）。
違いは [役割比較図](../diagrams/03_役割比較図.md)、起動の実際は [スキル実行シーケンス図](../diagrams/04_スキル実行シーケンス図.md) を参照。

| 原則 | 理由 |
|------|------|
| **結果は必ずメインで差分確認してからコミットする** | 返るのは要約だけ。**ビルド成功 ≠ 正しい実装** |
| **詳細を残したければファイルに書かせる** | 会話の文脈は消えるが、ファイルは残る |
| **並列レビューの指摘が食い違ったら自動解決しない** | 技術制約 vs 体験要求の衝突は**人が決める**（「要判断」として明示される） |

## 5. フックの挙動

### 5-1. 何が自動で走るか

| フック | タイミング | 止められるか |
|-------|-----------|------------|
| `pre-commit-check` | コミット前 | ✅ ブロックする |
| `pre-migrate-backup`（nextjs） | DB マイグレーション前 | ✅ ブロックする（**バックアップ対象を判定できない場合は警告して通す**） |
| `post-edit-lint`（nextjs） | ファイル編集後 | ❌ 通知のみ（自動修正は行う） |
| `post-commit-doc-check` | コミット後 | ❌ 通知のみ |
| `session-start-context` / `pre-compact-save` / `subagent-stop-diff` | セッション境界 | ❌ 通知のみ |

→ 発火順序と fail-open の経路は [フック発火タイミング図](../diagrams/05_フック発火タイミング図.md)。

### 5-2. 待ち時間（実測）

| フック | 上乗せ | 頻度 | 実用性 |
|-------|-------|------|-------|
| `post-edit-lint` | **約2.6秒/編集**（改善前は約4.2秒） | ファイル編集のたび | ⚠️ **固定費が約2.5秒残る**。十数ファイル触ると分単位で積み上がる |
| `pre-migrate-backup` | 約1.2秒 | migrate のとき | ✅ 気にならない |

> **`post-edit-lint` の固定費は ESLint の起動コストで、対象が1ファイルでも変わらない。**
> 「編集の反応がなぜか遅い」と感じたらこれ。**無言で待たされる**ため原因が分かりにくい。

### 5-3. 通知は画面に出る（SubagentStop だけ例外）

フックの通知は **`systemMessage`（ユーザーの画面）と `additionalContext`（Claude の文脈）の
2経路とも出す**。フックが何か言えば**画面にも出る**。

| イベント | 画面に出るか |
|---------|------------|
| SessionStart / PreToolUse / PostToolUse | ✅ 出る |
| **SubagentStop** | ❌ **出ない。** 通知経路が無いため、記録だけ残してコミット時に合流させる |

> **サブエージェントが動いたあとにコミットしようとすると、
> 「`git diff` で確認してからコミットすること」という注意が出る。** これが SubagentStop の代替。
> コミットがブロックされた場合、注意は**次の試行でも出る**（コミットが成立していないため）。

**「何も出ない＝動いていない」ではない。** フックは設定が無ければ黙って素通りする（§5-4）ので、
出ないときはまず config を疑う。確認したいときは**副作用を見る**
（バックアップが増えたか、コミットがブロックされたか）。

> **実務上の対策**: **区切りで `/harness-core:build-check` を自分から回す。**
> 編集後 lint は**編集した1ファイルの指摘しか出さない**ため、他ファイルへ波及した壊れ方は拾えない。

### 5-4. 設定が無ければ黙って素通りする（fail-open）

`.claude/harness.config.json` が無い・壊れている・コマンド未定義のとき、フックは `exit 0` で通過する。
**エラーにならない代わりに、何も検査していない状態になる。**
「入れたのに効かない」と感じたら、まず config を見る。

### 5-5. バックアップの世代

`pre-migrate-backup` が作るバックアップは、**新しい方から 10 世代だけ残して古い世代を自動で削除する**。
実 migrate のたびに1世代増えるため、上限が無いと溜まり続けるための措置（`.gitignore` 済みで git は刈らない）。

- 世代数は `tools/export-to-sql.ts` の `BACKUP_GENERATIONS` で変えられる。`0` 以下にすると掃除しない
- 削除したファイルは実行時のログに必ず出る。**黙って消えることはない**
- SQLite の `-wal` / `-shm` は本体の付随物なので、**世代としては数えず本体と一緒に**消える

> **10 世代は「直前の migrate に戻す」用途を満たすための数**であって、長期保存の仕組みではない。
> 消えて困るデータは、正式なバックアップ運用に載せること。

## 6. 設計書の運用

### 6-1. 3種類の文書を混ぜない

| 場所 | 役割 | 性質 |
|------|------|------|
| `docs/features/` | **機能設計書**（これから作るもの / 作ったときの判断） | 機能ごとに1ファイル |
| `docs/設計書/` | **実態**（API一覧・ER図など。今のコードの姿） | コードと同期し続ける |
| `docs/reviews/` | **レビュー結果の記録** | 追記のみ。手順書は置かない |

### 6-2. 機能設計書のライフサイクル

```
new-feature で docs/features/ 直下に作成 → 直下に置いたまま実装
  → 全タスク完了 → complete-feature
  → 🟢完了 は completed/ へ、⏸️一部保留 は pending/ へ
```

**作業中は必ず `docs/features/` 直下に置く。** `pending/` は保留の置き場であって作業場所ではない
（フックとスキルは直下しか見ない）。

### 6-3. 台帳（`.doc-sync.md`）の運用

`update-docs` が設計書を更新したとき、**コミットハッシュ単位で台帳に記録**する。
`pre-push-check` はこれを見て、未記録のコミットがあれば push を止める。

**記録が要るのは「ソース変更を含むコミット」だけ。**
`pre-push-check` は照合の前に `paths.source` で判定し、一致しないコミットは SKIP する（実測）。

> ⚠️ **台帳ファイル自身の説明文は、これより厳しく読める書き方になっている**
> （「無記録は許さない」）。**実挙動はスキル側が正**。
> 説明どおりに全コミットを律儀に記録しようとすると手間だけが増える。

### 6-4. 改訂履歴のコミットハッシュは後から埋める

`update-docs` は**コミット前**に走るのに、改訂履歴は**コミットハッシュ**を求める。
順序が逆なので、**`(未確定)` と書いてからコミット後に埋め直す**一手が必要になる。

**この一手はフローに定義されていない。** 忘れると `(未確定)` が残り続けるので、
`done` の前に埋めるのを習慣にする。

### 7-1. nextjs

| 項目 | 内容 |

| 項目 | 内容 |

## 8. 実運用の落とし穴

| 落とし穴 | 対策 |
|---------|------|
| **「省略せずに全部書いて」は守られない** | 分量で指示せず、**成果物の形**（表の列・節構成）で指定する |
| **サブエージェントの結果を過信する** | 必ずメインで差分確認。要約だけで判断しない |
| **設計書と実装が静かにずれる** | `update-docs` を毎回、`sync-check` を区切りで。**ずれは自然に起きる**前提で仕組みに任せる |
| **同じ情報を2箇所に書く** | 方針は `.claude/`、実態は `docs/設計書/`。**どちらが正か**を決めてから書く |
| **`CLAUDE.md` が肥大化する** | 追記前に「これは方針か実態か」を自問。300行を超えたら整理 |
| **規模が過小評価される** | 判定は AI 推測 → **人が承認**。承認の場で疑う |
| **安全のための禁止が、正しい手順を塞ぐ** | 止められた側に**出口があるか**を見る。出口の無い停止はローカル改変を強いる |
| **ハーネスの不便をプロジェクト側で直す** | 直さない。メモに残して**コアへ還元**する（→ [改善還元フロー図](../diagrams/06_改善還元フロー図.md)） |
