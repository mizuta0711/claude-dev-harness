| 項目 | 内容 |

## 0. 全体像

| Step | やること | 所要 | 飛ばすとどうなるか |
|------|---------|------|------------------|
| 1 | `create-project.mjs` でプロジェクトを生成する | 1分 | — |
| 2 | **`claude plugin install` でプラグインを導入する（★必須）** | 1分 | **スキルも hooks も一切動かない** |
| 3 | `/plugin` と `/` で導入を確認する | 30秒 | 動いていないことに気づかないまま進む |
| 4 | 環境ごとの追加セットアップ（§4） | 環境による | 環境固有スキルが使えない |
| 5 | `/harness-core:new-feature` で最初の機能を始める | — | — |

> **Step 2 が最大の落とし穴。** `.claude/settings.json` に設定が書かれているため
> 「起動すれば自動で入る」と思いやすいが、**入らない**（§2-1 に実測結果）。

導入後の**更新手順は §6**。なぜその手順なのか（変更が届くまでの全体像）は
[改善還元フロー図](../diagrams/06_改善還元フロー図.md) にあるので、ここでは繰り返さない。

## 1. プロジェクトを生成する

### 1-1. 必要なもの

| もの | 用途 |
|------|------|
| Node.js | `create-project.mjs`（ESM の Node スクリプト）の実行 |
| git | 生成先の初期化。ハーネス本体の取得 |
| Claude Code | 本体。プラグインの導入・実行 |

ハーネスは **public リポジトリ**なので、認証もトークンも要らない。

### 1-2. 生成する

```bash
git clone https://github.com/mizuta0711/claude-dev-harness.git
cd claude-dev-harness
node tools/create-project.mjs --env <nextjs|unity|wpf> --dest ../MyProject
```

- プロジェクト名などのプレースホルダは**対話で尋ねられる**（`--set KEY=VALUE` で先に渡すこともできる）
- **`--dry-run`** を付けると、生成予定のファイル一覧と置換内容を表示するだけで何も書き込まない。
  初回は一度これを見ておくとよい
- 生成先が git リポジトリでなければ `git init` まで行う

生成物は `templates/base` と `templates/<env>` の合成結果で、
`.claude/settings.json` / `.claude/harness.config.json` / `CLAUDE.md` / `constitution.md` /
`docs/` の骨格が入った状態になる。

> **環境ごとに要求されるプレースホルダが違う**（wpf は `CORE_PROJECT` / `UI_PROJECT` も尋ねる）。
> 宣言は `templates/<env>/template.json` にある。

## 2. プラグインを導入する（★必須）

生成先へ移動して、**一度だけ**実行する。

```bash
cd ../MyProject
claude plugin install harness-core@dev-harness   --scope project
claude plugin install harness-nextjs@dev-harness --scope project   # 環境に応じて unity / wpf
```

**`claude plugin marketplace add` は不要。** `.claude/settings.json` の
`extraKnownMarketplaces` が初回起動で marketplace の登録とクローンを自動で済ませる。

> ⚠️ **`--scope project` を省略しない。** 既定は `user` スコープだが、
> `enabledPlugins` によって `project` スコープの登録が**どのみち自動で作られる**ため、
> 省略すると**両方に登録が残り、更新のたびに両方へ当てる羽目になる**（§6-1）。
> 最初から `project` だけにしておけば、更新は1回で済む。

### 2-1. なぜ手動導入が必要か（実測）

`.claude/settings.json` には2つの設定が書かれているが、**役割が違う**。

| 設定 | 実際の効果 |
|------|-----------|
| `extraKnownMarketplaces` | ✅ 初回起動で marketplace の**登録とクローンまで**を自動で行う。ダイアログも出ない |
| `enabledPlugins` | ⚠️ **初回起動ではプラグインが導入されなかった**。2回目以降の起動で project スコープの導入が自動記録された |

`enabledPlugins` は「導入済みのプラグインを有効にする」設定であって、**導入そのものは行わない**
（少なくとも初回起動では行われない）。この状態ではスキルも hooks も存在しないため、
`/harness-core:new-feature` は候補にすら出ない。

> 2回目以降の自動導入が「クローン完了後なら自動で入る」ためか
> 「CLI 導入済みのものが project スコープへ登録されただけ」かは切り分けられていない。
> **CLI 導入を明示すればどちらでも確実に動く**ため、上の手順を正とする。

## 3. 導入を確認する

Claude Code を起動して、次の2つで確認する。

```bash
claude
```

| 確認方法 | 見るもの |
|---------|---------|
| **`/plugin`** | `harness-core` と環境プラグインが **enabled** になっていること、**バージョン**が期待どおりであること |
| **`/`** | スキル一覧に `harness-core:new-feature` が出ること |

### 3-1. 起動時の1行でも分かる（harness-core 0.5.0 以降）

SessionStart フックは**画面に1行だけ**出す。

```
[harness] nextjs / config OK          ← 載っている
[harness] ⚠️ .claude/harness.config.json が見つかりません   ← 載っているが設定が無い
（何も出ない）                          ← プラグインが導入できていない
```

状況の詳細（ブランチ・未プッシュ数・進行中の設計書）は `additionalContext` で
**Claude にだけ**渡している。人が毎回読むものではないため画面には出さない。

### 3-2. VS Code の拡張パネルではスキルが解決しない

**確認とスキルの実行はターミナル（CLI）で行う。**

VS Code の Claude Code **拡張パネル**では、`/harness-core:...` が
**`No matching commands`** になる（統合ターミナルの CLI では解決する）。

**これは導入の失敗ではない。**「パネルで出ない＝入っていない」と誤診しないこと。
実測での切り分け:

| 確認したもの | 結果 |
|---|---|
| `installed_plugins.json`（スコープ・版・パス） | 正しい |
| marketplace クローン / キャッシュ | スキルは存在する |
| セッション再起動 / プラグインのトグル / ワークスペースルート | いずれも問題なし |
| **統合ターミナルの CLI** | **解決する** |

同じマシン・同じプロジェクト・同じ `~/.claude` で結果が割れるため、**クライアント側の機能差**である。

**パネルで作業したい場合でもスキルは使える。** エージェントに
「`<スキル名>` を実行して」と依頼すれば、`CLAUDE.md` の
「スラッシュコマンドが解決しない環境での実行」の手順に従い、
**`SKILL.md` を直接読んで実行する**（harness-core 0.6.3 以降）。

> **確認は `/plugin` と `/` を正とする。** 起動時の1行は補助であり、
> 「出ない＝導入できていない」は言えても「出た＝すべて正常」までは言えない
> （バージョンが古いままの可能性がある）。
>
> ⚠️ **0.4.0 以前はこの行が出なかった。** 当時は「起動メッセージで判断しない」が正しく、
> その前提で書かれた手順書が残っている可能性がある。

## 4. 環境ごとの追加セットアップ

共通部はここまで。以降は**選んだ環境の節だけ**を読めばよい。

### 4-1. nextjs

| 項目 | 内容 |
|------|------|
| 追加プラグイン | `harness-nextjs@dev-harness`（`browser-test` スキル / `browser-tester`・`product-advisor` エージェント / `post-edit-lint`・`pre-migrate-backup` フック） |
| MCP | `.mcp.json` に **Playwright MCP** が登録済み。`/harness-nextjs:browser-test` が使う |
| フレームワークの初期化 | Next.js 自体の足場は**生成物に含まれない**。`create-next-app` を使う場合は**非空ディレクトリで失敗する**ことと、生成される `CLAUDE.md` / `AGENTS.md` がハーネスの `CLAUDE.md` を壊しうる点に注意する |
| DB | Prisma 前提の `harness.config.json`（`schema.prisma` の変更で `テーブル定義書.md` / `ER図.md` の更新を促す） |

> `.env` は `.claude/settings.json` の deny で保護されている。
> Prisma が `DATABASE_URL` を要求するため、初期化時にここへ触れる必要が出る場面がある。

### 4-2. unity

生成物に **`SETUP.md`** が含まれる。**そちらが正**なので必ず読むこと。要点だけ:

| 項目 | 内容 |
|------|------|
| 追加プラグイン | `harness-unity@dev-harness`（`unity-verify` スキル / `game-designer` エージェント / `pre-commit-cs-check` フック） |
| MCP | [MCP For Unity](https://github.com/CoplayDev/unity-mcp) を `.mcp.json`（プロジェクトスコープ）で登録済み |
| ユーザー側の操作 | Unity Editor で **Window > MCP For Unity** を開き Local Server を起動する。パッケージ解決を待つ。読み込ませるために VS Code の再起動が要る |
| プレースホルダ | `PROJECT_NAME` は **C# の root namespace を兼ねる** |

### 4-3. wpf

| 項目 | 内容 |
|------|------|
| 追加プラグイン | `harness-wpf@dev-harness`（`capture-screenshots` スキル / `product-advisor` エージェント。フックなし） |
| MCP | なし。スクリーンショットは UIAutomation で撮る |
| プレースホルダ | `PROJECT_NAME` / `PROJECT_DESCRIPTION` に加え **`CORE_PROJECT` / `UI_PROJECT`**（既定値は `<PROJECT_NAME>.Core` 等） |

## 5. 最初の機能を始める

```
/harness-core:new-feature <機能名>
```

**すべての作業（新規機能・改修・バグ修正）は規模判定 S/M/L から始める。**
判定は「AI が推測 → ユーザーが承認」の2ステップで、**UX 変更を含むものは自動的に L**。

| 規模 | フロー |
|------|--------|
| S | 実装 → `build-check` → コミット → `done` |
| M | 設計 → 実装 → `code-review` → 動作確認 → `build-check` → `update-docs` → コミット → `done` |
| L | Stage 1 設計 → `design-review feature` → **ユーザー承認** → Stage 2 設計 → `design-review tech` → 実装 →（以降 M と同じ） |

生成直後は `CLAUDE.md` に `<!-- TODO -->` が残っている。**プロジェクト概要だけは先に埋める**
（設計時に AI が読む前提の情報のため）。

## 6. ハーネスを更新する

ハーネスが新しくなったとき、プロジェクト側で取り込む手順。
**2層それぞれに別の操作が要る**（プラグイン層とテンプレート層は配信経路が違うため）。

> **いつ追従するか**（プラグイン層は常に最新 / テンプレート層は区切りで / `autoUpdate` は使わない）は
> [運用ガイド §1-2](運用ガイド.md) にある。ここは**手順**だけを扱う。

### 6-1. プラグイン層を更新する（skills / agents / hooks）

**スキルに任せるのが確実。**

```
/harness-core:plugin-update
```

導入済みのプラグインと**そのスコープ**を自動で特定して更新し、
**更新前後の版を表で報告**する。あなたがやるのは**再起動だけ**。

<details>
<summary>手で打つ場合</summary>

```bash
claude plugin marketplace update dev-harness                       # カタログを最新にする
claude plugin update harness-core@dev-harness   --scope project
claude plugin update harness-nextjs@dev-harness --scope project    # 環境プラグインも同様に
```

</details>

そのあと **Claude Code を再起動する**（`/exit` して開き直す）。セッション中には反映されない。

| 手順 | 忘れるとどうなるか |
|------|------------------|
| `--scope project` | **`not installed at scope user` で失敗する**か、既定の `user` 側だけが新しくなり、**セッションが読むのは古い方のまま**になる。`plugin-update` スキルはこれを自動で合わせる |
| 再起動 | プラグインはセッション起動時に読まれるため、**更新が効かないまま作業を続けることになる** |
| 確認（`/plugin`） | 更新できたつもりで古い版のまま進む |

> **プラグイン層とテンプレート層は別。** `plugin-update` が運ぶのは skills / agents / hooks だけで、
> `CLAUDE.md` / `.claude/rules/` / `harness.config.json` は届かない。
> そちらは**再起動してから** §6-2 の `/harness-core:harness-update` で追従させる。

更新後は `/plugin` で**バージョン表示**を確認する。スコープごとの版を厳密に見るなら
（`plugin-update` は同じ内容を自動で報告する）:

```bash
node ~/.claude/plugins/marketplaces/dev-harness/plugins/harness-core/skills/plugin-update/scripts/plugin-versions.mjs
```

#### スコープは `project` だけにしておく

**`user` スコープの登録は捨ててよい。** `project` 側は `enabledPlugins` によって
セッション起動時に自動生成されるため消しても復活するが、`user` 側は自分で入れない限り増えない。
両方持つと更新が「プラグイン数 × スコープ数」になり、**実際に3回連続で当て漏れが起きた**。

既に `user` に入れてしまっている場合、一度だけ移行する:

```bash
claude plugin uninstall harness-core@dev-harness   --scope user
claude plugin uninstall harness-nextjs@dev-harness --scope user
#    → /exit して再起動（project 側は enabledPlugins が作り直す）
```

上のワンライナーで **`user` の行が消えていること**を確認する。

> `user` スコープの利点（全プロジェクト共通で1回入れれば済む）は**そもそも効いていない**。
> `enabledPlugins` があっても初回起動では導入されず、結局プロジェクトごとに
> `claude plugin install` が要るため（§2-1 の実測）。

> **`already at the latest version` と出て何も起きない場合**、ハーネス側で**版番号が上がっていない**。
> 利用側では対処できないので、ハーネスを直した人に版を上げてもらう
> （[改善還元フロー図](../diagrams/06_改善還元フロー図.md) の関門1）。

### 6-2. テンプレート層を更新する（CLAUDE.md / rules / config / docs 骨格）

```
/harness-core:harness-update
```

プラグインの更新では**この層は届かない**。スキルが3点比較で差分を分類し、
**承認したものだけ**を適用する。

| 分類 | 意味 | 既定の扱い |
|------|------|-----------|
| `template-improvement` | テンプレート側だけが変わった | 適用を提案 |
| `project-local` | プロジェクト側だけが変わった | **保持**（触らない） |
| `already-applied` | 同じ変更が既に入っている | 対応不要 |
| `conflict` | 両方が同じファイルを変更した | **ユーザー判断が必須** |
| `template-removed` | テンプレートから消えたファイル | 削除するか残すかを判断 |

> **「競合」は失敗ではない。** ローカル改変を無断で上書きしないための分類であり、
> 出るのが正常。テンプレートの改善と自分の改変を**統合して**解決すればよい
> （統合した結果はテンプレートと一致しないが、それで「解決」と判定される）。

### 6-3. どちらを更新すべきか分からないとき

両方やってよい。順序も問わない。**片方だけでは中途半端になる**ことだけ意識する。

| 症状 | 更新すべき層 |
|------|------------|
| スキルの手順・エージェント・フックの挙動が古い | プラグイン層（§6-1） |
| `CLAUDE.md` / `constitution.md` / `.claude/rules/` / `harness.config.json` が古い | テンプレート層（§6-2） |

## 7. 既存プロジェクトへ後から導入する

> ✅ **1本で実測済み**（`skillup_mock` / nextjs・2026-08-15）。
> **エージェントにそのまま渡せる手順書**を用意してある:
> **[既存プロジェクト移行指示書](既存プロジェクト移行指示書.md)**
>
> この節は「何が起きるか」の概要。**実際に移行するときは指示書の方を使う**
> （ローカル資産の仕分け方・改変の移送先・踏んだ落とし穴が入っている）。
> 未実測なのは **unity / wpf 環境**のみ。

### 7-1. 何を入れることになるか

ハーネスは**2層**でできており、既存プロジェクトでは**それぞれ別に**入れる必要がある。

| 層 | 中身 | 入れ方 |
|----|------|--------|
| **プラグイン層** | skills / agents / hooks | `claude plugin install`（新規と同じ） |
| **テンプレート層** | `CLAUDE.md` / `constitution.md` / `.claude/rules/` / **`.claude/harness.config.json`** / 設計方針層の骨格 / `docs/` 骨格 | **手で置く**（既存ファイルとの統合が要るため自動化されていない） |

> **`.claude/harness.config.json` が要（かなめ）。** core の hooks / skills は**すべてこのファイルを読んで動く**ため、
> 無いと **fail-open で全部素通り**する。プラグインだけ入れても「入れたのに何も起きない」状態になる。

### 7-2. 手順

**Step 1 — 一時ディレクトリに「あるべき姿」を生成する**

既存プロジェクトの名前に合わせて生成し、**移植元**として使う。

```bash
node tools/create-project.mjs --env <nextjs|unity|wpf> --dest /tmp/harness-ref \
  --set PROJECT_NAME=<既存の名前> --set PROJECT_DESCRIPTION="..."
```

**Step 2 — `.claude/settings.json` に marketplace 設定を足す**

生成物の `extraKnownMarketplaces` / `enabledPlugins` を既存の `settings.json` へマージする
（[README のスニペット](../../README.md#プロジェクトからの利用marketplace-経由)と同じ内容）。
`permissions` は既存の設定を壊しうるので、[permissionsベースライン.md](../permissionsベースライン.md) を読んでから判断する。

**Step 3 — プラグインを導入する**

§2 と同じ。`claude plugin install` は必須。

**Step 4 — `.claude/harness.config.json` を実プロジェクトに合わせる**

生成物からコピーし、**実際のプロジェクトに合わせて直す**。ここを既定値のままにすると誤検知が続く。

| キー | 合わせるもの |
|------|------------|
| `commands` | 実際のビルド・型チェック・lint・テストのコマンド（無いものは `null`） |
| `gates.preCommit` | コミット前に必ず通すもの。**最初は軽いものだけにする**（重いと毎回のコミットが詰まる） |
| `paths.source` / `paths.docTriggers` | 実際のディレクトリ構成 |
| `designDocs` | 既存の設計書がある場合はその配置に合わせる。無ければ骨格ごと移植する |

仕様は [harness設定契約.md](../harness設定契約.md)。

**Step 5 — テンプレート層の残りを統合する**

`CLAUDE.md` / `constitution.md` / `.claude/rules/` / `.claude/01_development_docs/` 骨格 / `docs/` 骨格を移植する。
**既存の `CLAUDE.md` は上書きせず統合する**（既存プロジェクトの文脈の方が価値が高い）。
既に設計方針の文書を持っているプロジェクトは、それを残したまま `projectDocs` に登録する
（詳細は [既存プロジェクト移行指示書](既存プロジェクト移行指示書.md)）。

**Step 6 — 確認する**

§3 と同じ（`/plugin` と `/`）。加えて、`/harness-core:build-check` が通るかで
`commands` の設定が実態に合っているかを確かめる。

### 7-3. 既知の落とし穴

| 落とし穴 | 対処 |
|---------|------|
| **プロジェクト側の `.claude/hooks/` とプラグインの hooks が二重に走る** | 既存の hooks を無効化するか、役割が重ならないよう整理する。**同じチェックが2回走ると原因が分かりにくい** |
| **`/harness-core:harness-update` の差分が全て「競合」になる** | `.claude/harness-baseline.json` が無いため**2点比較**にしかならない（安全側に倒している）。`--set` で当時のプレースホルダ値を渡すと差分が減る |
| **スキルの呼び名が変わる** | 素の `/code-review` は Claude Code 組み込みが起動する。プロジェクト内の文書が旧名を参照していれば `/harness-core:*` へ書き換える |
| **既存の `permissions` と衝突する** | `deny` は「今回だけ許可」ができない層。厳しすぎると迂回を誘発する（実例が [permissionsベースライン.md](../permissionsベースライン.md) にある） |

> **迷ったら新規生成に寄せる。** 新しく生成したプロジェクトへ既存のソースを移す方が、
> 後付けより切り分けが容易な場面は多い。

## 8. 取り外す（アンインストール）

「合わなかったので外す」「一時的に無効にしたい」ときの手順。**壊れる操作ではない**が、
テンプレート層のファイルは**プロジェクトの資産として残る**点に注意する。

### 8-1. 一時的に止めるだけなら

`.claude/settings.json` の `enabledPlugins` を `false` にして**再起動**する。導入自体は残る。

```json
{ "enabledPlugins": { "harness-core@dev-harness": false } }
```

### 8-2. 完全に外す

```bash
claude plugin uninstall harness-core@dev-harness   --scope project
claude plugin uninstall harness-nextjs@dev-harness --scope project   # 入れた環境プラグイン
```

`user` スコープにも入れていた時期がある場合は、`--scope user` でも同じことを行う
（登録はスコープごとに独立しているため、片方を消しても残る）。

そのうえで **`.claude/settings.json` から `enabledPlugins` の記述を消す**。
消さないと、**次回のセッション起動時に project スコープの登録が作り直される**
（`enabledPlugins` は起動時に登録を作るため。§2-1 の実測と同じ挙動）。

marketplace の登録も消す場合:

```bash
claude plugin marketplace remove dev-harness
```

> ⚠️ marketplace と user スコープの導入は**他プロジェクトと共有**している。
> 他でもハーネスを使っているなら `marketplace remove` はしないこと。
>
> 外し残しの確認は、[改善還元フロー図](../diagrams/06_改善還元フロー図.md) の
> 「関門4 の確認」に載せたワンライナーで `installed_plugins.json` を見るのが確実
> （スコープごとに登録が分かれているため、片方だけ残ることがある）。

### 8-3. 外しても残るもの

| 残るもの | 扱い |
|---------|------|
| `CLAUDE.md` / `constitution.md` / `.claude/rules/` / `.claude/harness.config.json` | **プロジェクトのファイル**。不要なら手で消す。`harness.config.json` は残っていても、プラグインが無ければ誰も読まない |
| `docs/features/` / `docs/reviews/` / `docs/設計書/` | **成果物**。消さないこと。ハーネスの有無と無関係に価値がある |
| `.claude/statusline.js` | テンプレート由来。不要なら `settings.json` の参照ごと消す |

## 9. よくある失敗

| 症状 | 原因 | 対処 |
|------|------|------|
| **`/` にスキルが出ない**（`harness-core:new-feature` が無い） | Step 2 を飛ばした。`enabledPlugins` だけでは導入されない | `claude plugin install` を実行 → **再起動** |
| **起動しても `[harness] ...` が表示されない** | **harness-core 0.5.0 以降は1行だけ画面に出る。** 出ないなら導入できていないか、config が読めていない | `/plugin` と `/` で確認する。それでも出なければ `.claude/harness.config.json` の有無を見る |
| **プラグインを更新したのに古いまま** | セッション中は反映されない | **再起動**する（＝ `/exit` して `claude` を起動し直すこと） |
| **`plugin update` したのに古い版が読まれる** | 既定では `user` スコープしか更新されない。`project` スコープにも登録がある | `--scope project` を付けてもう一度当てる。**そのうえで `user` 側を捨てる**（§6-1） |
| **`plugin update` が `already at the latest version` と言う** | ハーネス側で**版番号を上げずに push** した | ハーネス側で版を上げ直す（[改善還元フロー図](../diagrams/06_改善還元フロー図.md) の関門1） |
| **`/plugin` に同じプラグインが何行も並ぶ** | Windows でドライブレターの大小（`D:` / `d:`）が別プロジェクト扱いになり `project` スコープが重複した。**起動元のシェルで表記が変わる** | `claude` の起動元を1つに揃える。古い登録は `installed_plugins.json` から削除してよい（次回起動時に作り直される） |
| **`CLAUDE.md` や `.claude/rules/` が新しくならない** | テンプレート層はプラグインとは**配信経路が別** | `/harness-core:harness-update` を実行する |
| **`harness-update` で「競合」が出た** | 異常ではなく**設計どおり**。ローカル改変を無断で上書きしないための分類 | 内容を統合して適用する。統合すれば解決と判定される |
| **build-check が初回から失敗する** | 環境側の初期化が未了（依存未インストール等） | 先にフレームワークの初期化を済ませる（§4） |
