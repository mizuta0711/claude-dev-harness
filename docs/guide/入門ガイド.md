## 1. 期待値をそろえる

### 1-1. このハーネスが解こうとしている問題

AI に任せると速い。**ただし放っておくと必ず次の3つが起きる。**

| 起きること | ハーネスの対処 |
|-----------|--------------|
| 動くけれど**意図と違うもの**ができる | 実装前に設計を確定させ、**人が承認するゲート**を置く |
| 動いたあと、**コードと設計書がずれていく** | 変更駆動（`update-docs`）と全量照合（`sync-check`）の二層で同期する |
| **同じ失敗を繰り返す** | 手順をスキルに、強制をフックに置き、人の記憶に依存させない |

**「速く書く」ためではなく、「速く書いても壊れない」ためのものだと考えるとよい。**

### 1-2. 期待していいこと / してはいけないこと

| ✅ 期待していい | ❌ 期待してはいけない |
|--------------|-------------------|
| 設計書を書けば、実装の大半は任せられる | **仕様を言わなくても察してくれる**こと |
| ビルド・型チェックの失敗はコミット前に止まる | **ビルドが通れば正しい**こと（→ §2-2） |
| 「なぜその設計にしたか」が文書に残る | レビューを読まずに承認しても大丈夫なこと |
| 小さな変更は軽いフローで済む | すべての変更が同じ速さで終わること |

> **実測の裏付け**: ドッグフーディングで、型チェック・lint・ビルド・コードレビューを
> **すべて通過した実装**から、ブラウザ動作確認が**本物の不具合を2件**捕まえた。
> 1件目は「送信中は入力欄が `disabled` なので `focus()` が無視される」というもので、
> 静的な検査では原理的に見つからない種類だった。

### 1-3. 最初に決めておくこと

- **承認は流し読みしない。** 承認ゲートは3つしかない（規模 / Stage 1 / Stage 2）。ここだけは読む
- **止まったら記録する。** 直さなくてよい。1行メモに残して先へ進む（→ §5-3）
- **最初の1〜2機能は遅い。** 設計書の書き方と承認のテンポに慣れるまでの投資と考える

## 2. 3つの原則

### 2-1. AI の出力は下書き。承認するのは人

AI は「それらしいもの」を必ず出す。**正しさは保証されない。**
だから承認ゲートがあり、レビュー結果がファイルに残る。

**サブエージェントの結果は特に注意。** 別の文脈で動いており、返ってくるのは要約だけ。
**必ずメイン側で差分を確認してからコミットする。**

### 2-2. ビルド成功 ≠ 正しい実装

型チェックが通ることと、意図どおり動くことは別。
だから**動作確認が独立した工程**として置かれている（`browser-test` / `unity-verify` / `capture-screenshots`）。

**この工程を飛ばすと、静的検査を全部通った不具合がそのまま残る。**

### 2-3. 仕組みで強制する。記憶に頼らない

「気をつける」で解決しようとしない。

| 忘れると困ること | 誰が担保するか |
|----------------|--------------|
| コミット前のビルド・型チェック | **フック**（人の判断を介さず発火する） |
| 設計レビューを通すこと | **スキル**（フローの一部として組み込まれている） |
| 設計書と実装の同期 | **フック＋スキル＋台帳**の三段 |

どれが何を担当しているかは [役割比較図](../diagrams/03_役割比較図.md) にまとまっている。

## 3. 最初の1機能を通す

### 3-1. まず S 規模で1周する

**いきなり大きい機能から始めない。** テキスト修正・ボタンの見た目調整など、
**1ファイルで終わる変更**をひとつ選び、フローの形を体で覚えるのが近道。

```
/harness-core:new-feature ヘッダーのタイトル文言を修正
```

起きることは次のとおり。

| 順 | 何が起きるか | あなたがやること |
|----|------------|----------------|
| 1 | AI が **S / M / L を推測して提示**する（根拠つき） | **承認する**（違うと思ったら直す）← ★ゲート1 |
| 2 | S なら**設計書は作られない**。そのまま実装に入る | 待つ |
| 3 | 実装後 `/harness-core:build-check` が走る | 結果を見る |
| 4 | コミット時に**フックがビルド・型チェックを実行**する | 失敗したら直してもらう |
| 5 | `/harness-core:done` が完了報告を出す | 内容を確認する |

**S 規模では設計書もレビューも通らない。** これは手抜きではなく設計判断で、
「全部の変更に重い手続きを課さない」ことがこのハーネスの原則になっている。

### 3-2. 規模が上がると何が増えるか

| 規模 | 増えるもの |
|------|-----------|
| **M** | 設計（Stage 2 のみ）/ コードレビュー / 動作確認 / 設計書の更新 |
| **L** | 上記＋ Stage 1 設計（何を作るか）と**承認ゲート2つ** |

**UX（画面・操作フロー）が変わるものは自動的に L。** 迷ったら L 寄りに出るようになっている。
経路の全体像は [開発フロー図](../diagrams/02_開発フロー図.md) を参照。

### 3-3. ⚠️ ただし「新規プロジェクトの最初の1機能」は例外

空のリポジトリでは、最初の機能はたいてい **土台づくりを含む L 規模**になる。
このときは**初期化を「Phase 0」として設計書に含める**のが既定の進め方。

> 「アプリを作る前に、アプリを作れる状態を作る」段階がある、と考えるとよい。
> ここは §4-1 で実際につまずいた箇所でもある。

## 4. つまずきポイント（実測）

ドッグフーディングで**実際に手が止まった7か所**。多くは修正済みだが、
**なぜ止まったか**を知っておくと同じ形の問題に気づきやすい。

### 4-1. 空のリポジトリで「何を作ればいいか」が決まらない

| | |
|--|--|
| **どこで** | 一番最初。`/harness-core:new-feature <機能名>` |
| **なぜ** | `package.json` も `src/` も無い。スキルは「機能設計書を書く」前提だが、**そもそも土台が無い** |
| **抜け方** | 初期化を **Phase 0** として設計書に含めた |
| **現在** | ✅ スキルに **Step 0（プロジェクトが初期化済みかの確認）** が入り、既定の進め方が示されるようになった |

### 4-2. `.env` を作る手前で必ず止まる

| | |
|--|--|
| **どこで** | 初期化中。DB の接続情報を用意する場面 |
| **なぜ** | 原則で「`.env*` に触らない」と決めており、**権限（deny）でも塞いでいる**。一方 DB ツールは `.env` が無いと動かない |
| **抜け方** | ユーザーが手で作った |
| **現在** | ⚠️ **構造として残る**。`.env.example` は deny から外れたが、`.env` 本体は今も塞がれている |

> **覚えておくこと**: **口頭で「今回は許可」と言っても deny は外れない。**
> 権限の deny はツール層にあり、セッション中の承認では緩められない。
> **秘密が入るファイルは自分で作る**のが正しい運用。

### 4-3. フレームワークの初期化コマンドが「非空ディレクトリ」で失敗する

| | |
|--|--|
| **どこで** | 初期化（`create-next-app` 等） |
| **なぜ** | ハーネス適用済みリポジトリには `CLAUDE.md` / `.claude/` / `constitution.md` が既にある |
| **抜け方** | 一時領域で生成し、必要なファイルだけコピーした |
| **現在** | ✅ 手順がスキルに入った。**危険なのは失敗ではなく上書き事故のほう** — 生成物の `CLAUDE.md` / `AGENTS.md` を混ぜると**プロジェクトの `CLAUDE.md` が壊れる**ので必ず除外する |

### 4-4. 初回の DB マイグレーションがフックに阻まれる

| | |
|--|--|
| **どこで** | 最初の `prisma migrate` |
| **なぜ** | バックアップフックが走るが、初回はバックアップ対象も生成物も無く**鶏と卵**になる |
| **抜け方** | 原因の切り分けに時間を取られた |
| **現在** | ✅ 修正済み（初回はスキップ）。ただし**空環境での再検証は未実施** |

### 4-5. 何も悪くないのに `build-check` が最初から赤い

| | |
|--|--|
| **どこで** | 初回の `npm run lint` |
| **なぜ** | **ハーネス同梱ファイル**が lint エラーになっていた。アプリのコードは 0 件なのに落ちる |
| **抜け方** | 対象外設定を足し、該当箇所を修正した |
| **現在** | ✅ 修正済み。**最初の赤が自分のコードのせいとは限らない**ので、まずエラーの出所を見る |

### 4-6. 設計書が指示しているコマンドを、同じハーネスの deny が禁止していた

| | |
|--|--|
| **どこで** | 2周目の着手直後（DB のリセット） |
| **なぜ** | 設計書の前提条件が実行を指示しているのに、権限側が同じコマンドを禁止していた |
| **抜け方** | **抜けられなかった。** 作業自体を見送った |
| **現在** | ✅ 解消（deny を外し、**承認＋バックアップフックの二段**に変更）。詳細は [フック発火タイミング図](../diagrams/05_フック発火タイミング図.md) |

> **教訓**: **設計の段階で「そのコマンドは禁止されていないか」を確認する。**
> 計画に書いたコマンドが実行できないと、着手直後に手戻りになる。

### 4-7. lint エラーを抱えたまま実装が進む

| | |
|--|--|
| **どこで** | 2周目の実装中 |
| **なぜ** | 編集後の lint フックは**検出していたのに通知が届いていなかった** |
| **抜け方** | まとめて `npm run lint` を回して初めて気づいた |
| **現在** | ✅ **解消**（harness-nextjs 0.2.1 以降）。通知は**画面と AI の文脈の2経路とも出る**。当初「画面には出ない」と判断して片方へ移した経緯があるが、**それが切り分けの誤りだった**（→ [フック発火タイミング図](../diagrams/05_フック発火タイミング図.md)） |

> **それでも区切りで `/harness-core:build-check` を回す。**
> 通知は届くようになったが、`post-edit-lint` が見るのは**編集した1ファイルの指摘だけ**である。
> **他ファイルへ波及した壊れ方は拾えない**ため、フックの沈黙を「全体が健全」の証拠にしない。

### つまずきの型

| 型 | 該当 | 気づき方 |
|----|------|---------|
| **土台が無い状態への配慮不足** | 4-1 / 4-3 / 4-4 | 「最初の1回」でしか起きない。2回目以降は再現しない |
| **安全のための仕組みが、正しい手順を塞ぐ** | 4-2 / 4-6 | 止められた側に**出口があるか**を見る |
| **動いているのに見えない** | 4-5 / 4-7 | 表示の有無で判断しない。**副作用を見る** |

## 5. 続けるときのコツ

### 5-1. 区切りで自分からチェックを回す

フックは万能ではない。**実装の区切りで `/harness-core:build-check` を明示的に回す**のを習慣にする。

### 5-2. 承認ゲートで止まったら、そこは読む

全部を読む必要はないが、**3つのゲート**（規模 / Stage 1 / Stage 2）は判断が必要な場所として設計されている。
ここを流すと、後工程の手戻りが一番大きい。

### 5-3. 気づいたことは「その場で直さず」メモに残す

ハーネス自体の不便に気づいても、**その場では直さない。**
プロジェクトに所見メモを1本作り、1行書いて開発を続ける。

- 開発の流れが止まらない
- **まとめて見ると共通の原因が見え、根本的な直し方を選べる**

区切りで見直し、本当に直すものだけをハーネスへ還元する
（→ [改善還元フロー図](../diagrams/06_改善還元フロー図.md)）。

> このガイドの §4 は、**まさにその所見メモから生まれた**。

### 5-4. 設計書に「次の周回」を書いておく

一度に全部作らず段階的に進めるとき、**保留した内容を設計書に節として残しておく**と、
再開時に「読むべき場所」が全部指されている状態になる。

これをやらないと、再開のたびに設計をやり直すことになる。

### 5-5. 「今後も従う決定」は機能設計書に置いたままにしない

Stage 2 で決めたことのうち、**その機能だけの話ではないもの**（層の分け方・エラー処理の方式・
命名の規則など）は、機能設計書に書いたままだと**次の機能を作るときに誰も見つけられない**。

`.claude/01_development_docs/` へ移す。設計書の「4-0. 設計方針への書き戻し」欄に行き先を書いておけば、
`/harness-core:complete-feature` が完了時に**未反映のまま終わらせない**。

> **ここに書くのは「これから何に従うか」だけ。** 「今どうなっているか」（API の一覧、テーブルの一覧）は
> `docs/設計書/` の職掌で、そちらは自動で同期される。混ぜると**片方が必ず腐る**。
> 詳しくは `.claude/01_development_docs/README.md`。
