# 既存プロジェクト移行指示書 — 旧テンプレートから claude-dev-harness へ

| 項目 | 内容 |
|------|------|
| 対応ハーネス版 | harness-core 0.9.1 / harness-nextjs 0.4.0 / harness-unity 0.3.0 / harness-wpf 0.3.0 |
| 最終更新 | 2026-08-16 |
| 位置づけ | **AI エージェントへそのまま渡す指示文**。旧テンプレート（nextjs-claude-template 等）から生成された既存プロジェクトを、プラグイン配信の統合ハーネスへ移す |
| 実測 | `skillup_mock`（nextjs）でフル移行1本 + `bookmark-app` / `skillup_mock` で 0.6.0 への追従2本。**想像で書いた手順は含まない** |

> **使い方**: 移行したいプロジェクトで Claude Code を起動し、
> 「`claude-dev-harness/docs/guide/既存プロジェクト移行指示書.md` に従って移行して」と指示する。
> **判断が要る箇所では必ず止まって聞くこと**（下記 §0）。

## 0. 大原則

| 原則 | 理由 |
|------|------|
| **勝手に決めない。判断が要る箇所は列挙してユーザーに聞く** | 「完璧に自動で」は達成できない。**判断を漏らさず出すこと**が実質的な最善 |
| **消す前に退避する** | ローカル資産の削除が中心の作業になる。取り返しがつくようにしてから進める |
| **削除判断はメイン1本で確定させない**（→ §3-6） | 「消してよい」の誤りは**自分では気づけない**。実測ではメインの自己点検で0件、独立レビューで7件の取りこぼしが出た |
| **移行と無関係な既存の壊れを直さない** | 検証で失敗が出たら、**移行由来かどうかを先に切り分ける**。無関係なら報告だけして直さない |
| **コミットはパス指定**（`git add -A` を使わない） | 他セッションの作業を巻き込む |

## 1. 前提を確認する（ここで止まることが多い）

```bash
git status -sb          # 未コミット・未 push・遅れの有無
git log --oneline -3
```

| 確認 | 引っかかったときの対応 |
|------|--------------------|
| **リモートより遅れていないか** | **遅れたまま移行しない。** 実測では **165 コミット遅れ**ており、そのまま進めていたら上流で追加された固有スキルを消していた。`git pull --ff-only` してから始める |
| 未コミットの変更が無いか | 中身を見る。**環境固有のローカル改変**（devcontainer のパス等）は上流に取り込み済みのことがある。`git show origin/<branch>:<path>` と突き合わせ、退避してから破棄する |
| どこで開発しているか | 別環境（devcontainer 等）が本番なら、そちらで移行する方が安全 |

**pull 後に棚卸しをやり直すこと。** 実態が変わる。

## 2. 環境と構成を調べる

```bash
ls .claude/skills .claude/agents .claude/hooks
cat .claude/settings.json
ls docs
node -e "console.log(require('./package.json').scripts)"   # nextjs の場合
```

- **環境**（nextjs / unity / wpf）を判定する
- **ビルド系コマンド**を実際の定義から拾う（`typecheck` が無いことがある。§5 で扱う）
- `docs/設計書/` と `.doc-sync.md` が既にあるか（旧テンプレ由来なら大抵ある。**あればそのまま使える**）

## 3. ローカル資産を3つに仕分ける（移行の本体）

**対象は以下すべて。** `.claude/` 直下を丸ごと見ること（skills/agents/hooks だけを見て設計文書を
「資料群」として素通りさせると、**ハーネスと二重管理になった文書が残る** — 実際に skillup_mock で起きた）。

| 対象 | 扱い |
|------|------|
| `.claude/skills` `.claude/agents` `.claude/hooks` | 下表で3分類 |
| `.claude/01_development_docs/` `02_design_system/` | 設計方針層。**中身を1本ずつ棚卸しする**（→ §3-5）。開発フロー文書は削除（→ §3-3） |
| `.claude/00_project/` | **残す**（要件・ドメイン知識） |
| `.claude/03_library_docs/` | **解体を前提に見る**（→ §3-4） |
| **`.claude/` 直下の単独ファイル** | ディレクトリに属さない独自ファイル（例: `browser-test-checklist.md`）。**プラグイン側に同名・同役割のものがあるか確認する**。あっても中身を照合してから消す（EngineerPotal の 38行版はプラグイン同梱 `browser-test/checklist.md` と内容一致だったが、**照合せずに消してよい理由にはならない**） |
| **`.claude/` の外にある「AI が読む文書」** | **`.serena/memories/` `.cursor/rules/` `.clinerules` `.github/copilot-instructions.md` 等。** MCP やエディタが持つプロジェクト記憶は `.claude/` の網に掛からないが、**git 追跡下ならチーム全員に配られ、実際に読まれる**。EngineerPotal では `.serena/memories/` の6本728行が生き残り、**`git add .` を案内する文書が CLAUDE.md と正面から矛盾**していた（→ §3-7） |

残す文書は §5 で `harness.config.json` の `projectDocs` に登録する（登録しないとスキルが読まない）。

| 分類 | 判定方法 | 扱い |
|------|---------|------|
| **素のまま** | 旧テンプレートの**履歴のどこかに完全一致で存在する** | **削除**。プラグイン側に後継がある |
| **改変あり** | 一致しない | **中身を見る**（→ §3-2） |
| **プロジェクト固有** | 旧テンプレートに存在しない | **残す**。プラグインと共存できる |

### 3-1. 判定は blob ハッシュで行う（目視で差分を読まない）

旧テンプレートを一時ディレクトリへ**全履歴つき**で clone し、対象ファイルを1つずつ照合する:

```bash
git clone https://github.com/mizuta0711/nextjs-claude-template.git /tmp/old-template

# 対象ファイルごとに（LF へ正規化してからハッシュを取るのが要点）
sha=$(sed 's/\r$//' <対象ファイル> | (cd /tmp/old-template && git hash-object --stdin))
(cd /tmp/old-template && git cat-file -e "$sha") && echo "素のまま" || echo "改変あり"
```

> ⚠️ **正規化を忘れると全ファイルが「改変あり」になる。** Windows のチェックアウトは CRLF、
> リポジトリの blob は LF なので、そのまま比較すると**全行差分**（`1,81c1,81` のような diff）になる。
>
> ⚠️ **最新版との単純 diff で判定しない。** テンプレートがその後進化しただけでも差分は出る。
> **「履歴のどこかに一致があるか」**で見ること。

#### 根本原因を確認する: `.gitattributes` があるか

```bash
ls -a | grep gitattributes
git ls-files --eol | awk '{print $1}' | sort | uniq -c    # index の改行コード
```

**無ければ §4 で必ず配置する。** これが無いと `core.autocrlf=true` の Windows 環境で
作業ツリーが CRLF になり、**この照合だけでなく以後の `harness-update` の3点比較でも
全ファイルが差分として出る**（skillup_mock で実際に発生し、原因がこれだった）。

- `i/lf` が大半なら**追加しても再正規化は起きない**（`git status` はクリーンのまま）
- `i/crlf` が多い場合は**大量の再正規化が起きる**。ユーザーに影響を伝えて判断を仰ぐこと

### 3-2. 「改変あり」の中身はたいていパスの埋め込み

実測では、改変の正体は**プロジェクト固有のドキュメントパスを本文に直接書き込んだもの**だった:

```diff
- | 常に | `01_architecture_design.md` |
+ | 常に | `.claude/01_development_docs/01_architecture_design.md` |
- レスポンスが設計書と一致しているか
+ レスポンスが `docs/設計書/API一覧.md` の定義と一致しているか
```

ハーネスは**これを外出しする設計**である（`harness.config.json` の `designDocs` と `.claude/rules/`）。
したがって **改変は捨てるのではなく設定へ移送する**。移送先を決めてからファイルを消すこと。

**移送先が思いつかない改変が出たら、そこがユーザーに聞くべき点。**

### 3-3. 開発フロー文書は必ず削除する（ハーネスと二重管理）

規模判定・S/M/L フロー・2段階設計・バグ修正フローを書いた文書は、**ハーネスの職掌**
（`constitution.md` §1〜§5 と `/harness-core:new-feature` 同梱の「開発フローと規模判定」）と
**内容が重複し、版がずれた瞬間に矛盾する**。

> ⚠️ **ファイル番号で特定してはならない。** 旧テンプレートでは nextjs=09 / unity=05 / wpf=08 だが、
> **実プロジェクトでは番号が振り直されている**（CommSim では 09 がフロー文書で、08 は
> `08_scripting_design.md` というプロジェクト固有の設計文書）。番号で消すと**別ファイルを誤削除する。**

```bash
# 中身で特定する
grep -rln "規模判定\|S/M/L\|Stage 1\|2段階設計" .claude/01_development_docs/
```

**削除の前に参照を張り替える**（残すと古い定義を指し続ける）:

```bash
grep -rn "開発フロー\|規模判定\|development_flow" CLAUDE.md
```

| 参照元の記述 | 張り替え先 |
|---|---|
| 規模判定・S/M/L フローの詳細 | `/harness-core:new-feature` が判定する。原則は `constitution.md` §1 |
| 2段階設計の詳細 | `constitution.md` §2 |
| バグ修正フローの詳細 | `constitution.md` §5 |

### 3-4. `03_library_docs/`（FW ガイド）は解体する

**この層に残るものは無い。** 中身を3つに割り、それぞれの正しい置き場へ移す:

| 中身 | 行き先 |
|------|-------|
| 環境共通の規約（別プロジェクトにも貼れる） | **ハーネスの `.claude/rules/`**。0.6.0 で MVVM・非同期/スレッド・XAML/デザイントークン・Zustand は既に入っている。**重複は rules 側が正** |
| 実態（ストア一覧・画面一覧・採用ライブラリの列挙） | **`docs/設計書/`**（→ §3-5）。軸を1本増やしたら `designDocs` と `docTriggers` にも足す |
| 版固有の罠（「この版には破壊的変更がある」等） | `CLAUDE.md` の環境セクション |

- **1,000行級の大型ファイルは特に混在している**（EngineerPotal の `prisma_guide` 1,068行 /
  `ui_component_guide` 1,238行）。**節ごとに判定する**
- **`03_library_docs/` は `projectDocs.policy` に登録しない。** 設計方針層の分類
  （`00_project` / `01_development_docs` / `02_design_system`）に属さない宙に浮いた層になる
- 解体しきれず一時的に残す場合も、**`policy` へは入れず**、棚卸しの宿題として報告する

> **実測（skillup_mock・2026-08-15）**: 解体後に残ったのは `02_state_management_guide.md` 1本だけで、
> それ自身が「このアプリのストアが今どうなっているか（実態）を書く」と宣言していた ＝ 定義上 `docs/設計書/` の職掌。
> **`docs/設計書/ストア一覧.md` へ移設して層ごと廃止した。**

### 3-5. 設計方針層の棚卸し（実態スナップショットの摘出）

**原則: 「今こうなっているか」の記述が `.claude/` にあってはいけない。** それは `docs/設計書/` の職掌で、
`docTriggers` により自動同期される。`.claude/` に置くのは**「これから何に従うか」と「なぜそうするか」**だけ。

旧テンプレート由来のプロジェクトは、この境界が無い時代に書かれた文書を抱えている。**残すと腐る。**

#### 判定手順

**1. 文書が主張している「数」と実装の数を突き合わせる**（乖離が大きいほど実態スナップショットである証拠）:

```bash
grep -c "^model " prisma/schema.prisma                    # テーブル数
find src/app/api -name route.ts | wc -l                   # エンドポイント数
find src/app -name "page.tsx" | wc -l                     # ページ数
find src -path "*/stores/*" -name "*.ts" | wc -l          # ストア数
```

**2. 各文書の改訂履歴の最終日付を見る。** 実装が動いているのに文書が数ヶ月止まっていれば、
**誰も更新していない ＝ 正本ではない**。

**3. 1本ずつ分類する**:

| 主体 | 判定 | 扱い |
|------|------|------|
| 一覧・表・件数 | **実態** | `docs/設計書/` に正本があるか確認 → あれば**下の削除前チェックを通して削除**、無ければ**移設して `designDocs` / `docTriggers` に登録** |
| 「なぜそうするか」「どう判断するか」 | **方針** | **残す** |
| 完了済みの過渡期メモ（移行計画・削除計画・「Phase 3 で対応予定」） | **陳腐化** | **削除**。ただし**計画が本当に完了しているかコードで確認してから消す** |

**4. 節単位で混在していることがある。** ファイルごと消さず、**節だけ削る**判断も出す
（例: architecture 設計書の「レガシーコード削除計画」節だけ削り、層構成・依存方向・命名規則は残す）。

**5. この基準は「消す側」だけでなく「書き直す側」にも当てる。**

削除の判定に「件数を書いていたら実態」を使っておきながら、
**その隣で書き直した文書に件数を書く**ことが実際に起きる。

> **実測（EngineerPotal・2026-08-16）**: 6,549行を「実態を書いていたから」と削った同じ作業で、
> 書き直した `01_design_system_overview.md` に `sm:` 296箇所 / `dark:` 102箇所、
> `react-nextjs.md` に「2026-08-16 時点」を入れていた。査読2 の指摘 ——
> **「『2026-08-16 時点』という但し書き自体が、実態を書いていることの自白」**。

| 書きたくなったもの | どうするか |
|------------------|-----------|
| 「〜が N 箇所ある」 | **書かない。** 数は `grep` で常に取れる |
| 「〜が N 本ある」 | **書かない。** 一覧はファイルシステムが持っている |
| 「YYYY-MM-DD 時点」 | **書きたくなったら、それは実態を書こうとしている合図**。書くのをやめる |
| 「〜という方針だから〜する」 | 書く（これが方針） |

**件数を書くなら、必ず数えた範囲を併記する。** 対象を絞りすぎた実測は嘘になる
（実測: `(未確定)` の残数を「7ファイル19行」と報告したが、
対象ディレクトリを3つに絞っていたためで、全体では **12ファイル34行**だった）。

#### 削除前チェック（3つとも通すこと）

> **「正本が別にある」だけでは削除の理由にならない。** 独立レビューで実際に3種類の取りこぼしが出た。

| # | 確認 | 実測で起きたこと |
|---|------|----------------|
| **1** | **正本の方が実装と合っているか。** 削除対象と正本を**実装コードと**突き合わせる | 通知 API で**正本の方が間違っていた**（一覧キーが `notifications`。実装と削除対象はどちらも `items`）。正本側が `rules/api.md` の規約にも違反していた。**先に正本を直してから消す** |
| **2** | **正本に無い情報が削除対象に無いか。** 特に**リクエスト/レスポンスの JSON 例・フィールドの必須任意・型の使い分けの理由** | 正本の API一覧はパス・メソッド・説明の3列だけで、**削除対象だけが契約を持っていた**。消える寸前だった。**先に移してから消す** |
| **3** | **参照元を全部 grep する** | `docs/features/pending/` からリンクされていた。**`pending/` は未着手の機能設計書＝アクティブ文書**で、`completed/`（過去記録・リンク切れ許容）とは扱いが違う |

```bash
grep -rn "<削除するファイル名>" --exclude-dir=node_modules --exclude-dir=.git . \
  | grep -v "docs/features/completed/"
```

#### 残す側も点検する

**削除対象より、残した文書の方が古いことがある。** 実測では、残した architecture 設計書の
「状態管理戦略」節に**存在しない persist キー**が書かれており、**削除した文書の方が訂正済みだった**
（＝正確な文書を消して不正確な文書を残していた）。

**残すと決めたファイルも、実態記述が混ざっていないか同じ手順で点検すること。**

#### 移設・新規記述は実装で裏を取る

移設や書き直しで**新しく書いた記述にも誤りが入る**。実測では移設先の新規記述に読み違いが3件あった
（「2つのコンポーネントから参照される」→ **実際はどちらも参照していない**、
「ハイドレーション対策」→ **実態は二重フェッチ防止のガード**など）。
うち1件は**移設元から検証せずに転記したもの**だった。

- 「〜から参照される」「〜のために使う」と書くなら、**その参照箇所を実際に開いて確認する**
- **別のエージェントに独立検証させると効果が高い**（この7件の指摘は全てそれで出た）

**値だけでなく「呼び出し方」も確認する。**
実測では、コンポーネントの variant を移設するときに**値（`sm` / `default`）は実装で確認したのに、
プロパティ名を確認しなかった**。書いたのは `sz`、実物は `size` で、
`sz` はコード中に**0箇所**だった（`<Button sz="...">` は DOM まで流れて警告になる）。

| 確認するもの | 例 |
|------------|-----|
| **値** | variant の候補、enum の要素、設定できる文字列 |
| **呼び出し方（API 名）** | プロパティ名・関数名・引数の順序・戻り値の形 |

**値が合っていても呼び出し方が違えば動かない。** 移設先に書いたシグネチャを
`grep` して**実装に存在することを確かめる**（0件なら書き間違い）。

#### 自動生成されるファイルに手書きで足さない

補注の移し先が**自動生成ファイル**だと、次回生成時に**無言で消える**。

- `docs/設計書/テーブル定義書.md` は `generate-table-docs.ts` が**全文上書き**する。
  補注は **`schema.prisma` の `///` コメント**へ書く（生成スクリプトが説明列に取り込む）
- 移し先を決める前に、**そのファイルが生成物かどうかを確認すること**

#### 二重管理を放置した場合の実害（実測）

skillup_mock では API 設計書が `docs/設計書/API一覧.md` と二重管理になっていた結果、
**設計レビューが「存在しない義務」を3回にわたって指摘していた**
（「Skills API が設計書に未定義」等。いずれも `API一覧.md` 側では同期済み）。
**レビュー工数がまるごと無駄になる。**

#### 実施のタイミング

**移行と同時にやらない。** 削除量が大きく、移行の差分が読めなくなる。

- 移行時は**「棚卸しが必要」と判定して一覧で報告する**（どのファイルが実態スナップショットか、乖離はどれだけか）
- 実施は**移行コミットとは別の作業**として提案し、ユーザーの判断を仰ぐ
- 実施するときは、**移設前の内容も古い前提で実装と突き合わせる**
  （skillup_mock ではストア一覧の移設時に、ストア数・persist キー・アクション名の誤りが5箇所見つかった）
- **実施は §3-6 の査読ゲートを通す。** 消す前と消した後の2回、別エージェントに見せる

### 3-6. 棚卸しは別エージェントの査読を通してから確定する（必須ゲート）

> **メイン1本で完結させない。** 棚卸しは「消す判断」の連続で、**間違えたことに自分では気づけない**。
> §3-5 の指摘7件は**すべて独立レビューで出たもの**で、メイン側の自己点検では1件も出ていない。

査読は**2回**入れる。片方だけでは足りない（消す前は計画の誤り、消した後は作業の誤りを見る）。

| # | タイミング | 査読者に渡すもの | 見てもらう観点 |
|---|-----------|----------------|--------------|
| **査読1** | **削除を実行する前** | 棚卸し一覧（**残す / 消す / 移設** の3列 + **各行の根拠**） | 削除前チェック3項目が**実際に踏まれているか**（「正本がある」で済ませていないか）／ 残す側の点検漏れ ／ 正本と実装の食い違い |
| **査読2** | **実施した後・コミットの前** | `git diff` と、移設・書き直しで**新しく書いた記述** | 新規記述が実装と合っているか ／ 参照切れ ／ 自動生成ファイルへの手書き ／ 消しすぎ |

#### 守ること

- **同じ会話の続きでやらない。** サブエージェント（`code-reviewer`）か**別セッション**で行う。
  同一文脈で自己レビューさせると**自分の判断を追認するだけ**になり、査読の意味が消える
- **査読者に「結論」を渡さない。渡すのは「対象と根拠」まで。**
  「これは実態スナップショットなので消します」ではなく、
  「このファイルはこういう内容で、正本候補はこれ。判断してほしい」の形で渡す
- 指摘は **`docs/reviews/YYYYMMDD_設計方針層の棚卸し.md`** に残す（会話に流さない）
- **メインは全指摘に「対応済み / 見送り（理由）」を必ず書く。** 黙って落とさない
- **査読の指摘自体が誤っていることもある。** 実測で1件あった（skillup_mock）。
  指摘を鵜呑みにせず、**実装で裏を取ってから**対応する。誤りだった場合はレビュー記録側も訂正する

#### 査読1 に渡すテンプレート

```markdown
## 棚卸し対象一覧（査読依頼）

| ファイル | 行数 | 内容の要約 | 正本候補 | メインの見立て |
|---------|------|-----------|---------|--------------|
| .claude/01_development_docs/03_api_design.md | 44 | API の一覧と契約 | docs/設計書/API一覧.md | 消す寄り |

### 見てほしいこと
1. 正本候補は**実装と合っているか**（削除対象の方が正しい可能性）
2. 削除対象**だけが持っている情報**は無いか（JSON 例・必須任意・型の使い分けの理由）
3. **残す**と判断したファイルに、実態スナップショットが混ざっていないか
4. 参照元（`grep`）の確認漏れ。特に `docs/features/pending/`
```

#### 実測（skillup_mock・2026-08-15）

この査読で **7件の指摘**が出た。内訳は §3-5 の各節がそのまま該当する:

| 種別 | 件数 | 例 |
|------|------|-----|
| 削除判断の誤り | 3 | 正本の方が実装と食い違っていた ／ 削除対象だけが API 契約を持っていた ／ `pending/` から参照されていた |
| 残した側の誤り | 1 | 残した architecture に**存在しない persist キー**（消す側が訂正済みだった） |
| 新規記述の誤り | 3 | 「2つのコンポーネントから参照される」→ **どちらも参照していない** など |

**そのうえで、この査読結果自体にも後から誤りが1件見つかっている。**
査読は「正解を出す工程」ではなく「**メインが気づけない範囲を広げる工程**」と捉えること。

### 3-7. `.claude/` の外にある AI 向け文書を洗い出す

**「AI が読む文書」は `.claude/` の中だけにあるとは限らない。** 次を必ず見ること:

```bash
git ls-files | grep -E "^\.(serena|cursor|clinerules|github/copilot|aider|windsurf)" 
ls -a | grep -E "^\.(serena|cursor|clinerules|aider|windsurf)"
cat .mcp.json 2>/dev/null   # どの MCP が居るか
```

| 層 | 見るもの |
|----|---------|
| **serena** | `.serena/memories/*.md` と `.serena/project.yml` |
| cursor / cline / windsurf 等 | `.cursor/rules/` `.clinerules` `.windsurfrules` |
| GitHub Copilot | `.github/copilot-instructions.md` |

**扱いは `.claude/` 配下と同じ**（§3-5 の棚卸し・§3-6 の査読ゲートを通す）。判断のポイント:

- **その層が「常時ロード」か「オンデマンド」か**を、**MCP の実装で確認する**。
  serena はメモリの**本文**はオンデマンドだが、**メモリ名の一覧は起動時に必ず注入する**ため、
  `task_completion_checklist` のような名前は**それ自体が読み込みを誘発する**
- **消すと自動再生成されないか。** serena は「メモリが0本」を検知して `onboarding` を促し、
  **同種の文書を作り直させる**。**層ごと廃止は成立しない**（1本残す必要がある）
- **書き込みを止められるか。** serena なら `.serena/project.yml` の `read_only_memory_patterns`

> **教訓**: 「正本は `CLAUDE.md` 側にある」と分かっていても、**MCP は自分の層を再生産する**。
> 消し方だけでなく**再発の止め方**まで設計しないと、次のセッションで戻る。

#### ⚠️ MCP の挙動を根拠にするときは、**実行時のバージョン**で確認する

`.mcp.json` が **`uvx --from git+...`** や `npx ...@latest` のように**追従型の指定**をしている場合、
**手元のキャッシュにある版と、実際に起動される版は違う**。

```bash
uvx --from git+https://github.com/oraios/serena serena --version   # 実行時の版を出す
```

**実測（EngineerPotal・2026-08-16）**: 査読者が uv キャッシュの `serena_agent-1.1.2` を読んで
結論を出したが、**実際に起動されるのは 1.7.1.dev0**（6マイナー版新しい）だった。
キャッシュには `0.1.4 / 1.0.0 / 1.1.1 / 1.1.2 / 1.7.1.dev0` が混在していた。

- 結論自体は維持されたが、**根拠3件のうち1件は指し示すコードが存在しなくなっていた**
  （ツールが削除され、別の機構に置き換わっていた）
- **バージョンを確認してからソースを読むこと。** 逆順にすると、
  「正しい結論・無効な根拠」という**最も気づきにくい形**になる

#### ⚠️ MCP は自分の設定ファイルを書き換える。**コメントで残した「なぜ」は消える**

**実測**: `read_only_memory_patterns: [".*"]` を設定し、
「意図した設定であり空に戻さないこと」という注意書きを YAML コメントで添えたところ、
**次の起動時に serena のスキーマ移行が `project.yml` を書き換え、コメントだけが消えた**
（設定値は残ったので動作影響は無かった）。

- **「なぜその設定にしたか」は、消えない場所に残す** —
  `docs/reviews/` の棚卸し記録、または `CLAUDE.md`。**YAML コメントは補助**と考える
- 設定ファイルをコミットするときは、**MCP が書き換えた差分が混ざっていないか**を見る
  （自分の変更だと思って通すと、消えた記述に気づけない）

#### 止め方には穴があることを前提に確かめる

**実測**: serena 1.7.x の `read_only_memory_patterns` は、**`memory_maintenance` の初期生成だけを止められない**
（`is_tool_context=False` で書かれるため書き込みガードを通らない）。
`onboarding` を実行しない限り起きないので方針は崩れないが、
**「この設定を入れれば絶対に増えない」とは言えない**。

- 止め方を設定したら、**その設定が本当に全経路を覆うかを実装で確認する**
- 覆えない経路が残るなら、**残ることを記録に書く**（「対策済み」と書いて終わらせない）

> ⚠️ **`permissions` を新規に入れることになる場合は、それを明示して報告する。**

## 5. `harness.config.json` を実態に合わせて書く

**既定値のままにしない。** 実際のディレクトリ構成とコマンドに合わせる。

| キー | 合わせ方 |
|------|---------|
| `commands` | 実在するものだけ。**無いものは `null`**。定義したら**実際に走らせて通ることを確認する** |
| `gates.preCommit` | **最初は軽いものだけ**。重いと毎回のコミットが詰まる |
| `paths.source` / `docTriggers` | 実際の構成（`src/lib/hooks` か `src/hooks` か等）を見て書く |
| `designDocs` | **既存の `docs/設計書/` の実ファイル名に合わせる**。プロジェクト固有の設計書も足してよい |
| **`projectDocs`** | **§3 で残した設計方針・要件の置き場を登録する。登録しないとスキルが読まない**（下記） |
| `verification` | nextjs は `browser-test` / unity は `unity-verify` + `manualGate: true` / wpf は `capture-screenshots` |

```json
"projectDocs": {
  "requirements": [".claude/00_project"],
  "policy": [".claude/01_development_docs", ".claude/02_design_system"]
}
```

- `requirements`（**Stage 1** で読む）: 要件・ドメイン知識。無ければ `[]`
- `policy`（**Stage 2** で読む）: 設計方針。**実在するディレクトリだけを書く**
- **`03_library_docs/` は入れない**（→ §3-4 で解体する）。設計方針層の3分類に属さない層を
  `policy` に入れると、**Stage 2 で古い実態スナップショットを読ませることになる**
- `designDocs`（＝実装の**現況**）と混同しないこと。`projectDocs` は「**これから何に従うか**」
- **`policy` に登録する前に §3-5 の棚卸しを通すこと。** 未棚卸しのまま登録すると、
  Stage 2 のたびに実装と乖離した一覧（古いテーブル数・エンドポイント数）を読ませることになる

**登録したら、指すディレクトリが全て実在することを確認する**（タイポは素通りして気づけない）:

```bash
node -e "const fs=require('fs');const c=JSON.parse(fs.readFileSync('.claude/harness.config.json','utf8'));
for(const k of ['requirements','policy']) for(const d of (c.projectDocs?.[k]||[]))
console.log((fs.existsSync(d)?'OK  ':'★無い')+' '+k+': '+d)"
```

## 6. `harness-baseline.json` を必ず書く（最重要）

```json
{
  "templatesCommit": "<ハーネスの完全な40桁 SHA>",
  "environment": "nextjs",
  "appliedAt": "YYYY-MM-DD",
  "placeholders": { "PROJECT_NAME": "...", "PROJECT_DESCRIPTION": "..." }
}
```

**これが無いと、以後の `/harness-core:harness-update` が2点比較になり、差分が全て「競合」になる。**
移行時に書いておけば、次回以降は3点比較で「適用 / 保持 / 競合」に正しく分類される。

- `templatesCommit` は**短縮形ではなく完全な SHA**（`git rev-parse <ref>`）
- `placeholders` は `create-project.mjs` に渡した値と一致させる
- **`.gitignore` に入れない。** チーム全員で同じ基準点を使うためコミットする

## 8-2. `docs/features/TEMPLATE.md` に「書き戻し先」欄を足す

プロジェクトが独自の `docs/features/TEMPLATE.md` を持っている場合、`new-feature` は
**プラグイン同梱版よりそちらを優先する**。つまり**プラグインを更新しても届かない**。

> ⚠️ **「4-0 を足す」だけでは足りない。まず同梱版と節構成を突き合わせること。**
>
> プロジェクト側 TEMPLATE が古いと、**同じ番号が別の節に使われている**。実測（EngineerPotal / skillup_mock の2件）:
>
> | | 3-2 | 3-3 | 3-4 |
> |---|-----|-----|-----|
> | 同梱版（正） | 受け入れ基準チェックリスト | **未解決事項** | Stage 1 レビュー記録 |
> | プロジェクト側（古い） | 受け入れ条件（ユーザー目線） | **Stage 1 レビュー記録** | （無し） |
>
> `new-feature` Step 2 が書き込む「未解決事項」の節が**存在しない**ため、4-0 を足しても直らない。
>
> **手順**: 同梱版（`plugins/harness-core/skills/new-feature/TEMPLATE.md`）を**ベースに取り直し**、
> プロジェクト固有の調整（環境語彙・設計書リンク）だけを載せ直す。
> **見出し名は同梱版から変えないこと**（スキルは見出し名で節を探す）。
> 調整内容は冒頭のコメントに残し、次回同梱版が更新されたときに載せ直せるようにする。
>
> あわせて**非名前空間のスキル名**（`/design-review` 等）を `/harness-core:` 付きに直す。

Stage 2（技術設計）の節に次を追加する（ハーネス同梱版の §4-0 と同じ）:

```markdown
### 4-0. 設計方針への書き戻し

| 決めたこと | 書き戻し先 | 状態 |
|-----------|-----------|------|
| | `.claude/01_development_docs/xx.md` | ⚪ 未反映 / ✅ 反映済み |
```

これが無いと `/harness-core:complete-feature` のゲート3（書き戻し確認）が空振りし、
**設計判断が機能設計書の中に埋もれたまま**になる。

### 10-2. config が宣言した前提が実在するかを機械で確かめる

> **移行の失敗はここに集中する。** `harness.config.json` も `rules/` も
> **「宣言」であって「実在の確認」ではない**。宣言だけして中身が無くても、
> **何のエラーも出ないまま完了してしまう**（実測でブロッカー1件・要修正2件がこれだった）。

```bash
node -e "
const fs=require('fs'),cp=require('child_process');
const c=JSON.parse(fs.readFileSync('.claude/harness.config.json','utf8'));
let ng=0;
// 1) projectDocs のパス
for(const k of ['requirements','policy']) for(const d of (c.projectDocs?.[k]||[]))
  { const ok=fs.existsSync(d); if(!ok)ng++; console.log((ok?'OK   ':'★無い ')+k+': '+d); }
// 2) designDocs の実ファイルと台帳
const dd=c.designDocs||{};
for(const f of [dd.ledger, ...(dd.docs||[]).map(x=>dd.dir+'/'+x.file)].filter(Boolean))
  { const ok=fs.existsSync(f); if(!ok)ng++; console.log((ok?'OK   ':'★無い ')+f); }
// 3) designDocs.sources が1件もヒットしないものが無いか
for(const d of (dd.docs||[])) for(const s of (d.sources||[])){
  const n=cp.execSync('git ls-files -- \"'+s+'\" | wc -l',{encoding:'utf8'}).trim();
  if(n==='0')ng++; console.log((n==='0'?'★0件 ':'OK   ')+d.file+' <- '+s+' ('+n+')');

// 4) verification.skill が要求する MCP が .mcp.json に居るか
```
