## 0. このガイドの範囲

**扱うのは「標準以外の MCP を足したいとき」だけ。**

環境プラグインが動作確認のために要求する MCP（nextjs の Playwright、unity の Unity MCP）は
**オプションではなく前提**なので、このガイドでは扱わない。
ハーネスと MCP の関係（何が配られ、何が配られないか）は
[役割比較図 §MCP — ハーネスは配らない（要求するだけ）](../diagrams/03_役割比較図.md) に整理してある。

ここから先は**どの環境（nextjs / unity / wpf）でも共通**の話として読める。
環境固有の注意がある箇所は **【nextjs】** のように明示する。

## 1. 追加前に確認すること

MCP は**入れれば入れるほど良いものではない**。追加前に3点を確認する。

### 1-1. 標準ツールで代替できないか

Read / Write / Edit / Glob / Grep / Bash で足りるなら MCP は要らない。
**「なんとなく便利そう」で追加しない。**

### 1-2. トークン消費の増加を受け入れられるか

MCP を追加すると**ツール定義がコンテキストに常時ロードされる**。
軽微な作業でも数千トークン増えることがある。

### 1-3. プロジェクト全体で要るのか、自分だけか

| 範囲 | 書く場所 | 性質 |
|------|---------|------|
| プロジェクト全体（チーム共通） | **`.mcp.json`**（Git 管理下） | 全員に配られる。レビュー対象になる |
| 自分だけ | **ユーザー単位設定**（`~/.claude.json`。`claude mcp add` が書く） | 他人に影響しない |

> **迷ったら個人側から始める。** `.mcp.json` に入れると、その MCP を必要としない人にも
> トークンコストと前提条件（インストール・ポート）を強制することになる。

> ⚠️ **`.mcp.json` に書くだけでは自動承認されない。**
> `.claude/settings.json` の **`enabledMcpjsonServers`** にも名前を足すこと。
> 足さないと起動のたびに承認を求められるか、環境によっては読まれない。
>
> ```jsonc
> // .claude/settings.json
> "enabledMcpjsonServers": ["playwright", "serena"]
> ```
>
> **既存プロジェクトへハーネスを後付けした場合は特に注意。** 既存の `.mcp.json` を
> そのまま残すと、**環境プラグインが要求する MCP が入らない**。実測では
> `verification.skill: browser-test` を宣言しているのに Playwright MCP が無く、
> **動作確認が起動できない状態でコミットまで通った**
> （[既存プロジェクト移行指示書 §4 / §10-2](既存プロジェクト移行指示書.md)）。
>
> ⚠️ **Windows の注意**: ユーザー単位設定はプロジェクトパスをキーに持つため、
> **ドライブレターの大小（`D:` / `d:`）で登録が迷子になる**ことがある。
> 起動元のシェルによってパス表記が変わるのが原因（詳細は
> [改善還元フロー図 §関門4](../diagrams/06_改善還元フロー図.md)）。
> プロジェクト共通で使うものは `.mcp.json` に置く方が安定する。

## 2. Serena MCP — シンボル単位のコード検索・編集

[oraios/serena](https://github.com/oraios/serena)。言語サーバー（LSP）を内部で使い、
シンボル単位でのコード把握・編集を提供する。

| | 内容 |
|--|------|
| **向く** | 大規模コードベース（数千ファイル以上）でのシンボル横断検索・リファクタリング。LSP 対応言語（TypeScript / Python / Rust / C# など）で型情報を使った検索がしたい。`grep` では辿りにくい「呼び出し元」「型の使用箇所」を追いたい |
| **向かない** | 小〜中規模（標準の Grep / Read で十分）。Python 環境（uvx）を用意したくない。トークンコストを最優先したい |
| **前提** | **uvx**（`uv` に付属）。`pip install uv` または [uv 公式手順](https://docs.astral.sh/uv/) |

```jsonc
// .mcp.json に既存の mcpServers と並べて追記する
{
  "mcpServers": {
    "serena": {
      "type": "stdio",
      "command": "uvx",
      "args": [
        "--from", "git+https://github.com/oraios/serena",
        "serena", "start-mcp-server",
        "--context", "claude-code",
        "--project", "<プロジェクトの絶対パス>"
      ],
      "env": {}
    }
  }
}
```

**`<プロジェクトの絶対パス>` は必ず実際の値に置き換える。** プレースホルダのままでは起動しない。

- 初回起動時に **LSP インデックスの構築**が走り、数十秒〜数分かかる
- パス指定を誤ると無言で起動しないことがある。Claude Code のログで確認する
- 複数プロジェクトで使うなら、ユーザー単位設定にプロジェクトごとの定義を置く方が管理しやすい

## 3. Context7 MCP — ライブラリの最新ドキュメントを動的取得

[upstash/context7](https://github.com/upstash/context7)。
プロンプトに `use context7` と書くと、各種ライブラリの**最新の公式ドキュメント**を取得して参照させられる。

**学習データのカットオフを補うのが役目。** 新しいバージョンの破壊的変更は、
モデルが知らないか、古い挙動で答えてしまうことがある。

| | 内容 |
|--|------|
| **向く** | 学習カットオフ後のバージョンを使うプロジェクト。API の変更・非推奨化を頻繁に確認したい場合 |
| **向かない** | 枯れたバージョンで安定運用している。オフライン環境。社内・非公開ライブラリ（公開ドキュメントのみ対応） |
| **前提** | Node.js / npx とインターネット接続。API キーは原則不要 |

```jsonc
{
  "mcpServers": {
    "context7": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@upstash/context7-mcp@latest"]
    }
  }
}
```

使い方は指示の中に `use context7` と書くだけ:

```
use context7
App Router で並行ルートを使う最新の書き方を教えて
```

- **取得できても誤解釈はありうる。** 重要な箇所は公式ドキュメントで裏を取る
- リアルタイム取得のぶん**応答が遅くなる**
- **`CLAUDE.md` との使い分け**: プロジェクト固有のルールは `CLAUDE.md` / `.claude/rules/`、
  汎用的な最新 API 情報は Context7。**同じことを2箇所に書かない**

## 4. drawio MCP — 図の作成・編集

XML / Mermaid / CSV から draw.io エディタを開く MCP。

| | 内容 |
|--|------|
| **向く** | Mermaid では表現しきれない複雑な図（スイムレーン等）を作りたい。図を頻繁に更新する |
| **向かない** | 単純なフローチャート・シーケンス図だけ（**Markdown に mermaid を埋める方が軽い**） |
| **前提** | Node.js / npx。使用ポートが空いていること |

```jsonc
// ユーザー単位設定（個人用途）に置くのを推奨
{
  "mcpServers": {
    "drawio": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "drawio-mcp-server"]
    }
  }
}
```

別パッケージ（`@drawio/mcp`）も存在するため、動作するほうを選ぶ。

> **⚠️【nextjs】ポート競合**: drawio MCP サーバーは既定で**ポート 3000** を使う。
> Next.js の dev server（`npm run dev`）も 3000 のため、**同時に起動できない**。
> 回避策は ①個人用途にして必要なときだけ有効にする ②dev server を別ポートで起動
> （`npm run dev -- -p 3001`）③drawio MCP 側のポート指定を変える（バージョンによる）。

### ハーネスの図との関係

`docs/diagrams/` の図は **mermaid（`.md`）を一次ソース**とする方針で、
`.drawio` はリポジトリに置かない（テキストで差分が読め、更新できるため）。

drawio MCP は**見栄えのある版が要るときに mermaid からその都度起こす**用途で使う。
`open_drawio_mermaid` は mermaid のパース確認にも使える。

## 6. 検討したが採用しなかった MCP（記録）

> **この節は 2026-04（統合前テンプレート時代）の判断記録**であり、以後の実装変更に追従しない。
> 再検討の目安だけ更新してある。

### 6-1. Cipher — セッションをまたぐ長期記憶

ベクトル DB でセッション横断の記憶を保持する MCP。

| 評価 | 内容 |
|------|------|
| 良い点 | 過去の議論・決定を参照できる。長期プロジェクトで効く可能性 |
| **不採用の理由1** | **「記憶はファイルに書き残す」という設計思想と衝突する。** 意思決定は `docs/features/` / `docs/設計書/` / `docs/reviews/` / 台帳（`.doc-sync.md`）に明文化する方針で、Git で追え、人にも AI にも透明。Cipher の記憶層は**不透明**で「なぜこの判断か」を後から説明しにくい |
| 不採用の理由2 | Claude Code 自体が記憶機構（メモリ・`CLAUDE.md`・コンテキスト圧縮）を持つため、**保管場所が分散**する |
| 不採用の理由3 | 別途サーバー（Docker / DB）の運用・バックアップが要る。**軽量に始められる**性格と合わない |
| 不採用の理由4 | 「正しく記憶しているか」の検証手段が乏しい。ファイルなら `git diff` / `grep` で確認できる |

**再検討の目安**: 「書いたはずだが、どこに書いたか分からない」が頻発する / 同じ判断を3回以上繰り返す /
設計書とレビューが数百件を超えて全体を把握できなくなる。

### 6-2. Chrome DevTools MCP — 実機デバッグ・性能分析

| 評価 | 内容 |
|------|------|
| 良い点 | Performance プロファイリング・Network 解析・Console エラー検知を自動化できる |
| 不採用の理由1 | **Playwright MCP と部分的に重複する**（コンソールログ・DOM スナップショットは取得済み）。追加で得られる情報は、**人が DevTools を開く方が速い**ことが多い |
| 不採用の理由2 | 性能改善は**意図的に行うもの**。設計時に確認計画へ盛り込むか、`/harness-core:code-review` の観点で見るか、問題が起きた時に手動で見る。常時ロードで自動デバッグさせる必要性は薄い |
| 不採用の理由3 | DevTools の情報は量が多く、**トークン消費が大きい** |

**再検討の目安**: 性能課題が継続的に出る / `/harness-nextjs:browser-test` で検出できないエラーが頻発する /
Core Web Vitals の定期記録に価値が出た。

### 6-3. Sequential Thinking MCP — 段階的思考の枠組み

| 評価 | 内容 |
|------|------|
| 良い点 | 判断プロセスが可視化され、論理の飛躍を減らせる可能性 |
| 不採用の理由1 | **ハーネスが既に段階的思考を構造で強制している。** 規模判定 S/M/L → 2段階設計（Stage 1 / Stage 2）→ `/harness-core:design-review` → 実装 → `/harness-core:code-review` という流れ自体がそれにあたる |
| 不採用の理由2 | 常時有効だと単純なタスクでも発動する。**「考えるべきタイミング」は人が決める**方が効率的 |
| 不採用の理由3 | 中間出力のぶんトークン消費が増える |

**再検討の目安**: 推論品質の明らかな低下 / 複雑なアルゴリズム設計が主業務になった。

### 6-4. Memory Bank MCP — ファイルベースの記憶管理

| 評価 | 内容 |
|------|------|
| 良い点 | サーバー不要で軽量。ファイルベースなので思想との衝突が少ない |
| 不採用の理由1 | **既存の設計書群と役割が完全に重複する**（`docs/features/` / `docs/設計書/` / `docs/reviews/` / 台帳）。同じ役割のファイルが2箇所に分散し、どちらが正か分からなくなる |
| 不採用の理由2 | 記憶管理は Markdown の読み書きで完結する。**MCP 層での抽象化は過剰** |
| 不採用の理由3 | 独自形式だと Git 履歴・レビューの一貫性が崩れる |

**再検討の目安**: 設計書では表現しづらい暗黙知が増えた / 複数プロジェクトをまたぐ記憶共有が要る。

## 7. 追加するときのチェックリスト

- [ ] 標準ツールで代替できないことを確認した
- [ ] トークン消費の増加を許容できる
- [ ] プロジェクト全体（`.mcp.json`）／個人（ユーザー単位設定）を区別して適切な側に書いた
- [ ] `.mcp.json` に書いた場合、`.claude/settings.json` の `enabledMcpjsonServers` にも足した
- [ ] プレースホルダを実際の値に置き換えた（絶対パス・ポート等）
- [ ] **Claude Code を再起動**して、MCP ツールが利用可能になったことを確認した
- [ ] 前提条件（uvx・ネットワーク・ポート）をチーム内で共有した
- [ ] 使ってみた結果（有用だった／外した）をこのガイドに追記した
