## ◎ ひと言でいうと

**「同じハーネスを3つコピーして別々に育てていた」のをやめ、
共通部分をプラグインとして1箇所で配信し、環境差分だけを設定ファイルと薄いテンプレートに残した。**

さらに Spec Kit の思想（原則の独立文書化・曖昧さの明示・受け入れ基準ゲート・トレーサビリティ）を、
本体を導入せずに概念だけ取り込んだ。

| 指標 | Before → After（統合直後） | 現在（0.9.0） |
|------|---------------------------|--------------|
| 保守するリポジトリ | **3 → 1** | 1 |
| コミット前チェック hook の実装 | **3本 → 1本** | 1本（config 駆動） |
| 導入済みプロジェクトへの更新反映 | **経路なし → 2経路** | 2経路（`plugin-update` / `harness-update` のスキル2本に定型化） |
| CLAUDE.md | **200行 → 90行（共通）+ 78行（環境）** | 126行（共通）+ 78〜105行（環境） |
| プラグイン | **→ 4**（core / nextjs / unity / wpf） | 4 |
| harness-core の要素数 | **→ skills 10 / agents 3 / hooks 5** | **skills 12 / agents 4 / hooks 7 + テスト/CI** |
| Spec Kit から取り込んだ概念 | **→ 6** | 6 |

> **共通 CLAUDE.md が 90行 → 126行 に増えている。** 肥大化ではなく、
> 設計方針層（0.6.0）・改訂履歴の規約（0.6.4）・スラッシュコマンドが解決しない環境での実行手順（0.6.3）が
> 順に足された結果である。**300行を超えたら整理**という自身の基準（`CLAUDE.md` 肥大化防止）の範囲内。

| Before（統合前） | After（統合後） |
|-----------------|----------------|
| **3つの独立リポジトリ**。実体はどれも「同じハーネスの環境別フォーク」（アプリ本体のコードは含まない） | **1リポジトリ `claude-dev-harness`**（public）に集約 |

## 1. 配布モデル

最大の変化。**「ファイルをコピーする」から「プラグインを購読する」へ。**

| 観点 | Before（コピー派生） | After（プラグイン配信） |
|------|---------------------|----------------------|
| 入手方法 | テンプレートリポジトリを clone / ファイルを手でコピー | `create-project.mjs` でプロジェクト生成 → プラグインを marketplace から導入 |
| 共通部の更新 | ❌ **伝播しない**。各テンプレートに手作業で反映 | ✅ **プラグイン更新で全プロジェクトに届く** |
| 改善の還元 | 派生先の良い改良を戻す仕組みが無い（手作業） | 「改善は必ず core へコミット」が運用ルール化 |
| 名前空間 | 素の `/done`（環境間で衝突しうる） | `/harness-core:done` と自動で名前空間化 |
| バージョン管理 | 実質なし（git ログのみ） | プラグインごとに semver + CHANGELOG。**`autoUpdate` は使わない**と後に決定（§5） |
| 新環境の追加 | 既存テンプレートを丸ごとコピーして書き換え | 環境アダプタ8項目（config / CLAUDE 環境部 / rules / 設計書の軸 / .gitignore・.mcp.json / 動作確認 / 体験系 agent / 追加 hooks）を用意するだけ |

### なぜ「2層」なのか

Claude Code のプラグインは **CLAUDE.md と `.claude/rules/` を配布できない**（公式仕様）。
そのため、運べるものと運べないものを層で分けた。

| 配布物 | 経路 | 更新の伝播 |
|--------|------|-----------|
| skills / agents / hooks / MCP 設定 | プラグイン（marketplace） | **`/harness-core:plugin-update` → 再起動**（0.6.2 でスキル化。それ以前は `claude plugin update` を手で打っていた） |
| CLAUDE.md / rules / docs 骨格 / settings.json / harness.config.json | テンプレート層（生成時コピー） | 半自動 — `/harness-core:harness-update` が差分提示 |

> **当時は「`autoUpdate` に任せる」も選択肢に挙げていたが、後に不採用にした**（§5）。
> また更新を**スキルに寄せた**のは、手で打つと `--scope project` を落として
> 「更新したのに古いまま」になる取りこぼしが**実際に3回連続で起きた**ため。

> **実運用上の注意（C1 実測・2026-08-14）**
>
> | 設定 | 実際の効果 |
> |------|-----------|
> | `extraKnownMarketplaces` | ✅ 初回起動で自動で効く。marketplace が登録・クローンされる（**ダイアログすら出ない**）。そのため `claude plugin marketplace add` は**不要**だった |
> | `enabledPlugins` | ❌ **初回起動ではプラグインが導入されない**（`installed_plugins.json` が空を実測）。2回目以降の起動で project スコープの導入が自動記録された |
>
> したがって**プラグイン導入の CLI 実行は「トラブル時の代替」ではなく正規手順**として案内する。
>
> ```bash
> claude plugin install harness-core@dev-harness
> claude plugin install harness-<env>@dev-harness
> ```
>
> ※ 2回目以降の自動導入が「`enabledPlugins` による導入」なのか「CLI で user スコープに入れた物の
> project 登録」なのかは未切り分け（検証途中で CLI 導入を挟んだため）。
> 実務上は CLI 導入を明示すればどちらでも確実に動くため優先度は低い。

## 2. 環境依存の外出し

「環境依存は5カテゴリに集約される」という調査結果が、統合の技術的な土台になった。

| # | 依存カテゴリ | Before（3テンプレートでの姿） | After |
|---|------------|---------------------------|-------|
| ① | ビルド / lint / 型チェックのコマンド | 各 hook スクリプト内にハードコード | `commands` に外出し（null ならスキップ） |
| ② | トリガーとなるパスパターン | 同上（`src/**` / `Assets/Scripts/**` …） | `paths.source` / `paths.docTriggers` のテーブル駆動 |
| ③ | 設計書の軸（一覧文書の種類） | スキル本文に環境固有の文書名を直書き | `designDocs.docs[]`（file / tracks / sources） |
| ④ | 動作確認手段 | 別実装（Playwright / Unity MCP / UIAutomation） | **環境プラグイン**に分離 + `verification.skill` で指名 |
| ⑤ | 技術ガイド・レビュー観点・規約 | CLAUDE.md に混在 | **テンプレート層**（`CLAUDE.section.md` / `rules/`）に分離 |

①〜③を1つのファイルに外出しした結果、**hooks と大半の skills が全環境で単一実装**になった。

**Before** — 同じ役割の hook が3つの別ファイル。名前も中身も違う:

```js
// Next.js 版（pre-commit-type-check.js）
execSync('npx tsc --noEmit')

// Unity 版（pre-commit-cs-check.js）
// → C# の namespace/クラス名を grep 検査

// WPF 版（pre-commit-build-check.js）
execSync('dotnet build')
```

**After** — 実装は1本。差は設定値だけ:

```jsonc
// harness.config.json
"commands": {
  "build":     "npm run build",
  "typecheck": "npx tsc --noEmit",
  "lint":      "npm run lint",
  "format":    null,
  "test":      null
},
"gates": { "preCommit": ["typecheck"] }

// Unity は commands 全て null / preCommit []
// → 実装は共通のまま、環境ごとに挙動が変わる
```

### 設定契約の全体像

```
.claude/harness.config.json
├ schemaVersion   スキーマ版数（harness-update が引き上げ時に承認を取る）
├ environment     nextjs | unity | wpf
├ commands        build / typecheck / lint / format / test / dev（不要は null）
├ gates           preCommit: 実行するコマンドの並び
├ envOptions      環境固有オプション（例: unity の rootNamespace）
├ paths           source[] / docTriggers[]（パターン → 更新すべき設計書）
├ designDocs      dir / ledger / docs[]（file・tracks・sources）
└ verification    skill（browser-test / unity-verify / capture-screenshots）
                  manualGate（Unity のみ true = 体感確認は人間が行う）
```

## 3. 実装と呼び名の一本化

### 呼び名の分裂を解消

| 対象 | Before（環境ごとにバラバラ） | After（統一） |
|------|---------------------------|-------------|
| 実装レビュー スキル | `review-impl`（Next.js）/ `code-review`（Unity・WPF） | `/harness-core:code-review` |
| コミット前 hook | `pre-commit-type-check.js` / `pre-commit-cs-check.js` / `pre-commit-build-check.js` | `pre-commit-check.js`（1本・config 駆動） |
| 設計書同期の台帳 | `docs/設計書/.doc-sync.md`（Next.js・WPF）/ `docs/.doc-sync.md`（Unity） | `docs/設計書/.doc-sync.md`（config で指定） |
| 開発フロー文書 | `09_開発フローと規模判定.md` / `05_development_flow.md` / `08_開発フローと規模判定.md` | `new-feature` スキル同梱の `開発フローと規模判定.md` |

### プラグインの中身

**太字が統合後に増えたもの。** 骨格（何をどのプラグインに置くか）は統合時から変わっていない。

| プラグイン | skills | agents | hooks / tools |
|-----------|--------|--------|--------------|
| **harness-core**（0.2.0 → **0.9.0**） | new-feature / design-review / code-review / build-check / update-docs / sync-check / complete-feature / pre-push-check / done / harness-update / **proofread-ja**（0.4.0）/ **plugin-update**（0.6.2） | coding-specialist / code-reviewer / documentation-manager / **japanese-proofreader**（0.4.0） | session-start-context / pre-compact-save / **pre-commit-scope**（0.8.0）/ pre-commit-check / post-commit-doc-check / **post-branch-notice**（0.7.0）/ subagent-stop-diff |
| **harness-nextjs**（0.1.0 → **0.3.1**） | browser-test | browser-tester / product-advisor | post-edit-lint / pre-migrate-backup |
| **harness-unity**（0.2.0 → **0.2.1**） | unity-verify | game-designer | pre-commit-cs-check |
| **harness-wpf**（0.1.0 → **0.2.0**） | capture-screenshots | product-advisor | tools/ui-capture.ps1 |

> **増えた4つの性格が揃っている。** `proofread-ja` / `japanese-proofreader` は
> **成果物のほぼ全量が AI の書いた日本語**という統合後に自覚された課題への対処、
> `plugin-update` は**配信経路そのものの運用コスト**への対処である。
> いずれも「作るための機能」ではなく、**回し続けるための機能**が増えている。
>
> 環境プラグインの版が上がっているのは中身の追加ではなく**欠陥の修正**
> （nextjs 0.3.1 の「黙った fail-open」など）。**構成要素は統合時のまま**である。

> **hooks 実装規約も統一された**
> ① 全て Node.js（Windows / コンテナ両対応）
> ② 非公式の `if` フィールドに依存せず stdin JSON を自前判定（WPF 版方式を逆輸入）
> ③ パース失敗時は `exit 0`（fail-open）
> ④ ブロック強度は自己修復可能なら `permissionDecision:"deny"`、人間判断が要るなら `continue:false`（Next.js 版方式）
> ⑤ スクリプト参照は `${CLAUDE_PLUGIN_ROOT}`

### Unity の実運用ノウハウがスキルとして形式化された

| Before | After（`unity-verify` スキル） |
|--------|------------------------------|
| Unity MCP による Editor 操作・動作確認は**実運用では行っていた**が、テンプレートには CLAUDE.md の運用ルール記載のみ | Play モード開始/停止（`manage_editor`）、状態待機（`mcpforunity://editor/state` ポーリング）、スクリーンショット取得までを手順化 |
| スキル化されておらず、手順は各自の頭の中 | 前提として `PlayerSettings.runInBackground = true` を明記（false だと Editor 非アクティブ中にゲームが進まず、MCP 経由の確認が成立しない — 実測で確認） |
| — | それでも `manualGate: true` は維持 — **体感・面白さの判断は人間の仕事**という原則は変えていない |

## 4. 派生劣化・既知バグの解消

コピー派生で実際に起きていた欠落を、統合の過程で塞いだ。

| テンプレート | Before で起きていた問題 | After |
|------------|---------------------|-------|
| Unity | **permissions が丸ごと欠落** — `.env` 読取拒否も `rm -rf` 拒否も無く許可制御ゼロ | 共通の permissions ベースライン（allow / ask / deny）をテンプレート層で全環境に適用 |
| Unity | hook に条件が無く、**あらゆる Bash 呼び出しで node が2プロセス起動** | stdin JSON の自前判定で対象コマンドのみ処理 |
| Unity | `git diff --name-only HEAD~${0:-1}` — シェル構文として不正（コピー時の劣化） | 単一実装なので同種の劣化が起きない |
| Unity | SessionStart / PreCompact / SubagentStop hooks が無い | core の5 hooks が全環境に届く |
| Next.js | `build-check` に `node_modules` 不在ガードが無い | config 駆動 + ツール不在はサイレントスキップの規約 |
| Next.js | TEMPLATE.md の節番号を他ドキュメントが古い番号で参照 | TEMPLATE.md を再構成し参照を整合 |
| WPF | `settings.local.json` に `.env`/secrets の deny が無い | 同上（共通ベースライン） |
| WPF | エンコーディング方針の不統一（BOM 有無が2通り混在） | `.gitattributes` で LF 固定。生成プロジェクトにも引き継ぐ |
| 共通 | rules / statusline / 三層 permissions が Next.js にしか無い | テンプレート層で全環境に配布 |

### 各テンプレートの「良いところ」が全環境に行き渡った

| 出どころ | 改良 | After での扱い |
|---------|------|--------------|
| WPF 版 | プレースホルダ機構 + `init-template.ps1`（dry-run 付き一括置換） | Node 移植して `create-project.mjs` に。全環境で使える |
| WPF 版 | hooks の非公式 `if` 非依存化（stdin 自前判定） | core hooks の実装規約に採用 |
| WPF 版 | CLAUDE.md 肥大化防止 / `git commit` パス指定必須 | 共通 CLAUDE.md・constitution に反映 |
| Unity 版 | `.mcp.json` プロジェクトスコープ採用（Windows のドライブレター大小問題の回避） | 環境テンプレートで維持 |
| Next.js 版 | `.claude/rules/` パス連動ロード / SessionStart 系 hooks / permissions 三層 | core + テンプレート層で全環境へ |

## 5. 導入済みプロジェクトへの更新反映

「ハーネスを直したとき、すでに動いているプロジェクトにどう届くか」。
**統合の目的そのものであり、最も大きく変わった点。**

| Before（届ける手段が無い） | After（層ごとに経路がある） |
|------------------------|--------------------------|
| テンプレートを直しても、**過去に作ったプロジェクトには一切届かない** | **プラグイン層**（skills / agents / hooks / MCP）＝ marketplace 経由で**更新が配信される** |
| 反映したければ **730行の手順書**を人間が読み、Phase ごとにプロンプトを手で実行 | **テンプレート層**（CLAUDE.md / rules / config 等）＝ `/harness-core:harness-update` が**差分を提示して承認のうえ適用** |
| **どこまで適用したかの記録が無い**。プロジェクトごとに「たぶん適用済み」が積み上がる | 「前回どこまで適用したか」は `.claude/harness-baseline.json` に**記録され、コミットされる** |
| ローカル改変を壊さない保証も無い（上書きするか、諦めるかの二択） | ローカル改変は分類して**保護される**（無断上書きをコードで拒否） |
| 結果として**プロジェクトごとにハーネスの版がバラバラに固定される** | 版を固定したいプロジェクトと、常に最新を追いたいプロジェクトを**選べる** |

### 何を直したら、どう届くか

| 直したもの | 層 | 届き方 | 利用側でやること |
|-----------|----|-------|----------------|
| skills / agents / hooks / MCP 設定 | プラグイン | marketplace から配信 | `/plugin` で更新、または `autoUpdate` に任せる |
| CLAUDE.md / constitution.md / `.claude/rules/` / `harness.config.json` / `settings.json` / docs 骨格 | テンプレート | リポジトリを取得して**3点比較** | `/harness-core:harness-update` を実行し、提示された差分を承認 |
| `docs/features/` / `docs/reviews/` / `docs/設計書/`（台帳を除く） | 対象外 | 届かない（意図的） | プロジェクト自身の資産のため、ハーネスは触らない |

### プラグイン層 — 配信される

```
harness を直す → コミット → 【版番号を上げる】 → push
  → 利用側が /plugin 更新 → 全プロジェクトに反映
```

> **最重要の落とし穴: 反映のトリガーは「版番号の変化」（C1 実測）**
>
> **中身だけ変えても利用側には届かない。** `plugin.json` と `marketplace.json` の `version` を
> 上げて初めて更新として認識される。実際に C1 では、修正を入れたのに「還元済み」と扱ってしまい、
> **コミットも版番号の引き上げも push もされていない**状態が発生した。
>
> **還元が完了したと言えるのは3段そろったとき** — ① コミット ② 版番号を上げる（プラグインを触った場合）③ push。
> 手元で試すだけなら `claude plugin uninstall` → `install` → 再起動でよい。

### テンプレート層 — `/harness-core:harness-update` が差分を持ってくる

| 仕組み | 内容 |
|-------|------|
| **3点比較** | **A** = 前回適用した時点のテンプレート / **B** = 最新のテンプレート / **C** = 現物のプロジェクト。A・B は**クローン側の `create-project.mjs` をその時点のコミットで実行して再現**するため、合成規則の二重実装が起きない |
| **基準点の記録** | `.claude/harness-baseline.json`（`templatesCommit` / `environment` / `appliedAt` / `placeholders`）。**コミットする** — チーム全員が同じ基準点を使うため |
| **差分の分類** | `template-improvement` / `project-local` / `already-applied` / `conflict` / `template-removed` |
| **3つのコマンド** | `analyze`（分類して提示）→ `apply`（承認したものを適用）→ `finalize`（baseline を進める） |
| **取得方法** | `git clone --depth 1`。`--repo <path>` でローカルクローンも使える（オフライン用） |

> **「勝手に上書きしない」がコードで担保されている**
>
> - `apply` は **`conflict` と `project-local` の上書きを拒否**する（`--force` で意図的な巻き戻しのみ許可）
> - `finalize` は**未解決の競合が残っていると中断**する — baseline を進めるとテンプレート側の変更が視界から消えてしまうため
> - `template-removed` は**警告するがブロックしない** — 残す判断も有効なため
> - 解析対象は **A ∪ B のファイル集合に限定**。C にしかない巨大ツリー（`node_modules` / Unity の `Library` / `.next` 等）を舐めない
> - `harness.config.json` は**スキーマ差分**として扱う（新フィールドの追加提案・既存値の保持・`schemaVersion` 引き上げ時はユーザー承認）

### 反映方針を選べるようになった → 後に「層で分ける」へ確定した

当時は**プロジェクト単位で `autoUpdate` か版固定かを選ぶ**構図で整理し、
「どちらを既定にするかは実運用の判断待ち」としていた。**その判断は後に出ている（C5・2026-08-15 決定）。**

| | 当時の整理 | 現在の方針 |
|--|-----------|-----------|
| 分ける軸 | **プロジェクト単位**（このプロジェクトは自動 / あれは固定） | **層単位**（プラグイン層は常に最新 / テンプレート層は区切りで） |
| `autoUpdate` | 選択肢の一つ | **使わない** |

**軸がプロジェクトから層へ移ったのが要点。** 追従のコストが層によって桁違いに違うためである
— プラグイン層はコマンド1本と再起動で**判断がゼロ**、テンプレート層は競合の統合に**中身を読む判断**が要る
（0.2.3 → 0.5.0 の追従で競合4件すべてに判断が必要だった実測）。

`autoUpdate` を捨てたのは、プラグインが**セッション起動時に読み込まれる**ため、
自動で版が変わると**「今このセッションが何を読んでいるか」が曖昧になる**から。
更新のタイミングを自分で握っていれば、いつ何が変わったかを追える。

> **Before は選択肢自体が存在しなかった。** 「手で当てるか、当てないか」だけで、
> 結果的に**全プロジェクトが放置され版が固定**されていた。
> 詳細は [運用ガイド §1-2](../guide/運用ガイド.md)。

> **この節の要点**
>
> **「直した」＝「届いた」ではない。** 統合前は届ける手段そのものが無かったが、統合後は
> **プラグイン層＝配信（版番号がトリガー）／ テンプレート層＝差分提示と承認（baseline が基準）**
> という2つの経路が用意され、どちらも**ローカル改変を壊さないこと**を前提に設計されている。

## 6. 使う側から見た変化

| 場面 | Before | After |
|------|--------|-------|
| プロジェクトを始める | テンプレートを clone → 手順書を読んで置換・削除 | `node tools/create-project.mjs`（base + 環境を合成 / dry-run 可）→ プラグイン導入 |
| スキルの呼び出し | `/new-feature`, `/done` | `/harness-core:new-feature`, `/harness-core:done`（慣れの問題。環境間の名前衝突は起きなくなる） |
| セッション開始時 | テンプレートによっては何も出ない | core の SessionStart hook が文脈を注入。`harness.config.json` が無ければ「設定不在」として素通り |
| ハーネスを改善したい | 目の前のプロジェクトを直して終わり（他に届かない） | `claude-dev-harness` にコミット → 全プロジェクトへ配信 |
| プロジェクト固有の事情 | テンプレートを直接書き換える＝以後の追従が困難に | ローカル改変は `project-local` として保護され、上書きされない |

## 7. 既存プロジェクトへの導入

「すでに動いているプロジェクトにハーネスを後入れする」観点。
**統合の効果が最も大きい部分と、まだ穴が残っている部分が同居している。**

| Before（全部コピー、全部手作業） | After（ロジックは2コマンドで入る） |
|------------------------------|--------------------------------|
| skills / agents / hooks を**ファイル単位でコピー**するしかない | skills / agents / hooks の実体は**プラグイン**なので、既存プロジェクトでも `claude plugin install` **2行で入る** |
| コピー先の環境に合わせて**中身を書き換える**必要がある（コマンド・パスがハードコードされているため） | 環境依存はハードコードされていないため、**書き換え不要** |
| 手順は**730行の手順書**を人間が読み、Phase ごとにプロンプトを手で実行 | 代わりに `.claude/harness.config.json` を**1つ書く**（＝設定契約を満たす）だけで core が動き出す |
| コピーした瞬間に**そのプロジェクト専用のフォーク**になる（以後の改善は届かない） | プラグインは**フォークにならない**ので、以後の改善も同じ経路で届く |

> **KEY INSIGHT**
>
> 統合の副産物として、**既存プロジェクトへの導入コストが「コピーと書き換え」から
> 「インストールと設定1ファイル」に変わった。** ハーネスの**ロジックの大半
> （skills 12 / agents 4 / hooks 6）はプラグイン層**にあるため、それだけなら既存プロジェクトでも
> 新規と同じものが即座に手に入る。

### 導入の3ケース

**当時 ❌ だった2ケースのうち ③ が解決した。** ①③ は実測済み、② だけが未実測で残っている。

| ケース | プラグイン層 | テンプレート層 | 当時 | 現在 |
|-------|------------|--------------|------|------|
| **① 新規プロジェクト**（`create-project.mjs` で生成） | install 2行 | 生成時にコピー + `harness-baseline.json` 記録 | ✅ 検証済み | ✅ 検証済み |
| **② ハーネス未適用の既存プロジェクト**（アプリのコードが既にある） | install 2行 + `harness.config.json` を書く | 必要な物を選んで手でコピー（baseline が無い状態から始まる） | ❌ 未検証・手順書なし | ◐ **手順はある**（[セットアップガイド §7](../guide/セットアップガイド.md)）が**実測なし** |
| **③ 旧テンプレート由来のプロジェクト** | install 2行 + **既存 hooks の無効化が必須** | 移行指示書に従って仕分け・移送し、`harness-baseline.json` を書く | ❌ **当面なにもしない**と決定 | ✅ **実測3本**（nextjs）。**[既存プロジェクト移行指示書](../guide/既存プロジェクト移行指示書.md)** が 1.8 まで育っている |

> ### ③ の判断は覆った
>
> 当時「当面なにもしない」としたのは、**差分が全て「競合」扱いになる**ことを理由に
> 費用対効果が低いと見たためだった。実際にやってみると、**競合の山は本質的な障害ではなかった**
> — 効いたのは `harness-update` ではなく、**ローカル資産を blob ハッシュで仕分けして
> 「改変の正体」を特定し、移送先を決める**という別の手順だった（実測では改変の正体は
> **すべてドキュメントパスの埋め込み**で、`designDocs` と `rules/` へ移送できた）。
>
> **「想定していた障害を潰す」のではなく「そもそも別の道具が要る」と分かった**型の覆り方である。
>
> なお ③ で最も重かったのは移行そのものではなく、**移行後の棚卸し**だった
> — 残すと決めた設計方針文書の過半が実は実態スナップショットで、
> 削除8本・約105KB に達した。これも当時は視界に無かった作業である。

### ②③ を実際にやる場合の順序（設計上の整理）

```
1. プラグイン導入 → 2. harness.config.json を書く → 3. 既存 hooks の無効化
  → 4. テンプレート層を選択的に導入 → 5. 設計書の初版を作る
```

**1〜2 だけでも動く**のが統合後の利点。`harness.config.json` が無い場合、
core の hooks / skills は**「設定不在」として素通りする**（fail-open 設計）ため、段階的に入れられる。

| # | やること | 注意点 |
|---|---------|-------|
| 1 | `claude plugin install harness-core@dev-harness` / `claude plugin install harness-<env>@dev-harness` | これだけで skills / agents / hooks が入る。**ファイルのコピーは発生しない** |
| 2 | `.claude/harness.config.json` を作る | 既存プロジェクトの実態（build コマンド・ソースパス・設計書の軸）を書く。**ここが唯一の環境適応作業** |
| 3 | プロジェクト側 `.claude/hooks/` の無効化 | **③ では必須。** プラグインの hooks と**二重に走る**（コミット前チェックが2回、設計書チェックが2回） |
| 4 | CLAUDE.md / constitution.md / rules/ / docs 骨格 | 既存の CLAUDE.md がある場合、**`create-project.mjs` は同名ファイルを上書きする**（警告は出るが止まらない）。既存プロジェクトへ直接実行してはいけない |
| 5 | 設計書（`docs/設計書/`）と台帳の初版 | 既存コードから起こす必要がある。`sync-check` の converge が使えるが、初回は量が多い |

### 既知の障害

| 障害 | 内容と対処 |
|------|-----------|
| **hooks の二重発火** | 旧テンプレート由来のプロジェクトは `.claude/hooks/` を持っている。プラグイン側と同じ役割の hook が両方走る。**プロジェクト側の無効化が必要** |
| **baseline が無い** | `harness-update` は3点比較が前提。A が無いため**2点比較になり、差分が全て「競合」として提示**される（安全側に倒した設計）。`--set PROJECT_NAME=...` でプレースホルダ値を渡す必要がある |
| **スキル呼称の変更** | `/new-feature` → `/harness-core:new-feature`。**プロジェクト内の文書に書かれた参照も更新**が要る |
| **`create-project.mjs` は上書きする** | 非空ディレクトリでも**止まらず、同名ファイルを上書き**する（警告のみ）。既存プロジェクトへの後入れツールではない |
| **逆方向でも摩擦がある** | C1 で実測 — **ハーネス適用済みリポジトリにフレームワークを入れる**方向も詰まる。`create-next-app` は非空ディレクトリを拒否し、生成物の `CLAUDE.md` / `AGENTS.md` をそのまま取り込むと**プロジェクトの CLAUDE.md を破壊する** |

> **正直な現状（2026-08-16 更新）**
>
> **③ は解決した。** 旧テンプレート由来のプロジェクトへは
> [既存プロジェクト移行指示書](../guide/既存プロジェクト移行指示書.md)（エージェントへそのまま渡す手順書）があり、
> **nextjs で3本通っている**。手順書は実測のたびに 1.0 → 1.8 まで育っており、
> **想像で書いた手順は含まれていない**。
>
> **残る穴は2つ。**
>
> | 穴 | 内容 |
> |----|------|
> | **② の実測がない** | 「プラグイン導入 → config 1ファイル」で動くのは今も**設計上そうなるという整理**にとどまる。セットアップガイド §7 に手順の骨格はあるが、一度も通していない |
> | **unity / wpf の移行が未実測** | 実測はすべて **nextjs**。config 契約で環境差を吸収する設計なので原理的には同じはずだが、**「はず」であって実測ではない** |
>
> したがって推奨は **「新規プロジェクトから適用する。旧テンプレート由来なら移行指示書に従う」**。
> ② に当たる場合は、まず1本試して手順を確定させるのが順当（③ で得た教訓の大半は流用できる）。

## S. Spec Kit を取り入れたことによる違い

> **結論: 本体は導入しない。思想と成果物構造の概念だけを harness-core に取り込む。**
>
> 理由は ①既存ハーネスと機能が大幅に重複し `docs/features/` と `specs/` で真実が二重化する
> ②リリース間隔 1〜3日・破壊的変更ありで、追随コストが「メンテコスト削減」という統合目的と矛盾する
> ③公式の Claude Code プラグインが存在せず今後も出ない方針でプラグイン配信に乗らない
> ④規模適応が「人間が2経路を選ぶ」までで、S/M/L 自動判定を持つ既存ハーネスの方が優れている
> ⑤実装後の生きた設計書・台帳・レビューエージェント・hooks ゲートは Spec Kit 側に無い。

### 取り込んだ6つの概念

| Spec Kit の概念 | 取り込み先 | Before | After（実装された姿） |
|----------------|-----------|--------|---------------------|
| **constitution**（プロジェクト原則の独立成果物化） | `templates/base/constitution.md` | 原則も手順も技術ガイドも CLAUDE.md（200〜255行）に同居。何が「絶対に守る原則」かが埋もれる | **原則だけを独立文書に**。手順は書かない（手順はスキルが持つ）。**変更にはユーザーの明示承認が必要**、原則が衝突したら番号の小さい方を優先、と明記。CLAUDE.md は共通部90行 + 環境部78行に縮小 |
| **clarify**（曖昧さの体系的な解消） | `new-feature` スキル Step 2 | 曖昧なまま設計書を書き進め、AI が**推測で空欄を埋める**余地があった | Stage 1 承認前に `[NEEDS CLARIFICATION: 何が不明か]` マーカーで未確定事項を洗い出し、質問して潰す。**L 規模は必須**、M でも曖昧なら実施。潰せない項目は「3-3. 未解決事項」表に `❓未解決` のまま明示的に残す（推測禁止） |
| **checklist**（受け入れ基準のゲート化） | TEMPLATE.md §3-2 + `complete-feature` | 完了判断が「動いたっぽい」「ビルドが通った」に流れやすい | Stage 1 に**テスト可能な受け入れ基準チェックリスト**を持たせ、**これを完了ゲートにする**。未チェック項目が残ったまま完了処理をしない |
| **analyze**（成果物間の整合検査） | `design-review` スキル Step 3 | Stage 1 の要求が Stage 2 に落ちているか、タスクに反映されているかは**目視頼み** | **トレーサビリティ検査**を全モード共通・軽量ステップとして追加。要求→設計→タスクの反映漏れを対応表で示し、漏れ件数を報告フォーマットに含める |
| **converge**（実装↔成果物の突合と残作業の追記） | `sync-check` スキル Step 3 | 乖離を**見つけて報告して終わり**。タスク化は人任せ | 発見を**機能設計書のタスク一覧に追記提案**する。実装済み・設計書未記載 → ✅完了として逆追記／設計書あり・実装なし → 🔵未実施として追記。**追記は必ずユーザーに提示してから** |
| **tasks の3層分離**（WHAT / HOW / TASK） | TEMPLATE.md §2 | Stage 1（WHAT）と Stage 2（HOW）はあったが、TASK 層は付随物扱い | タスク一覧を**第一級の成果物**に。L 規模では依存関係・並列実行可否を持たせる |

### 機能設計書テンプレートの構成変化

| Before | After（★ = Spec Kit 由来） |
|--------|--------------------------|
| 概要 / タスク一覧 | 1. 概要（背景 / 目的 / 方針） |
| Stage 1: 機能・画面設計 | 2. タスク一覧 ★第一級化 |
| Stage 2: 技術設計 | 3. 機能・画面設計（Stage 1）— 3-1. 対象と操作フロー / ★3-2. **受け入れ基準チェックリスト** / ★3-3. **未解決事項** / 3-4. Stage 1 レビュー記録 |
| 動作確認計画 | 4. 技術設計（Stage 2）4-1〜4-5 |
| 改訂履歴 | 5. 動作確認計画（5-1〜5-5 に細分化 — WPF 版由来）/ 6. 関連ドキュメント / 7. 注意事項 / 改訂履歴 |

**Before の問題**: 「未確定事項」「受け入れ基準」を書く欄が定位置になく、暗黙知になっていた。

### 最重要: 規模ゲート原則 — Spec Kit の弱点を持ち込まない

Spec Kit 最大の批判点は「小さな変更にも重いセレモニーを課す」こと。
概念を取り込むにあたり、**これを自分のハーネスに再導入しない**ことを constitution の第1原則にした。

| Spec Kit の経路選択 | 統合ハーネスの規模ゲート |
|-------------------|----------------------|
| `shorter path` ＝ specify → plan → tasks → implement | 規模判定 S/M/L → S・M ＝ 軽量フロー |
| `full path` ＝ constitution → specify → clarify → plan → checklist → tasks → analyze → implement → converge | └→ L ＝ 2段階設計 + 設計レビュー + 網羅同期チェック |
| **経路は人間が選ぶ**。規模の自動判定は無い | **AI が推測 → ユーザーが承認**の2ステップ（AI 単独で確定させない）。迷ったら L 寄り。**UX 変更を含む場合は自動的に L**。フル形パイプラインは **L 規模のみ**に課す。ただし **analyze / converge 相当のトレーサビリティ検査は軽量なので全規模に適用** |

> **取り込みの結果、カバー範囲は Spec Kit 本体より広い**
>
> 要求 → 設計 → タスク → 実装 → **実態設計書（`docs/設計書/` ＋ `.doc-sync.md` 台帳）** の
> 全区間にトレーサビリティチェックが通る。Spec Kit 本体は「実装後の生きた設計書」を持たないため、
> この最後の区間が無い。

### 将来 Spec Kit 本体を試すときの指針（記録）

- `--script py` を指定（生成スキルの OS 固有パスハードコード問題の回避）
- 独自テンプレートは preset 化（`wrap` 戦略）して `specify integration upgrade` の保護を受ける
- 日本語テンプレートは文字化け検証ステップを組み込む（エンコーディング系は修正済みだが CP932 実測は未確認）
- 併用は **L 規模1機能のパイロットに限定**し、`docs/features/` と `specs/` の二重管理を常態化させない

詳しい対比は [02_SpecKitとの差異.md](02_SpecKitとの差異.md)。
