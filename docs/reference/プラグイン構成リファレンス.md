# プラグイン構成リファレンス — どのフォルダ・ファイルが何のためにあるか

| 項目 | 内容 |
|------|------|
| 作成日 | 2026-10-11 |
| 対応ハーネス版 | harness-core 0.40.2 / harness-nextjs 0.5.3 / harness-unity 0.5.3 / harness-wpf 0.5.0 / harness-android 0.3.0 |
| 最終更新 | 2026-10-11 |
| 読者 | **プラグインを直す人**。「このフォルダは何のためにあるのか」「新しく足すならどこか」を引く |

**この文書は種別の決め事を書く。個々のスキル名・フック名の一覧は持たない**
（増減のたびに腐るため）。一覧は [README §harness-core が提供するもの](../../README.md#harness-core-が提供するもの) と
[フック発火タイミング図 §フック一覧](../diagrams/05_フック発火タイミング図.md#フック一覧発火点と止められるか)が正。
**プラグイン以外**（`templates/` / `tools/` / `tests/`）はそれぞれの README が正で、§7 に入口だけ置く。

## 0. 全体の見取り図

**ファイルは書かない**（増減で腐る）。**主要なディレクトリと、その役割の境目だけ**を示す。

```
claude-dev-harness/
├── .claude-plugin/        配信カタログ（marketplace.json）… 版番号がここにも要る → §2
├── plugins/               ★ 配信される層。プラグイン1本ずつ → §1〜§6
│   ├── harness-core/          環境非依存（全環境で同一）
│   └── harness-<env>/         環境ごとの拡張（core と併用する）
├── templates/             配信されない層。生成時にコピーされる → §7
├── tools/                 ハーネス自体のツール（利用側には届かない）→ §7
├── tests/                 判定ロジックの検査（node --test）→ §7
├── .claude/               このリポジトリ自身のガード → §7
└── docs/                  ハーネスの仕様・運用文書（この文書もここ）

plugins/<plugin>/          ← プラグイン1本の中身（§1 の5つ）
├── .claude-plugin/        マニフェスト（版番号・メタ情報）… 必須 → §2
├── skills/                手順書。人が名前で呼ぶ → §3
│   └── <name>/
│       ├── SKILL.md           スキルの実体
│       └── scripts/           Claude が Bash で実行する（ESM）
├── agents/                別コンテキストの人格定義 → §4
├── hooks/                 自動発火の関所 → §5
│   ├── hooks.json             登録表
│   └── scripts/               フック本体 ＋ 共有モジュール（CommonJS）
└── tools/                 スキルから呼ぶ再利用ライブラリ → §6
```

**境目は「配信されるか」**。`plugins/` だけが版番号つきで利用側へ届き、
`templates/` と `tools/` は**届かない**（届かせたいときの形は §3-4）。

## 1. プラグイン1本の中身

`plugins/<plugin>/` の下で**このリポジトリが使っているのは次の5つ**である。
**ランタイムが読めるものの全部ではない**（スラッシュコマンドを `commands/` で持つ形は使っていない。
スキルが `/<plugin>:<name>` の入口を兼ねるため、**同じ入口を2通りで持たない**）。

| ディレクトリ | 誰が読むか | 中身の性質 | 必須 |
|------------|-----------|-----------|------|
| `.claude-plugin/` | Claude Code ランタイム（導入時） | **マニフェスト**。版番号とメタ情報 | ✅ |
| `skills/` | **メイン Claude**（文脈に読み込まれる） | **手順書**。人が名前で呼ぶ | — |
| `agents/` | **メイン Claude**（`Agent()` で起動する） | **別コンテキストの人格定義** | — |
| `hooks/` | **ランタイム**（イベントで自動起動） | **関所**。Claude の判断を介さない | — |
| `tools/` | **スキルの手順の中から**呼ばれる | 再利用ライブラリ（スキルに属さない実行物） | — |

**マニフェスト以外はすべて任意。** フックを1本も持たない環境プラグインもある
（どれが持つかは [README §環境プラグイン](../../README.md#環境プラグイン)）。

**どれも `${CLAUDE_PLUGIN_ROOT}` を起点に参照する。** これは**キャッシュへコピーされた後の
プラグインの置き場**に展開される（ソースのパスではない。
[プラグイン開発手順 §0](プラグイン開発手順.md#0-まず理解しておくこと)）。

> **プラグインをまたいだ参照はしない。** `${CLAUDE_PLUGIN_ROOT}` はプラグインごとに別の場所を指し、
> 他プラグインが導入されている保証も無い。だから環境プラグインは core のライブラリを使わず、
> **必要な最小ヘルパを自前で持つ**（§5-3）。

## 2. `.claude-plugin/plugin.json` — 版番号が2箇所ある理由

| ファイル | 置き場 | 役割 |
|---------|--------|------|
| `plugins/<plugin>/.claude-plugin/plugin.json` | プラグインの中 | **そのプラグイン自身の宣言**。`name` / `version` / `description` / `author`（**オブジェクト**。`{ "name": ... }`）/ `homepage` / `repository` / `license` / `keywords`（**配列**） |
| `.claude-plugin/marketplace.json` | **リポジトリ直下** | **配信カタログ**。`plugins[]` に各プラグインの `name` / `source`（`./plugins/<plugin>` の相対パス）/ `version` / `description` を並べる |

**書き方は既存の1本をそのまま写すのが早い**（`plugins/harness-core/.claude-plugin/plugin.json`）。
型を間違えるとマニフェストの検証で弾かれる（[プラグイン開発手順 §方法A](プラグイン開発手順.md#方法a-直して入れ直す) の手順2）。

**カタログ側も版番号を持つ。** 利用側の `claude plugin update` が見るのはカタログで、
`plugin.json` だけ上げても届かない（逆も同じ）。**必ず2箇所そろえる**
（手順は [プラグイン開発手順 §方法C](プラグイン開発手順.md#方法c-版を上げて-push-する)）。

## 3. `skills/<name>/` — 手順書とその付属物

```
skills/<name>/
├── SKILL.md        # 必須。これがスキルの実体
├── <参照用>.md     # 任意。SKILL.md から読ませる雛形・チェックリスト
└── scripts/        # 任意。SKILL.md の手順の中で Claude が Bash で実行する
```

### 3-1. `SKILL.md` の frontmatter

| キー | 必須 | 意味 |
|------|------|------|
| `name` | ✅ | スキル名。**ディレクトリ名と一致させる**（`/<plugin>:<name>` で呼ばれる） |
| `description` | ✅ | **何をするスキルか・いつ呼ぶか**。Claude が自然文の依頼からこのスキルを選ぶ判断材料になるので、入口になる言い回しを含める |
| `allowed-tools` | ✅ | 使うツールの宣言。`"Bash(git log:*), Read"` のように**サブコマンド単位**で絞れる |
| `argument-hint` | 任意 | 引数の説明（`"[機能名 or 修正内容]"`）。引数を取るスキルには書く |

**使うのはこの4つだけ。** `arguments:` というキーが1本だけに残っているが、
**ソースにもテストにも参照が無く、どこからも読まれていない**（引数の宣言は `argument-hint` が正）。
**真似しないこと。**

`disable-model-invocation` は**どのスキルにも付けていない**
（理由は [役割比較図 §スキル](../diagrams/03_役割比較図.md#要素ごとの補足)）。

### 3-2. 同梱する `.md` は「SKILL.md から読ませるもの」だけ

`SKILL.md` が長くなるからといって分割するのではなく、**手順とは別の読み物**を置く。
雛形（設計書の `TEMPLATE.md`）・観点表（`checklist.md`）・判定基準の解説がこれに当たる。

### 3-3. `skills/<name>/scripts/` は `hooks/scripts/` とは別物

| | `skills/<name>/scripts/` | `hooks/scripts/` |
|--|------------------------|------------------|
| **起動するのは** | **Claude**（`SKILL.md` に書いた Bash コマンドとして） | **ランタイム**（イベント発火） |
| **拡張子・形式** | `.mjs`（**ESM**） | `.js`（**CommonJS**） |
| **入力** | コマンドライン引数（`--json` 等） | **stdin の JSON** |
| **出力** | 人／Claude が読む JSON・テキスト | ランタイムが解釈する JSON |
| **失敗したら** | Claude が結果を見て判断する | **設定の不在・パース失敗は fail-open**（`exit 0` で素通り）。**判定が成立したうえでの不合格は `deny` を返す**（どのフックが止めるかは [05 図 §フック一覧](../diagrams/05_フック発火タイミング図.md#フック一覧発火点と止められるか)） |

どちらも**依存パッケージを入れず Node 標準ライブラリだけで書く**。

> **判定ロジックを `SKILL.md` の散文で書かない。** 同じ判定を人が目で追うと再現しないため、
> スクリプトへ出して [`tests/`](../../tests/README.md) で守る（CLAUDE.md §4）。
> スキルから `hooks/scripts/` の共有モジュールを `node -e` で require して使う形もある（§5-2）。

### 3-4. 配信されないものへの橋渡しは scripts が担う

`tools/create-project.mjs`（リポジトリ直下）は**プラグインに含まれないので利用側に届かない**。
`skills/create-project/scripts/create.mjs` は、**リポジトリを一時取得してそちらを実行する薄い層**で、
生成ロジック自体は持たない。**同じ処理を2つ持たない**ための形で、
「配信されない実装を使いたい」ときの既定の解き方である。

## 4. `agents/<name>.md` — 別コンテキストの人格定義

1エージェント1ファイル。本文がそのまま**起動される Claude への指示**になる。

| キー | 必須 | 意味 |
|------|------|------|
| `name` | ✅ | エージェント名。**ファイル名と一致させる** |
| `description` | ✅ | **いつ起動するか**。メイン Claude がこれを読んで起動を決めるので、呼ばれたい場面を書く |
| `model` | ✅ | 使うモデル。**既定は `sonnet`**。上げるなら**理由を `description` に書く** |
| `color` | 任意 | 表示色 |
| `tools` | 任意 | **省略すると全ツールが使える。** 書くと**そこに書いたものだけ**に絞られる |
| `mcpServers` | 任意 | 前提とする MCP サーバー（`["playwright"]` 等）。**ハーネスは MCP を配らない**（§7） |

> ⚠️ **`tools` を「念のため」書かない。** 省略が全許可なので、**書いた瞬間に機能を削る**ことになる。
> 実際、`browser-tester` の不調を `tools` の不備と見て足そうとしたが、
> **元はその項目自体が無く、足していれば逆に絞っていた**（CLAUDE.md §8）。

`model` が全エージェントに在ることと既定が `sonnet` であることは [`tests/`](../../tests/README.md) が検査する。

## 5. `hooks/` — 登録表とスクリプト

```
hooks/
├── hooks.json      # どのイベントで何を起動するかの登録表
└── scripts/        # フック本体と、共有モジュール（どちらも CommonJS）
```

### 5-1. `hooks.json`

イベント名（`SessionStart` / `PreToolUse` / `PostToolUse` / `PreCompact` / `SubagentStop` …）ごとに、
`matcher`（対象ツール名の正規表現。`SessionStart` では起動種別）と `hooks[]` を並べる。
各要素は `type: "command"` / `command`（`node "${CLAUDE_PLUGIN_ROOT}/hooks/scripts/<名前>.js"`）/
`timeout`（秒。既定の上限は 600）/ `statusMessage`（実行中の表示）を持つ。

**同じイベント・同じ matcher に複数登録すると、書いた順に走る。**
時間予算の決め方は [harness設定契約 §6](harness設定契約.md#6-hook-の時間予算とイベント登録実装上の決定)。

### 5-2. `hooks/scripts/` には2種類が入る

**すべて Node.js（CommonJS）。** PowerShell / Bash は使わない（Windows・コンテナ両対応のため・CLAUDE.md §7）。

| | **フック本体** | **共有モジュール** |
|--|--------------|------------------|
| `hooks.json` への登録 | ✅ する（**ファイル名が登録名と対応する**） | ❌ **しない** |
| 使われ方 | ランタイムが `node` で起動する | 他のフックが `require("./<名前>")`。**スキルから `node -e` で require することもある** |
| 書き方 | stdin の JSON を読み、判定して JSON を返す | `module.exports` で**純関数**を出す |
| テスト | 本体は薄く保つ | **ここを [`tests/`](../../tests/README.md) で守る**（CLAUDE.md §4） |

**判定ロジックは共有モジュール側へ出す。** フック本体に埋めると `tests/` から呼べなくなり、
**同じ判定を複数のフックが持つ**ことにもなる（1つのモジュールを複数の本体が require している形が既にある）。

### 5-3. `harness-lib.js` と `plugin-lib.js` — 重複は意図的

| ファイル | 置き場 | 中身 |
|---------|--------|------|
| `harness-lib.js` | **core のみ** | config の読み込み・git 操作・コマンド実行・通知・マーカーの受け渡しなど、core のフックが共有する一式 |
| `plugin-lib.js` | **フックを持つ環境プラグインが1本ずつ** | `projectDir` / `readPayload` / `loadConfig` / `commandFor` / `emit` / `notify` 程度の**最小ヘルパ** |

**環境プラグインは `harness-lib.js` を require しない**（§1 のとおりプラグイン間参照が成立しないため）。
**同じ関数が各プラグインに重複しているのは承知のうえの設計**で、まとめようとすると参照が壊れる。
直すときは**どちらを直したのかを意識する**（core 側の修正は環境側へ自動では波及しない）。

> **フックを持たない環境プラグインには `plugin-lib.js` も無い。** 「あるはず」と思って
> `require` を書くと、**フックは fail-open なので静かに素通りして動かない**。
> 新しくフックを足すときは、そのプラグインに `hooks/` と `plugin-lib.js` があるかを先に見る。

## 6. プラグイン内の `tools/`

**スキルに属さない再利用物**の置き場。例として `harness-wpf` が、
`SKILL.md` の手順から dot-source して使う PowerShell ライブラリ（`ui-capture.ps1`）を置いている。

> **`.ps1` だけは UTF-8 BOM 付きで保存する。** Windows PowerShell 5.1 は BOM 無し UTF-8 を
> CP932 と誤読して日本語が化け、BOM が唯一の判別材料になる（CLAUDE.md §7）。
> **フックに `.ps1` は使えない**（§5-2）。ここに置けるのは**スキルから呼ぶもの**だけ。

## 7. プラグインの外（配信されない層）

| 置き場 | 役割 | 正の文書 |
|--------|------|---------|
| `templates/` | プラグインでは配れないもの（`CLAUDE.md` / `constitution.md` / `.claude/rules/` / 各種 config / `.mcp.json` / `docs/` 骨格）を**生成時にコピーする層** | [templates/README.md](../../templates/README.md) |
| `tools/` | ハーネス自体のツール（プロジェクト生成・実物との食い違い検査） | [tools/README.md](../../tools/README.md) |
| `tests/` | 判定ロジックの検査（`node --test`） | [tests/README.md](../../tests/README.md) |
| `.claude/` | **このリポジトリ自身**のガード（`repo-guard.js`） | [CLAUDE.md](../../CLAUDE.md) §9 |

**MCP はハーネスが配らない。** 環境プラグインは `agents/` の `mcpServers` で**前提として要求する**だけで、
接続先の宣言は `templates/<env>/.mcp.json`、サーバーの実体は外部プロセスである
（[役割比較図](../diagrams/03_役割比較図.md)）。

## 8. 新しく足すときの判断

| 足したいもの | 置き場 |
|------------|--------|
| 人が名前で呼んで進める手順 | `skills/<name>/SKILL.md` |
| その手順が読む雛形・観点表 | `skills/<name>/<名前>.md` |
| その手順が実行する処理 | `skills/<name>/scripts/*.mjs`（ESM・引数で受ける） |
| イベントで自動的に走る検査・通知 | `hooks/scripts/<名前>.js`（CommonJS・stdin で受ける）＋ `hooks.json` へ登録 |
| **複数のフック・スキルから使う判定** | `hooks/scripts/<名前>.js`（**登録しない**・`module.exports` で純関数・`tests/` で守る。§5-2） |
| 別コンテキストで判断させたい専門役 | `agents/<name>.md`（`tools` は**省略が全許可**。§4） |
| 複数のスキルから使う実行物 | `tools/`（プラグイン内） |
| **外部プロセスへの窓口（MCP）** | `templates/<env>/.mcp.json`。**プラグインでは配れない**（§7） |
| プロジェクト側に置かれるべき前提・設定 | `templates/`（＝**プラグインではない**） |
| **環境ごとの拡張を1本まるごと** | `plugins/<plugin>/` を作り、`.claude-plugin/plugin.json` と `marketplace.json` の `plugins[]` の**両方**に登録する（§2） |
| 判定の正しさを固定したい | `tests/*.test.mjs` |

**どれを足しても版番号を2箇所上げる**（§2）。**フック・スキル・エージェントの増減は、
一覧を持っている文書を grep して全部当てる**（[CHANGELOG 冒頭](../../CHANGELOG.md)の「対象は思い出さず、grep で出す」）。

**この文書のヘッダの「対応ハーネス版」は、記述した挙動の版である**（最新への追従義務は持たない。
CHANGELOG 冒頭の規約どおり）。種別の決め事が変わったときだけ上げる。
